# PureEOS 整链抗量子实施计划

日期：2026-11-04 · 修订：R1 · 状态：实施设计；不代表已实现或已激活抗量子功能。

英文对应版本：[Full English plan](FULL_CHAIN_POST_QUANTUM_PLAN.en.md)。可复核源码清单：[SOURCE_AUDIT.json](SOURCE_AUDIT.json)。

## 1. 实施目标、完成含义与本轮授权

目标是使激活后的链安全、资产授权、治理和经认证的验证流程，不再依赖攻击者无法伪造 K1、R1、WebAuthN 椭圆曲线签名或 BLS 签名这一假设。钱包增加一种签名选项只是中间交付物。

本计划对“整链抗量子”的验收范围定义如下：

1. 所有能够改变受保护状态的外部主体均须满足抗量子授权策略，包括父权限、委托账户、资源赞助者、BP 管理、中继权限、恢复与升级权限。
2. 出块者认证、active 与 pending 两套最终确认策略均须要求抗量子证明。仅凭传统签名不能确立最终性、替换委员会或授权升级。
3. 新的安全承诺采用明确审核的哈希方案；抗量子签名与真实交易、代码、策略、检查点之间，不能只由一个较短的旧哈希连接。
4. 历史回放、引导、快照、轻客户端和历史策略交接均保持上述安全边界。
5. 宣称保护范围内的所有持币合约，均须完成授权路径复盘。任意未来 WASM 可以自行实现不安全的授权；原生权限升级无法证明所有应用逻辑都安全。
6. 钱包分发、管理通道、服务响应认证与密钥保管单独验收。仅支持传统签名的操作系统安装器、证书根或远程管理凭据，在替换或获得独立保护之前仍是外部安全假设。

当前授权交付物是源码复盘、中英文两份 Markdown 计划和 Git 上传。本轮不执行实现、链操作、协议激活、新增服务器、TPS 测试或生产发布。后续阶段是拟议实施顺序，不是现在执行的控制命令。

当前链、原有 26 个节点进程、普通业务、历史服务、唯一创世 HTTP 中继、既有禁令、投票、保证金、代币上限和发行制品均不属于本次文档变更。提案 #3 继续保留 pending/vetoed；不得为了本计划而取消或覆盖它。

## 3. 威胁模型与安全不变量

假设未来攻击者能够伪造当前使用的椭圆曲线和 BLS 签名，同时考虑恶意中继／RPC／P2P 节点、畸形编码、降级攻击、泄露的历史密钥、进程崩溃、过期快照和索引覆盖不完整。不得假设旧公钥始终不公开，也不得把公钥哈希当作永久免除公钥暴露风险的办法。

设计仍依赖足够的诚实有效投票权重、正确的抗量子原语、安全保管的终端秘密，以及共识协议原有安全假设。抗量子算法不会自动解决恶意法定人数、已控制解锁钱包的恶意软件、审查交易或合约业务逻辑漏洞。

必须保持：

- **I1——抗量子证明必要性：**严格模式保护的操作，不能由传统签名单独授权。
- **I2——完整绑定：**证明绑定实际语义消息、算法套件、角色、链与激活域。
- **I3——重放身份稳定：**随机化签名字节变化，不能为同一未签名意图制造第二个可执行身份。
- **I4——权限闭包：**弱父权限、委托、动作关联、恢复或代码升级，均不能单方面移除抗量子保护。
- **I5——共识连续性：**保留权重、门槛、强弱票语义、active/pending 检查与持久化投票锁。
- **I6——工作有界：**昂贵验签前即限制长度、数量、解压、内存与密码计算工作。
- **I7——历史表述真实：**迁移前历史以采用的检查点锚定，不能追溯宣称其原始签名已抗量子。
- **I8——不静默降级：**不支持的客户端明确失败；超时或应急状态不启用传统签名单独放行。

## 5. 拟议密码套件

以下是 P0／P1 应审核冻结的设计建议，不是已激活的协议编号。

| 套件 | 拟议用途 | 必需性质 |
|---|---|---|
| `PQ-HYBRID-V1` | 账户、出块主体迁移 | K1 AND ML-DSA-65，绑定同一登记的混合主体与同一消息 |
| `PQ-STRICT-V1` | 严格账户／出块授权 | 必须具有 ML-DSA-65 证明，传统证明不能替代 |
| `PQ-QC-V1` | finalizer 投票与证书 | 每个验证者独立 ML-DSA-65；临时 BLS 兼容须为 AND 且签署者集合一致 |
| `PQ-COMMIT-V1` | 新安全承诺 | 对规范完整输入进行域隔离 SHA-512 |
| `PQ-RECOVERY-V1` | 可选离线恢复／发布多样性 | 单独审核 SLH-DSA 策略与参数；不能在主方案失败后接受更弱回退 |
| `PQ-CHANNEL-V1` | 经认证的保密控制通道 | 使用 ML-KEM 的已审核混合密钥建立方案，加独立 PQ 认证 |

主签名算法建议 ML-DSA-65。ML-DSA-44 用于体积／成本对照；SLH-DSA 用于不同数学基础的备选研究。ML-KEM 用于建立共享秘密，不用于交易签名。Falcon／FN-DSA 与研究性 PQ 聚合不作为首版正确性的前提。NIST 当前项目页仍将 Falcon 列为标准化进行中。实现前冻结标准及勘误版本。[S1–S4]

建立窄接口密码适配层，固定算法和错误语义。评估已经 vendored 的 BoringSSL `MLDSA65_*`、适合钱包的 Java 实现，以及用于差分核对的独立实现。头文件存在不代表部署二进制支持，更不代表密码模块取得认证。`liboqs` 适合研究，其官方支持说明对生产依赖有限制。[S7–S8]

签名可采用经批准的随机化生成方式；同一输入的验证结果必须确定。不能要求不同实现生成完全相同的随机签名字节。精确输出比较使用官方测试模式／向量；独立生成的有效签名进行交叉验证。

## 6. 哈希、标识与完整签名转录

SHA-256 不会像椭圆曲线签名那样被同一种方法攻破。但原像与碰撞是不同安全性质，不能把量子碰撞分析简化成“任何场景的 256 位都变成 128 位”。本计划建议新安全承诺采用 SHA-512，并审核每个实际用途及成本，不声称已证明整个系统具有某个统一安全位数。[S5–S6]

实施要求：

1. 保持历史 chain ID、区块／交易 ID 和旧表索引可读。新增有类型的 `pq_block_commitment`、`pq_transaction_id`、`pq_policy_digest`、`pq_code_digest`、`pq_abi_digest`、`pq_review_digest`、`pq_checkpoint_digest`。新摘要为 64 字节，不能塞入旧 32 字节类型。
2. 每个新哈希以明确的域、套件／版本、角色和带长度的规范输入开头。Merkle 叶子、内部节点、空树和集合长度分别编码，绑定顺序、索引与证明长度。
3. 抗量子交易身份覆盖完整未签名语义交易、action／CFA 描述，以及所有非证明用途的语义 CFD。授权签名字节排除在外，避免循环签名和随机化签名改变重放身份。
4. 明确 owner 与原生资源付款方证明的层次：owner 绑定未签名操作；资源付款方同时绑定所提交 owner 证明及全部收费数据。任何签名都不能包含在自身签名输入中。
5. 新交易的原生去重表 `transaction_object` 使用新权威身份。旧别名只作辅助；别名碰撞不能选择或授权错误交易，旧 ID 查询存在歧义时明确拒绝。
6. 新区块安全承诺覆盖原始／规范交易与回执内容、完整新策略和前一区块 PQ 承诺。不能仅对旧 SHA-256 交易 ID、Merkle 根或代码哈希重新哈希。
7. 最终性验证树、可逆区块承诺与证明验证采用新配置。注意 `action_mroot` 在 legacy 和 Savanna 含义不同，不能统一当作动作回执树根。
8. TAPOS 兼容字段继续可读，新授权额外绑定不可逆 PQ 检查点及链域，旧短前缀不能独自承担抗量子重放／域隔离防御。
9. RIPEMD 派生的 4 字节密钥校验和只用于输入纠错。新地址／公钥编码须定义版本、套件、网络上下文、有界解析与校验和；身份比较使用完整规范公钥或强承诺。

优先签名接口为：对包含 SHA-512 承诺和上下文的规范应用封装使用 pure ML-DSA。若 HSM／provider 选择 HashML-DSA，须分配不同套件并实现其规定的预哈希标识／上下文规则。向 pure ML-DSA 输入摘要，不能标成 HashML-DSA。[S1]

## 7. 原生验签、编码与资源记账

新增显式公钥验签，不在旧 recovery visitor 中虚构恢复公钥操作。保留现有变体标签与旧序列化字节。新证明包含套件、主体／key epoch、规范公钥材料或已认证的不可变公钥引用，以及精确长度的签名组件。

首版原生交易携带显式公钥，便于安全地异步预验证。通过权限解析公钥引用仅作为后续优化，前提是定义安全的主线程不可变捕获方式。工作线程不得读取可变 chainbase 来解析公钥。

向授权层返回“已验证主体”。混合主体只有两种签名都对已登记密钥对验证通过才有效，而且只计一次权重。不能把两个独立验证后的 K1、PQ 公钥加入普通权重集合，就假定得到了 AND 策略。

新增可供 context-free 调用的纯字节 PQ 验签 host 函数及匹配 CDT API。它应拒绝未知套件、错误固定长度、尾随数据和非规范编码，解析前限制分配，具有确定返回语义与执行预算检查，验证过程无 I/O、无宿主随机数。策略查表和强制套件检查仍在有状态授权路径执行。

协议激活共同管理密钥类型、authority 存储、intrinsic、ABI 编解码、快照与特性验证。复盘 `num_supported_key_types`、签名 CPU 计费、变长内存、队列估算、压缩交易与解压上限。本地主观准入可更严格，但不能让不同节点以不同规则决定共识有效性。

验签缓存至少绑定套件、完整消息／PQ 承诺、完整密钥身份、链／激活域、角色及相关 key／policy epoch。重组与激活切换后，过期策略结果不能授予权限。不能只按某个 SHA-256 交易 ID 缓存“已通过”。

## 8. 命名账户权限闭包

把 `owner`、`active`、所有自定义动作关联权限、恢复权限与账户委托图作为完整闭包迁移。仍能替换 PQ active 的旧 owner 会使严格保护失效。

增加协议强制的账户保护状态和单调 key epoch。选择加入混合模式后，该受保护账户所有控制变更都必须满足其保护策略。严格激活后，外部状态变更授权必须满足强制 PQ 的权限闭包，纯等待权重、传统委托或较低权限不能独自达到强制 PQ 门槛。

保留合法合约代码委托：系统 inline action 不必每次取得新的人工签名，但权限来源须经过审核代码和已认证 PQ 根调用，或明确规定的共识生成系统动作。拒绝伪造 `eosio.code`、任意特权转发及仅传统签名管理调用。区分隐式 `onblock` 和外部签名交易。

已封存系统账户特殊处理：原生治理故意让 owner／custom 权限不可满足，不能重新开放或注入创世密钥。需要的 PQ 策略／迁移数据通过单独审核的原生转换加入，保留封存模型。

闭包清单包括：代币发行、可改变上限的代码、开户、BP 注册／换钥、投票、保证金退出／结算管理、维护、中继配置、升级与否决。签名规则改变不能顺带改变这些操作的经济或资格语义。

## 9. `eosio.key` v3、收款与费用迁移

采用新的 v3 proof／action／schema，或只追加的扩展表；每个钱包明确必需套件与 key epoch。旧 v2 行和回执按历史规则保留。

当前 `prove()` 是 context-free，不能读取钱包策略。v3 proof 需验证规范交易数据内完整描述符，有状态 `verify_envelope()` 再将描述符及套件与钱包已存策略匹配。钱包要求 v3 后，拒绝旧版 `ksend`、`withdraw`、`selfout`、`cancel`、`selfcancel` 及任何策略变更绕过。

保留不依赖共享顺序 nonce 分配器的设计。不同设备继续独立签发不同完整交易，保留撤销 epoch、精确原生／PQ 交易身份、到期与原子去重。同一未签名意图重新签名不能产生第二次付款。request ID 是被绑定的关联值，不能替代完整原生去重。

冻结 v3 前比较：

| 方案 | 好处 | 代价／要求 |
|---|---|---|
| 授权表保存完整规范 PQ 公钥 | 稳定解析，不必每笔重复传公钥 | 更高赞助 RAM；迁移存储须先有预算 |
| 表中保存强公钥承诺，每份证明附公钥 | 持久行较小 | 每笔额外携带 1,952 字节 ML-DSA-65 公钥；必须验证完整公钥与承诺 |

本地生成 PQ 钱包仍免费，不需要命名账户。首次真实收款仍要求有资金支持的链上 RAM 准入，并由付款方承担费用。旧“新 key＋余额 1,536 字节”估计不能直接容纳 1,952 字节完整 PQ 公钥及其他行数据。

收款协议也需要具体改造：当前 memo／key 解析不能把千字节公钥当成短 K1 字符串。设计经审核的存款封装，将完整描述符放在 action data、转账 memo 使用短的版本化引用，并原子验证付款方授权、准入及本金记账。保留收款人无需签名的语义。验证通知歧义、inline 调用、描述符不符和回滚，不能信任一个未被核实的前置注册动作。

重新资格验证分配界限、RAM 曲线报价、执行工作和签名费用上限。除非另行批准经济调整，保留 0.0100 AIC 保底、已批准中继费率范围、完整本金到账、AIC／USD 白名单、赞助预算、USD 命名收款人预开余额及收入领取免应用费。密码迁移不授权静默提费或自动购买 RAM。

合约、SDK、中继、钱包、历史投影的系统／代币／代码 pin 只能在匹配已审核版本时共同更新。系统升级可能使旧客户端按设计拒绝服务，须在激活前规划兼容窗口和用户可用性。

## 10. 出块密钥与签名器保管

账户管理、区块提议、finalizer 投票、P2P 身份、中继资源签名和发行签名使用不同 PQ 角色。独立随机生成各自密钥，不从未来可能被恢复的旧椭圆曲线私钥派生 PQ 私钥。

版本化 proposer authority 及共享表示。区块签名绑定新承诺、链／激活域、proposer 身份、schedule version、key epoch 与套件。附加签名扩展和带权多密钥规则一致校验。旧块继续使用原规则回放；新的严格时期区块不能只凭旧 producer signature 通过。

扩展 signature-provider／keosd 接口，避免隐含的“只签 32 字节 K1 摘要”契约。远程签名请求须经过认证且限定协议域，避免成为跨协议签名接口。逐 provider 实测硬件能力；软件签名加密存储不能描述为硬件内部签名。

保留 producer watermark、防双签与 finalizer 持久锁。切换到 PQ 密钥时继承验证者相关安全历史。生成新密钥不构成以空 safety 记录启动在线验证者的理由。

## 11. 抗量子最终确认与证书设计

首版保留共识算法，QC 使用逐个可验证的 ML-DSA 签名和按策略索引的投票 bitset。聚合／门限签名单独研究，不能把未经资格验证的结构作为正确性前提。

拟议投票转录包含：链域、激活检查点、套件／版本、稳定验证者身份、签名 key epoch、区块高度、PQ 区块／最终性承诺、active 策略 generation／digest、存在时的 pending generation／digest，以及强弱票角色。须精确定义一份转录是否同时认证两套策略；对双重成员建议使用同时认证方式，并证明符合原投票语义。

QC 必须检查：

1. 选择被证明区块对应的历史 active／pending 策略，不能取当前 head 成员代替。
2. bitset 长度精确、策略顺序规范，每个声明成员有一份认证证明，拒绝重复索引、替换公钥、多余签名与强弱票重叠。
3. 混合模式的 BLS 与 PQ 部分认证同一组选中成员及投票角色，不以两组互不对应的法定人数拼成混合证明。
4. 每个成员权重只累计一次，与各策略记录的 threshold 比较。常规等权最终性为 `floor(2N/3)+1`，当前为 21 中 15；治理否决是另一公式 `ceil(2N/3)`。
5. 存在 pending 时，它的证明与门槛也必须满足；同时存在于两套策略的验证者投票一致。
6. 新策略／密钥承诺进入被签名的最终性依赖链，PQ 签名不能只绑定旧 BLS 策略哈希。
7. 保留弱票行为、锁定、活性条件和不可逆交接。缺失 PQ 证明不能被当成合法弱票。
8. 发布投票前验证并持久化 safety 变化，故障测试原子替换、目录同步与版本检查，保留 inactive key safety 与 key epoch 历史。

`max_finalizers=65,536` 是旧结构上限，不是已经验证的 PQ 运行规模。在该规模下，单策略全量 ML-DSA-65 证书仅签名就需 216,858,624 字节。应确定逐特性的客观证明／数量／字节预算，并验证实际运行规模。新的共识限制须明确审核，不能静默改变当前候选容量或未来 active BP 增长政策。

## 12. 治理与协议升级引导

复盘完整控制路径：`developer@upgrade` 及父权限、BP 否决授权、`refreshgov`、`devpropose`、`devcancel`、`devexec`、受保护代码／ABI capability 检查、特性预激活与节点制品分发。

现有治理绑定旧新代码、ABI、审核文档的 SHA-256，并通过一次性能力执行合约 `setcode/setabi`。增加单独版本的强载荷承诺，保留精确字节检查与原子回滚。保留已有提案截止时间、冻结选民、永久禁令排除、重复否决拒绝和空有效选民阻断。生产公示仍七天；已选择 TEST 构建仍 1,800 秒；旧公示规则按历史事实保留。

存在引导依赖：旧二进制不理解 PQ 原生权限或新 QC。建议原链原地迁移路线：

1. 先资格验证预备节点版本，PQ 特性默认未激活，包含精确兼容行为及明确的迁移／激活规则；只在另行授权的部署中安装。
2. 在传统授权仍可信时，以合法现有授权加 PQ 持有证明登记开发者与 BP 控制身份。若传统签名已可伪造，登记窗口本身不能解决身份真实性。
3. 封存合约需要新动作时，资格验证精确 system／key 候选并通过现有公示治理。不得恢复 `eosio` owner、旧 multisig 或直接 `setcode` 绕过。
4. 设计经原生审核的激活记录，绑定完整发行清单、特性集合、检查点、必需注册表、资源配置及不可逆激活条件。其授权／否决程序须明确设计审计；本计划命名它不代表现有链已实现。
5. 强制新证明前，active／pending 策略和验证节点均须 PQ-ready，不能只凭运营者声明把不支持的二进制计为就绪。

`devexec` 不会替换节点程序，Git 上传也不批准协议激活。任何原生迁移能力须范围明确、阶段受限、防重放、可审计，不能成为应急任意改状态接口。

## 13. 迁移状态机与未迁移资产

使用链上不可逆状态及特性依赖，不使用本地时钟或浏览器设置决定规则。

| 状态 | 允许行为 | 转换必需条件 |
|---|---|---|
| `LEGACY` | 当前规则，不宣称 PQ | 预备制品与精确来源完成资格验证 |
| `REGISTRY_READY` | 可登记 PQ 密钥及持有证明 | 开发者／BP 角色已登记，客户端可解码新版本 |
| `HYBRID_OPT_IN` | 受保护账户要求 AND，其余明确标为 legacy | 受保护账户没有 owner／委托绕过或降级 |
| `CONSENSUS_HYBRID` | 出块与 QC 要求相匹配的传统和 PQ 证明 | 两套有效策略就绪，safety 已迁移，验证节点全部通过资格检查 |
| `STRICT_SCHEDULED` | 发布精确检查点／激活条件和策略快照 | 治理、合约、客户端、预算和恢复计划达到全部门槛 |
| `PQ_STRICT` | 范围内所有外部控制及共识操作必须提供 PQ | 不可逆激活，不存在仅传统签名的写路径 |
| `PQ_AGILE` | 后续经审核 PQ 套件可替换／增强首版 | 转换认证不变弱，不提供泛化 fallback |

激活高度／时间、登记时长和具体部署日期均未选择。提案必须规定 pending 交易、中继队列、跨边界到期、可逆块与就绪清点后发生的权限变化如何处理。

链无法为未迁移账户生成其所有者专属的新 PQ 秘密。建议严格模式保留余额与所有权记录，但在无法满足预先独立登记的 PQ 恢复策略时，拒绝旧签名单独支出／改控制。这可能冻结无人管理的资产，严格激活前须明确批准该经济／用户政策。不得没收、自动归集、自动登记替代密钥，或保留传统签名单独恢复后门。传统签名已能被伪造后，仅持有旧私钥不能成为可信恢复证明。

同时清点合约自带授权。若合约自行验 K1 便可支出，即使账户原生权限已 PQ，相关资产仍可能暴露。保护范围内的已部署合约须审核并迁移，未支持应用明确标注。签名层升级无法保证任意新合约逻辑绝对安全。

## 14. 历史检查点、回放与轻客户端

建立独立采用的 PQ 检查点，包含旧 chain ID／高度／block ID、新完整检查点承诺、确定性状态承诺、active／pending 的 proposer 与 finalizer 策略、key epoch、特性集合、代码／ABI 清单、归档覆盖和新信任根。按照审核后的迁移规则取得必须含 PQ 的授权，并通过独立认证渠道分发精确检查点。

原生认证状态承诺是新增工作，不能假定现有 node snapshot 已经是规范状态证明树。明确账户／权限／表／代码／系统状态的顺序、资源状态、pending 提案、策略和排除项。信任其状态验证前，须将确定性快照导出与完整回放交叉核对。

按区块范围维护不同解码和有效性规则。以旧签名回放旧块是历史验证，不允许新的 strict 时期交易使用旧规则。即使分叉上的所有传统签名都看似有效，新节点也必须拒绝伪造的检查点后历史。

PQ 检查点在采用信任假设下认证当时接受的状态／归档，不能证明迁移前每份传统签名本来就抗量子，不能补出缺失原始历史，也不能修复登记前已丧失的真实性。已退役高配链的原始数据库按既有要求未保留，不能声称可由证据包恢复。

新增区块／最终性／回执证明格式，轻客户端从固定检查点验证策略交接。RPC 的 `get_info`、索引“不可逆”标签或代码哈希响应本身不是密码证明。不能验证新链的浏览器须显示受限信任／不支持状态，不能宣称独立 PQ 验证。

## 15. P2P、TLS、RPC、中继与管理通道

共识验证与传输保密是不同工作。伪造节点身份不能让无效区块／QC 被接受。引入认证连接后仍保留公共／匿名节点的资源限制。

用完整转录替代仅签时间的认证：绑定双方新鲜挑战、双方端点、链／激活域、支持版本、选中套件、key epoch 和临时密钥协商材料。认证套件协商，阻止剥离 PQ 支持。明确重放窗口、撤销、限速与有界消息帧。

保密通道评估标准化、审核过的 ML-KEM 与传统组件混合密钥建立。不能自行发明 KEM combiner，也不能把 ML-KEM 当身份认证。既防主动伪造，也考虑先录制后解密。P1／P7 冻结实际传输规范及实现版本；本计划不假定所有浏览器／TLS 栈均具同样 PQ 能力。[S3–S4]

RPC／中继就绪还应包含 PQ 认证的应用清单和绑定客户端挑战、已验证链检查点的证明。HTTPS 采用 PQ 密钥交换但服务器认证链仍仅有传统签名，不能自动视为可抵抗主动量子攻击的完整 PQ 认证。

当前项目仍只保留创世 HTTP 中继。未来 PQ 中继须共同迁移资源权限、父授权、精确包日志、费用／profile pin、请求体限制与状态 ID。本轮文档不需要增加 HTTP 服务。

审核 SSH／CI／CD／云凭据、备份加密、远程签名器、DNS／证书依赖和部署清单。若传统凭据仍允许攻击者替换验证程序或钱包，即使链协议通过 strict 测试，也须将其列为端到端安全声明的阻断项。

## 16. 钱包、备份与软件分发

检查的钱包使用 K1 编码，最低 API 26、target SDK 36。新密钥记录需要套件、key epoch、公开描述符、加密种子／私钥格式、绑定状态和核实的链上策略。保留多个独立本地钱包及公钥／命名账户界面。

对相同规范消息、公钥和上下文执行 Java／native 互操作验证。Android 当前文档的 ML-DSA 标识从 API 37 开始，不代表现有手机硬件支持。在实际资格范围内提供软件签名与加密保管，并把签名执行位置和包裹 AES 密钥的硬件／软件保护分别显示。[S9]

版本化 vault 和备份。独立生成的 PQ 秘密须有真实恢复／导出方案，不能把任意 PQ 私钥塞进旧 32 字节 WIF。精简种子备份只有在算法／派生版本固定、熵足够、跨实现恢复通过且用户说明清楚时才能采用；不能从 K1 秘密派生恢复种子。

保留 AES-256-GCM、唯一 nonce、认证元数据、PIN 加固、后台锁定、`FLAG_SECURE`、禁止系统／云备份及加密 pending 包。短 PIN 不会变成高熵抗量子密钥。保留失败退避，诚实显示设备级别。托管语言副本难以保证完全擦除，仍是终端边界。

`TxStore` 保存套件、权威 PQ ID、旧别名、精确签名包、到期、引用检查点和未决状态。不能因随机签名字节不同或中继超时而重造交易；跨激活重试必须有明确核对规则。

发布 PQ 签名发行清单，覆盖 APK／节点／工具链／依赖摘要、版本与更新限制，并预先建立信任根。Git／PGP／APK 旧签名可保留用于平台兼容。应用层清单不能使标准 Android 安装器或 OS verified-boot 自动支持 PQ；端到端声明前须说明这一外部边界，并验证独立更新验证器／受管理分发路径。

## 17. 历史、API、浏览器与外部接入方

共同版本化原生 RPC、SHiP ABI／消息、finality 导出、索引 schema、回执 API 和 SDK 类型。不能原地改变某个 64 字符十六进制字段的含义。明确返回 `legacy_id`、权威 PQ 标识、套件、key／policy epoch、区块范围与证明／覆盖信息。

历史服务保存并提供规范原生记录。新字段进入独立版本投影，不混 chain ID，不改写旧资产事件。保留精确整数、费用归属及所有现有历史。安全覆盖须核对实际规范记录，不能用索引高度替代。

浏览器标明 legacy／hybrid／strict 时期，区分当前策略与执行时策略，历史未知不能标为已 PQ 保护。公钥查询、QR／地址解析、表分页、代码 pin、导出限制和双语错误均需支持新 schema。只读浏览器／历史服务不接收私钥。

外部 SDK、交易平台、桥与轻客户端需支持新证明及检查点信任边界。仍只信任旧 BLS 证书的桥属于传统安全依赖。不支持的新旧消费者不能静默以旧确认规则回退。

测量实际封装、策略差分、proposer 证明、CFD／原生 NET 记账、磁盘／索引放大和网络扇出。当前记录的区块 NET 为 1 MiB、交易 CPU 上限为 150,000 微秒；这是现有配置，不是提高它们的授权。明确 QC 字节实际从哪里记账，不能用资源上限除以签名大小就声称获得 TPS。

保留主机记录的实际硬件为共享 Intel Cascadelake VM，4 vCPU、2 个来宾可见核心、8,125,768 KiB 内存，不能确认物理核心独占。S10 的外部 Intel 测试使用不同硬件，不能作为此主机、Android Java 或合约 WASM 的资格证明。

估算模型：

```text
单节点 CPU = 交易数 × 每笔被验证证明数 × 实测验签成本
           + 投票/QC 验证 + 哈希/序列化 + 执行 + 持久化
同机总 CPU = 各实际节点进程工作之和 + 历史/中继/普通业务
网络/磁盘成本 = 实际编码字节 × 实际扇出/保留副本数
```

不能假定每条路径都固定验 26 遍，但同机节点常会重复大量验证，应剖析实际路径而非假定共享结果。覆盖无效证明、签名拒绝采样尾延迟、p50／p95／p99、排队、RSS 峰值、CPU 周期、墙钟和最终性延迟。优化原生 C 的速度不能代替 Java 或 WASM 成本。

未来测量仅在远端隔离目录／端口运行，明确 CPU／内存／时间边界、低优先级和独立临时密钥。目前未授权新服务器或在线 TPS。若保留的低配主机没有安全余量，暂停该资格阶段并报告资源依赖，不能暂停 BP 或调整上限掩盖过载。历史 35 BP 容量失败不被本计划重新认定为通过。

## 21. 后续部署顺序与失败处置

以下供未来获授权部署评审，不是自动执行控制器。

1. 无秘密导出地确认精确运行／源码映射，以及服务／PID、策略、密钥角色、供应、保证金、禁令和历史基线。
2. 冻结套件、编码、证明预算、支持的资源配置、迁移窗口和未迁移资产政策。
3. 公布精确候选源码、构建／工具链／依赖清单、PQ 发行证明、测试证据及独立审查问题。
4. 验证所有节点／客户端／历史读取方在特性未开启时能回放旧数据并解码预备格式。
5. 采用另行审核的运维升级，保持 quorum 和 safety 文件。当前文档“保留 PID”的约束不意味着未来替换二进制能不更换进程。
6. 为全部必需 BP／控制角色登记独立 PQ 密钥及持有证明，核实父权限／委托闭包和 pending 策略。
7. 精确合约候选完成适用原生公示／否决程序。已有 pending 冲突只通过另行授权动作处理，本轮不改提案 #3。
8. 有状态核实就绪，验证者之间比较确定性检查点／状态承诺。
9. 不可逆前提满足后才进入 opt-in／hybrid，报告实际覆盖，剩余 legacy 账户不标成已保护。
10. 验证混合出块／QC、真实不可逆交接、key epoch 继承和客户端验证，并完成获批准的观察期。
11. 经审核治理取得另行批准的严格激活记录，在实际切换时重新核实权限／策略，不能只用早期就绪快照。
12. 按承诺的链条件激活，严格区间拒绝传统签名单独写入／出块／QC，同时保留历史解码。
13. 核对 pending 包、余额、储备、提案、投票、禁令和历史；有界清理前保留失败及原始证据。
14. 发布最终源码／制品摘要、精确激活块／检查点、实际硬件／验证范围、外部假设和验证说明。

强制激活前可按既定治理延期，不伪造就绪。不可逆强制后，恢复应保持 PQ 必需授权和已最终确认历史，以审核后的前向修复解决。回退旧二进制、降低法定人数、删除 safety 或使用仅传统应急密钥，均不是通用安全恢复机制。提前制定 PQ 保护的恢复策略；若无法安全恢复 quorum／密钥保管，应报告停顿，不发明绕过。
