## 1. 一句话说明

**票数决定谁进入前 210 名候选名单；候选按顺序轮流进入最多 21 人的出块班组；正常每次只换 1 人，故障节点优先替换；节点收入按实际有效出块数量分配。链可以先用 1 台启动，再逐步扩容。**

### 1.1 已确认的业务规则

| 项目 | 最终方向 |
|---|---|
| 入围资格 | 按票数取前 210 名合格候选；不满 210 名时按实际数量运行 |
| 同时出块人数 | 最多 21 人，不是 210 人同时出块 |
| 轮换方式 | 顺序轮换，取消随机抽选；不是一次更换整组 21 人 |
| 正常换人 | 每次退出 1 人、补入 1 人；完成本次切换和观察后才开始下一次 |
| 初始启动 | 允许 1 台服务器启动；不要求先上线 21 台或 210 台 |
| 后续上线 | 候选可以同时注册、启动和同步；只有正式出块名单按安全流程逐人扩容 |
| 候选故障 | 不能正常参与的候选跳过，继续检查下一人 |
| 现任故障 | 优先处理故障席位，其他正常成员保留；替换仍遵守共识生效条件 |
| 节点奖励 | 只按有效出块工作量分配节点奖励，取消按票数直接分配的节点奖励 |
| 投票用途 | 决定候选入围资格，不直接决定每个区块能拿到多少节点奖励 |
| 节点职责 | 出块、验证、同步和最终确认；不发起系统治理提案，不作升级批准或参数管理。按 2026-10-04 新需求，仅保留开发者升级公示期内的 2/3 否决权，详见第 10.3 节 |

“踢掉故障节点”按暂时跳过、移出当前出块名单及进入冷却处理，不等于永久封禁、删除票数、没收本金或清除已赚奖励。永久惩罚不在本次范围内。

### 1.2 必须保留的边界

- 本文件确定的是奖励分配依据，不擅自确定是否取消增发、发行比例或手续费分成；奖励资金来源仍需单独定稿。
- 备用节点不参与日常 21 人的全部共识工作，但仍需要同步、预连接和健康检查，不能宣称 210 个候选完全没有额外开销。
- “换下一个”不是绕开协议直接修改当前名单。正式名单变更必须经过合法的 proposer/finalizer policy 切换。
- 提前检查能够降低故障概率，不能保证加入后永不掉线、永不漏块或性能完全不变。

## 2. 顺序轮换怎么运行

### 2.1 候选排名与轮岗顺序分开

拟定实现规则如下，目的是避免每次选人又从票数第一名开始，导致低排名但已入围的候选长期轮不到：

1. 先校验报名、有效出块公钥、有效 BLS finalizer 公钥等资格，再按票数降序取前 `min(210, 合格候选数)`；普通候选要求正票数，创世启动账号例外见第 3 节。
2. 票数相同时按账号数值 `name.value` 升序，保证所有节点得到相同结果。票数口径沿用原计划的一 Token 一票、整数记账。
3. 初始候选轮岗队列按上述排名建立。已有候选只要仍然入围，就保留相对顺序和已走到的位置；票数小幅变化不把游标重置到第一名。
4. 新入围候选按确定性顺序加入队尾；已出围者不再获得新的入场机会。取消注册再注册不能插队。
5. 每次寻找补入者，从上次位置继续向后扫描，跳过现任、冷却中及预检失败者，到队尾后回到队首。每轮最多扫描本轮快照一次，不能无限循环。
6. 排名变更在下一次选举快照中处理，不改变正在执行的单次换人任务。若目标在真正提交前注销、撤销必要密钥或失去资格，则终止该目标并按规则继续扫描，不能提交失效目标。

前 210 是候选资格边界，不是“按在线状态临时重排到第 211 名”。入围者离线只影响本次可用性；不能为了补满 21 人就越过本轮前 210 名范围。若有注册失效等资格变化，应先按统一规则更新下一份候选快照。

### 2.2 谁先退出

正常轮换拟采用“先入场，先退出”：维护现任成员的入场顺序，最早入场者轮到退出，新成员加入现任队尾。创世多个成员的初始顺序也要写入确定性配置。

该顺序是业务轮岗顺序，不是区块链底层对账号、公钥进行排序后的出块顺序。两者分别保存，不能拿排序后的第一个账号当成每次固定的退出对象。

假设 210 个候选资格稳定、全部在线，编号表示首次建立队列时的位置：

| 阶段 | 当前出块成员 | 下一次正常换人 |
|---|---|---|
| 初始达到 21 人 | 1～21 | 1 退出，22 加入 |
| 第一次换人完成 | 2～22 | 2 退出，23 加入 |
| 第二次换人完成 | 3～23 | 3 退出，24 加入 |
| 完成 21 次正常换人 | 22～42 | 22 退出，43 加入 |
| 队列走到末尾 | 190～210 | 190 退出，1 重新加入 |

每行都以“前一次名单已生效并完成观察”为前提。故障、冷却、排名进出及共识等待会改变实际时间，因此不承诺固定多少分钟让 210 人全部轮完。

### 2.3 正常换人、故障替换与扩容的优先级

拟按以下优先级执行，且同一时间只允许一个名单变更任务：

1. 优先替换已确认故障、失去必要资格或已经出围的现任成员；多名异常成员按确定性顺序逐个处理，不整组换人。
2. 现任不足 21 人且有合格备用者时，从 `k` 扩容到 `k+1`，不为扩容先踢掉健康成员。
3. 达到 21 人后，按现任入场先后顺序进行正常的一出一进。
4. 没有可用备用者时，保留现有安全可运行名单，不移除健康成员、不提交空名单，不因候选暂时不足强制大幅缩减委员会。

对于已出围但仍在当前生效名单中的节点，其新的入场资格已经失效，但退出必须等待安全交接；交接前按实际有效出块计酬。不能要求票数一变化就瞬时改变共识名单。

正常选举机会拟沿用原计划 `252 slot` 的节奏；`500ms/slot` 下为 126 秒。这只是尝试开始下一次轮换的机会间隔，不是强制完成时限。增长期和故障处理的检查间隔在上线参数中另行固定。

## 3. 从 1 台服务器启动

继续沿用原计划“新链从创世即原生 Savanna”的前提，而不是先启动旧 DPoS，再等投票达到旧激活门槛后切换。

- Genesis 允许 `1 <= k <= 21`，本次目标支持默认从 `k=1` 开始。
- 初始 proposer 与 finalizer 使用同一批账号，finalizer 等权；出块密钥与 BLS 密钥分别配置。
- 启动账号通过创世配置明确指定。不能为了开链伪造票数，也不能等待旧的 15% 激活投票条件才允许基本出块、轮换检测和扩容。
- 后续候选可以一次上线很多台，边同步边等待；正式委员会仍逐个扩容，直到 21 人。
- 当具备正常候选池后，启动账号是否继续留任遵守同样的资格与顺序规则，不能获得永久保留席位。
- 系统合约的“当前共识模式”与创世名单必须正确初始化，不能因没有历史 `last_proposed_finalizers` 表就误认成 legacy 模式。

最终确认票数门槛沿用等权规则：`quorum(k) = floor(2k/3) + 1`。

| 当前人数 k | 达成门槛所需票数 | 说明 |
|---|---|---|
| 1 | 1 | 能启动，但唯一节点停机后无法在链上自动补位 |
| 2 | 2 | 缺 1 个 finalizer 就不能达到门槛 |
| 3 | 3 | 同样不能容忍缺 1 票 |
| 4 | 3 | 可缺 1 票，仍需满足其他共识条件 |
| 21 | 15 | 正常稳定策略下可缺 6 票，不代表任意网络分区都能正常运行 |

扩容和换人阶段还要满足旧、新策略的交接条件，不能只用目标人数的门槛判断。若当前链已失去推进最终确认的能力，链上自动替换也可能无法完成；这是协议活性边界，不是“跳过下一个”可以解决的问题。

## 4. 没开机、掉线和不出块怎么处理

### 4.1 入场前失败：先跳过，不占正式席位

系统合约不能直接知道一台服务器的电源是否开启，也不能依赖每台验证节点各自的 ping、墙上时间或本地网络观察来决定名单。

拟在入场前检查：候选仍在快照内、密钥有效、近期同步状态、出块与 BLS 密钥的持有证明、必要的 P2P 连接及可验证的就绪证据。链外观测必须通过确定性、可验证的上链证明参与决策；仅有账号签名或心跳不能证明服务器真的能稳定出块。

- 若 22 号未通过检查：保留原来的 1～21 号，再检查 23 号；不先把 1 号踢掉留下空位。
- 失败者记录原因并进入冷却，扫描游标继续向后；本次不反复检查同一个失败者。
- 所有备用者都未通过：结束本次扫描，保持现有名单，下一次按规则重试。
- 就绪证据有有效期；拟提交时重新检查，不能无限使用旧心跳。

预检见证者资格、证明格式、需要几份证明、超时及冷却时长尚待定稿。见证者只提供规定格式的运行证据，不因此获得任意踢人、任命节点或审批升级的治理权；但其信任与作恶风险必须公开并测试。

### 4.2 入场后故障：确认异常，再替换同一席位

1. 根据**实际生效**的调度计算该节点应负责的出块窗口；现有节奏为每人连续 12 slot。
2. 以完整分配窗口及链上已确认记录判断漏块，不能因为别人还没有轮到、区块暂时分叉或单个网络观察就处罚。
3. 完整窗口零出块可作为初版故障判定的依据之一；连续多少个窗口、允许多大漏块比例及何时触发必须在上线前固定，本文不把“一次没出块”直接定为永久故障。
4. 同时检查最终确认进展与可验证的 BLS 活动。某个 QC 没包含某人的签名，不等于该节点一定没投票，不能据此直接踢人。
5. 确认故障后暂停正常换人，只为该故障席位继续顺序寻找替代者；其他 `k-1` 个正常成员保持不变。
6. 替换仍等待共识允许的生效边界。已正式加入的离线节点可能造成漏块，无法承诺立刻无损接管。

恢复上线的节点在冷却结束并重新通过检查后，可以继续排队；不能自动夺回原席位。已产生且符合结算条件的奖励继续保留。

### 4.3 必须实现的名单状态机

拟定流程：`空闲 → 固定快照与待换席位 → 顺序扫描/预检 → 提交目标名单 → 等待实际生效 → 观察 → 确认完成`。

- 分开记录“当前实际生效名单”“已提交目标名单”“已完成观察的名单”，不能提交成功就认为交接完成。
- proposer 与 finalizer 的目标账号集合相同；底层排序可以不同，但账号和密钥映射必须正确。
- 两类策略可能不是同一时刻生效。交接期间保留所需旧、新连接，记录策略版本；不得在第一个策略生效时就开启下一轮换人。
- 一份策略已提交后，不能因一次超时就随意叠加另一份目标。必须先查明实际 active/pending 状态，再执行协议允许的继续或恢复路径。
- 两份目标策略均已实际生效后，至少观察目标人数 `k × 12 slot`，且覆盖新人的完整出块窗口，并满足预定出块率、最终确认推进和健康条件；21 人时最低观察长度为 252 slot。
- 所有扫描、健康统计、奖励推进及历史清理都要分批、有界，不能让每个 `onblock` 执行无限工作或导致出块超时。

## 5. 奖励与有效出块数量挂钩

### 5.1 业务口径

- 取消节点的按票数奖励；票数高只影响入围，不提高单个有效区块的奖励权重。
- 有效出块是：由当时合法调度的节点产生、验证通过，并最终进入已最终确认主链的区块。
- 空块只要合法且最终确认，也计 1 个；不按交易笔数或交易金额加成，避免鼓励刷交易。
- 分叉后被丢弃的区块、重复记录以及没有真正产生的漏块不计酬。
- 备用期间没有有效出块，就没有该期间的出块奖励；节点不必通过自己买 REX、给自己投票才能领取已赚的出块奖励。
- 节点同时承担 finalizer 职责；本版不另外设置按 QC 签名数量分配的奖励，也不因某份 QC 没收录其签名就扣掉已有出块收入。

### 5.2 拟采用“按期封账、按数量分配”

为避免谁先领取谁改变分母，拟先封存结算周期，再计算每个节点的应得金额：

```text
B_e = 第 e 期实际已拨入、允许用于出块奖励的预算
n_i = 节点 i 在第 e 期的最终确认有效出块数量
N_e = 第 e 期所有节点的最终确认有效出块数量之和

节点 i 本期奖励 = floor(B_e × n_i / N_e)
```

同一期内出块数量相同，奖励相同；数量加倍则份额相应增加，不受票数、账号是否拆分或领取先后影响。不同期预算或总出块数量不同，单个区块的金额可以不同，本方案不是承诺固定每块金额。

结算实现要求：

1. 周期按协议固定的 slot 边界划分，时长待定；不能由领取人或节点临时指定。区块按其自身时间所属周期归属，不按被最终确认的时间重新归期。
2. 保存待确认出块记录与最后已计账区块游标；最终确认推进后，按确定的主链顺序计账，每个区块只计一次。
3. 本期终点已被最终确认覆盖且计账完整后才能封账；最终确认延迟时允许延迟结算，不发放不可回收的分叉奖励。
4. 预算只能来自明确批准且实际到账的资金，不得把尚未收取的手续费、全部账户余额或 REX 持有人资产直接当预算。
5. 使用整数金额、足够宽的乘法中间值；取整余数按固定规则结转。若 `N_e=0`，不做除法，预算结转；不允许某账户抢走剩余金额。
6. 先形成个人已赚余额，再由本人授权领取。退出当期名单、失去候选资格、暂时离线或注销报名，不清除已结算应得余额。
7. 统计表可以按保留窗口清理，但未结算记录和未领取债权必须保留或安全汇总，不能因历史清理丢失收益。

### 5.3 资金来源仍需单独确认

现有代码有通胀发行、per-block/per-vote 分桶和独立收费路径。取消 per-vote 分配，不自动意味着把原有全部发行收入或手续费都改给出块节点。

上线前必须明确：保留哪种发行安排、是否拨出某类手续费的固定份额、是否由预存资金供给，以及每期预算怎么确定。如果最终选择零增发，就必须有经确认的非增发资金来源；没有预算不能凭空承诺节点有收入。

本文件不更改 RAM、PowerUp、REX 租赁费用的资金去向，不擅自从 `eosio.rex` 分走持有人的收益。REX 收益与节点出块奖励是两本账。

## 6. 现在的代码需要改哪些地方

### 7.2 必须通过的场景

候选与顺序：

- 候选数为 0、1、20、21、22、209、210、211 时边界正确；无普通候选时不提交空策略，已启动链不因空候选池立即自停。
- 固定 210 名、全部健康且资格不变时，每名候选都能顺序获得机会，没有长期只选前 21 名或每轮重置游标的问题。
- 第 22 名预检失败则检查第 23 名，原第 1 名在有效目标交接前不被提前移除；全部备用者失败时维持名单。
- 当前成员掉线优先换该成员；故障替换后的新人排在现任入场队尾，不因旧席位位置而立即再次被正常轮出。
- 票数并列、排名进出、注销重注册、提交期间失效和多名故障都产生确定且可重放的结果。

启动与共识：

- 只配置 1 台即可启动、出块和形成最终确认；不需要凑齐其他 209 个账号，不依赖旧激活票数。
- 候选可以批量注册、同时同步，但 active 名单依次从 1 增到 21，后续始终最多 21 人。
- 交接期间准确区分 proposed/pending/active；只生效一份策略、入场后掉线、密钥变更和超时都不引发并发名单覆盖。
- 唯一节点停机、2/3 人阶段缺 1 票、21 人阶段缺 7 票等场景明确表现为无法满足相应门槛，不能通过降低安全门槛伪造“自动恢复”。
- 轮换前后 BP 均无直接系统升级/参数管理权限；自动选举无需 BP 多签提案。开发者升级另按第 10.3 节保留限期否决，不恢复 `eosio.prods` 的管理授权。

奖励与资金：

- 同期有效出块数相同则奖励相同，票数多少不直接改变奖励；备用但零出块者无出块奖励。
- 合法空块计数，漏块和废弃分叉不计数；重放、回滚、重复最终确认通知不重复记账。
- `onblock` 前块语义、周期边界和延迟最终确认的区块归期均正确，不发生错位一块。
- 领取顺序不影响应得金额；已经退出或注销的节点仍能领取已赚余额；无本人授权不能领取。
- 零区块周期、零预算、大数乘法、取整余数、长期未领取、历史清理均不丢账、不超额支付。
- 如果部署独立 `eosio.bpay`，其入账不再产生旧的按票 top-N 平分，也不对同一资金重复分配。

性能与运行：

- 对比相同硬件、负载与网络下的固定 21 人和“210 候选＋21 人轮换”，记录 TPS、CPU/NET、漏块率、最终确认延迟及 policy 切换耗时。
- 验证候选同步、预检、P2P 预连接和失败重试的额外成本，尤其在大量候选离线时仍有界。
