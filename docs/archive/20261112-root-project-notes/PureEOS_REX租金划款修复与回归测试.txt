一、本次范围
用户要求修复 REX 租金误从 eosio 系统账户划出的问题，并确认票数继续使用
代币最小单位的整数，不改回浮点数。此次没有修改投票规则、REX 定价公式、
收益分配、30 天租期、续租条件、候选扩容或黑名单条件。

二、原因与修复
租客 deposit 的真实代币由 eosio.rex 托管。首次租赁扣减个人 rexfund；
续租扣减对应租单的余额。原 add_loan_to_rex_pool 却使用 get_self()，
因此由 eosio 代付给 eosio.fees，而不是从存放租客资金的账户划款。

已将 reference-contracts/contracts/eosio.system/src/rex.cpp 中该调用改为：
  channel_to_system_fees(rex_account, payment)

首次租赁和续租共用该路径。资金按原逻辑转给 eosio.fees；部署当前费用
转发合约且 REX 可用时，再捐入 REX 收益池。没有费用转发合约时留在费用
账户。本次不直接修改收益池公式，也不绕过费用合约。

三、新增验证
PureEOS/unittests/pureeos_resource_split_tests.inc：
1. 部署费用转发合约，核对 CPU/NET 首租和续租实际 token::transfer 的方向和金额。
2. 将隔离测试链的 eosio 代币余额清零，再封存治理，租赁和续租仍须成功。
3. 未部署转发合约时，REX 托管余额恰好减少租金，费用账户恰好增加租金。
4. 使用最终轮岗配置的系统合约重复完整租赁流程。
每个场景均核对托管余额等于可出借资产、待分配收益、个人资金和租单余额之和；
检查余额不足回滚、续租不重复扣个人资金、重复执行不重复收费、到期仅退款一次。
31 天、62 天边界使用真实 WASM/控制器推进区块时间，不是现实等待 62 天。

旧 WASM 在新增 4 个场景全部失败：观察到 eosio 错误扣款、REX 托管余额与
负债不一致，以及系统余额为零时租赁失败。修复后 4/4 场景、1,239 条断言通过。
专项在 eos-vm 和 eos-vm-jit 上各连续重复 3 次，均通过。

五、本次续测发现的环境问题、修正与记录保留
1. socket 权限：此前四个联网目标在创建 socket 时被执行环境拒绝，尚未进入
   合约业务验证。现在已通过正式授权在允许本机监听的执行环境续跑，四个目标
   全部通过；没有关闭全局安全限制，也没有改防火墙或原手动链配置。
2. 磁盘保护：恢复联网后，两个单节点目标触发 nodeos 默认 90% 磁盘使用率
   保护。当时磁盘已用约 93%，但仍有约 10～11 GiB 可用；这是保护性退出。
   只对隔离测试脚本设置 8 GiB 绝对预留，与原四节点测试配置保持一致。
   仍保留磁盘不足时退出的保护，没有修改生产默认值或禁用保护。
   修改 tests/pureeos_single_choice_local_test.py::start_node，已有显式参数则
   保留；tests/pureeos_local_test_harness_test.py 新增两项参数回归自检。
3. 报告采集：CTest 非 verbose 的成功日志不会保留每次运行的 Report 路径。
   本轮调度脚本对重复四节点目标启用 verbose，最终校验恰好两份独立报告、
   两个不同链 ID、租金交易最终确认和进程退出，不能只凭一个 CTest 名称通过。
4. 生产代码及编译产物在续跑期间未变化；测试脚本的磁盘预留调整记录在
   regression-summary.json 的 artifact_revisions 中。受影响的支持组、两个
   单节点目标和两次四节点运行全部重新测试；未受影响组按哈希核对后复用。
   历史权限失败、磁盘保护失败及被新测试替代的旧结果保留在 previous_attempts
   和 *.attempt-* 日志中，没有删除或把原失败改写成成功。

六、未覆盖范围与仍需处理的逻辑风险
1. 未自动部署或重启 manual-test-chain；原有手动链、钱包和密钥未改动。
2. 既有链历史代付的金额没有自动追溯补账或划回；需要独立核对并确认处理办法。
3. 此轮测试不代表 OC/macOS、跨地域、真实断电或 21/841 个独立进程测试。
   不是无差别执行全部 1,577 个 CTest 注册项：部分上游端到端脚本包含
   全局进程探测、固定目录或端口，尚未逐项完成隔离验证，另有未构建的
   可选测试程序。本轮使用隔离目录与端口，不结束已有手动链来腾出环境。
   具体已执行项以命令和日志为准。
   委员会边界测试使用不带轮岗的基线配置；其中“不含轮岗/黑名单”的日志
   只描述该配置，最终轮岗规则另由 sequential_rotation 专项验证。
4. 本报告当时以下四项尚未解决（后续已修复，见第七节；保留当时结论）：
   a. 奖励计算 int64 中间乘法可能溢出，需要宽整数中间值及结果范围检查。
   b. 现任节点组合/交替漏块可能阻塞轮岗推进。
   c. 不满 21 人时，故障新人可能无限等待，阻塞后续接入。
   d. 治理候选名单扫描没有按已访问行数限制工作量。
   本轮通过不能证明这些问题已消失，也不能当作“全部逻辑问题已修复”。
5. 最小单位整数比 double 更适合精确计票；较宽的中间乘法和结果范围检查仍必需。
