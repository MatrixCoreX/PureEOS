用户决定暂时不实施本计划，暂不强制出块节点保存全部历史。

- 现有节点运行、轮岗、奖励、最终确认及历史存储配置保持不变，不新增历史存储准入或处罚条件。

## 1. 先把目标说清楚

目标是：**每个出块节点都承担保存完整历史账本的责任；不满足历史存储证明要求的节点，不能产生被新协议接受的区块，也不能靠这些无效区块获得奖励。**

这不是让当前 21 个节点去访问新人的服务器、投票决定新人有没有存账本。证明规则公开，任何验证节点执行相同的数学检查；没有现任成员单独批准、打分或举报处罚的入口。

必须说明一个边界：纯网络协议不能直接观察某块物理硬盘，更不能绝对证明数据就在“签名服务器的本地磁盘”上。远程磁盘、委托存储和同一运营者控制多台机器无法仅凭区块区分。可落地的严格目标是：

1. 官方出块程序必须维护完整可读档案，不能只靠状态快照运行。
2. 每个出块账号必须提供与完整历史范围绑定的存储证明，协议强制验证。
3. 若要防止很多账号只共用一份未编码历史，则还要引入账号绑定的副本证明及持续存储证明；只做随机读取几段旧区块不够。
4. 上述证明仍有密码学、计算成本、随机性及时间窗口假设；不能宣传为“100% 证明每一台物理机器每一秒都保存每一个字节”。

本计划按第 3 项的严格方向拆分工作，但不把未选型的密码学方案伪装成可直接上线的成品。第一阶段的普通历史抽查只是基础设施验证，不能作为最终需求完成的验收依据。

## 2. 用户能看到的运行方式

正常运行流程：

```text
节点取得完整历史并验证
        ↓
为历史分段建立索引和账号绑定的存储副本
        ↓
后台持续更新存储证明，补齐新增历史
        ↓
轮到自己出块时附带协议要求的证明或已验证证明的引用
        ↓
所有验证者按同一规则检查
        ├─ 合格：继续正常交易验证、最终确认和出块计酬
        └─ 不合格：拒绝该区块，不产生该块对应的奖励计数
```

对用户现有规则的衔接：

- 候选仍按票数入围，容量仍按四年分段线性增长；不改一票一投、不恢复代理投票。
- 正常仍最多 21 个在岗、顺序一次换一人；不改成存储量竞争出块，也不新增备用节点奖励。
- 不要求现任 21 个在岗节点做人工预检；新人可直接按原顺序进入名单，但其第一次有效出块也必须满足新证明规则。
- 证明失败导致发出的区块无效，整个本人窗口都没有有效产出时，才可能按现有零产出规则累计。
- 满 21 人、三个连续完整本人出块窗口零产出，且满足现有最终确认证据及暂停保护，才永久禁止账号再次轮岗；不足 21 人不因本机制新增永久拉黑。
- 不冻结资产、不清除此前合法出块形成的奖励权益；不因当前无法提交存储证明而额外禁止领取历史已累积奖励。
- 账号换签名密钥，不应免费重置存储责任或黑名单；不擅自给注销重注册提供逃避通道。

这里的“拒绝区块”不是立即完成链上换人。正式名单及 Savanna 新旧策略交接仍遵守现有协议。

## 3. 当前底层代码实际做了什么

### 3.1 历史保存只是本地配置，不是出块有效性条件

`PureEOS/plugins/chain_plugin/chain_plugin.cpp`：

- 约 263–280 行支持区块日志分段、保留数量及移入归档目录。
- 约 390 行支持 `block-log-retain-blocks`；正数裁剪，零关闭区块日志。
- 约 703–735 行选择完整、分段、裁剪或空日志实现。
- 约 791–825 行支持快照启动；没有快照的全重放要求日志从第 1 块开始。

因此，当前“能启动、能出块”不等于“持有从创世开始的全部历史”。禁用这几个参数只能约束官方程序，运营者改代码仍能绕过，必须另加共识验证。

`blocks-archive-dir` 当前只是退役日志的存放位置，说明明确指出 nodeos 不再访问其中的文件。不能把“文件还在 archive 目录”直接当作“P2P 可提供完整历史”。

### 3.2 区块 ID 不是整个区块文件的哈希

关联文件：

- `PureEOS/libraries/chain/block_header.cpp:19`：`calculate_id()` 对区块头计算摘要，并明确排除 `producer_signature`。
- `PureEOS/libraries/chain/include/eosio/chain/block.hpp`：交易收据和 `block_extensions` 在区块体中；当前扩展包含附加签名和 QC。
- `PureEOS/libraries/chain/transaction.cpp:163`：`packed_transaction::packed_digest()` 覆盖交易压缩标记、原始打包交易及签名/上下文数据摘要。
- `PureEOS/libraries/chain/controller.cpp` 的 `create_block_state_i()` 另行检查交易 Merkle 根和 QC。

直接对各节点的 `blocks.log` 文件做哈希比较不可行：文件头、偏移、分段布局不是账本内容；同一个区块 ID 也不能直接证明附加见证字节完全一致。新增证明必须有统一的账本编码和认证方式。

### 3.3 存储证明必须早于发确认票，不能只在执行合约时检查

`PureEOS/libraries/chain/controller.cpp`：

- `create_block_state_i()` 验证基本不变量、交易根、区块签名及 QC 后，会保存恢复记录、整合 QC，并调用 `consider_voting()`。
- `apply_block()` 约 3968 行也可能在交易执行之前调用 `consider_voting()`。
- 当前 Savanna 的提前投票有它的共识设计依据；新增历史证明必须专门接入其有效性边界，不能假定“执行完交易后才投票”。

实施要求：证明的格式、绑定关系和密码学校验必须在该区块有机会触发本节点确认投票之前完成。若父状态尚不具备验证证明所需的可信上下文，应延迟处理，而不是相信区块自己声明的历史根。

### 3.4 在 onblock 中 check 失败，不能替代底层拒块

`PureEOS/libraries/chain/controller.cpp:3501` 附近处理隐式 `onblock` 交易。普通合约执行异常可能只被记录为 `onblock ... is REJECTING`，并非全部作为区块无效异常抛出。

因此不能这样实现：只在 `eosio.system::onblock` 增加一个 `check(已保存历史)`，就声称协议已经禁止无历史节点出块。区块合法性必须由 native controller 的硬规则控制。

### 3.5 奖励和零产出窗口已经有可以衔接的入口

- `reference-contracts/contracts/eosio.system/src/producer_pay.cpp:22`：`onblock` 对传入的父区块生产者累计 `unpaid_blocks`。
- 同文件约 105 行：`claimrewards` 要求历史出块计数大于零；新增发行 100% 进入按出块分配的奖励池。
- `PureEOS/libraries/chain/controller.cpp:5028` 附近：`get_on_block_transaction()` 传入的是已执行父区块头，不是当前待生产区块。
- `reference-contracts/contracts/eosio.system/src/rotation_state.cpp`：`observe_windows()` 按完整本人窗口结算，最终确认覆盖后累计零产出；`advance_rotation()` 执行生产环境轮岗。
- `contracts/eosio.system/src/rotation.cpp` 是历史独立模型，不是当前 v2 轮岗生产入口，不能改错位置。
- `PureEOS/libraries/chain/controller.cpp:5990` 和 `rotation_context.hpp`：轮岗证据取自已执行父区块的共识状态，不取每台机器瞬时观察到的本地 LIB。

若无证明的块在底层已经被拒绝，它就不能作为正常父区块进入后续奖励和窗口观察。合约以核对、展示和回归测试为主，不需要重新发明一套罚款或奖励分配公式。

### 3.6 持久化与同步已有必须保护的基础

- `controller.cpp:5801` 的 `fetch_serialized_block_by_number()` 先读分叉数据库，再读区块日志；`net_plugin.cpp:1732` 附近的 `enqueue_sync_block()` 使用它发送历史。
- `libraries/chain/reversible_recovery.cpp/.hpp` 保存崩溃恢复所需区块；`controller.cpp:1698` 附近要求先确保持久区块日志落盘，再清理恢复记录。关闭区块日志时恢复记录会持续保留，不是无成本方案。
- `libraries/chain/finalizer.cpp` 管理独立的 `safety.dat`。新增档案、换盘、重建索引都不能删除或回退它。
- 当前 `chain_snapshot.hpp` 快照版本为 10，分叉库也有单独版本化格式。增加原生共识字段必须同时处理快照、分叉库、恢复记录及旧版本兼容。

## 4. 全历史的范围和数据格式

### 4.1 必须保存的内容

正式要求覆盖：

1. 原始 genesis 配置及链 ID 绑定资料；原生 Savanna 创世策略相关数据。
2. 从第 1 块至最新已最终确认区块的连续规范链记录，包括交易收据、完整打包交易、交易签名、上下文数据及重放需要的有效区块见证。
3. 最新未最终确认区块和恢复资料，继续由当前分叉/恢复机制维护；不要求永久保存所有曾经出现的废弃分叉。
4. 协议要求的历史索引、分段承诺及证明辅助数据。

不要求保存每个历史高度的全状态快照、全部控制台日志、所有 HTTP 查询结果或所有历史状态索引。状态历史插件和完整区块账本不是同一概念。

旧式延迟交易的部分收据只有交易 ID；必须保存其原始提交交易和完整链序列，通过历史执行恢复上下文，不能把仅存 ID 的收据当成单独完整交易。

### 4.2 统一编码是上线前置条件

拟新增 `archive_record_v1`，规范端序、长度编码、字段顺序、域分隔、版本、空值和大小上限。账本业务内容、签名/QC 等见证、磁盘容器元数据分开定义。

- 保留打包交易的真实压缩标记及字节，不进行解压后再压缩来“统一内容”，否则可能改变已承诺的交易摘要。
- 对同一 ID 的多个有效附加见证，不得用“本机最先收到的那份”来决定全网共同历史根。
- 新协议若要承诺额外的 QC 或证明正文，必须在区块头中放置其摘要，再由签名覆盖；不能仅放进未由区块头绑定的新 `block_extensions`。
- 不得把当前生产者签名本身放进其自己所签区块头的摘要承诺中，造成签名自引用。
- 对升级前的区块，需明确“共同的规范业务内容承诺 + 可独立验证的签名/QC 见证”的认证规则，或者另设计有可验证来源的历史见证承诺。不能假定已有 ID 已经逐字节承诺所有旧见证。

**验收必须区分两个范围：业务账本内容完整性、用于独立重放的见证完整性。只证明前者而删除后者，不算满足全历史要求。** 统一见证格式及旧历史认证方案在阶段 0 冻结；未解决不能启用严格存储证明。

## 5. 方案分层和不能偷换的保证

| 层级 | 实现什么 | 不能声称什么 |
|---|---|---|
| A 本地全档案约束 | 官方程序不裁剪、检测缺口、提供全部历史同步 | 无法阻止修改客户端或使用远程磁盘 |
| B 历史内容挑战 | 协议验证抽中的历史内容和认证路径 | 抽查通过不等于保存所有数据；不能防共享档案代答 |
| C 独立副本与持续证明 | 账号绑定完整历史副本承诺，周期证明并限制有效期 | 仍不能证明物理位置、操作者独立或永久保存 |

本需求最终验收以 A+B+C 及其明确的安全假设为目标。B 可先用于开发网打通底层，但不得以 B 的通过报告替代 C。

副本证明需要采用经过公开分析的构造，而不是自创“账号名加盐后哈希一下”。账号盐不会使公开历史自动变成独立存储副本，也不会阻止按需重新生成。Filecoin 的 PoRep/PoSt 是可参考的技术类别，不能直接推定其性能适合本链。[副本证明规范](https://spec.filecoin.io/algorithms/sdr/)、[存储证明规范](https://spec.filecoin.io/algorithms/pos/)。

## 6. 历史承诺和证明设计

### 6.1 历史根必须来自链本身

拟采用固定规则的历史分段和可追加 Merkle 累加器，记录完整前缀的高度、字节长度和分段范围；不能由生产者自行挑选几段数据作为“我的完整历史”。

- 累加器随分支状态推进，支持回滚；一个可研究的构造是每个新区块推进其父块记录的承诺，避免把当前区块完整数据承诺进自身而产生循环。
- 最终确认发生跳跃时，不允许在 500ms 出块路径里重新扫描全部历史；历史承诺应在正常处理区块时增量构建，之后选取已最终确认前缀。
- 挑战目标只落在父分支可确定的已最终确认历史范围内。引用锚点由协议规则确定，生产者不能自行选择一个很旧的有利高度。
- 根、已覆盖高度、分段数、尾段长度必须一起认证，避免“根合法，但只保存了前半段”。
- 验证者根据认证根验证正文和路径，不根据自己磁盘是否恰好读得到文件来决定区块真假。自己的磁盘损坏属于本地故障，不是对端作恶证据。

完整历史和承诺索引可以由后台线程存取，但共识状态转换必须确定、可重放；不能在网络线程随意读写 chainbase 数据库或共享可变历史索引。

### 6.2 分段副本和持续证明

拟采用以下接口边界，具体密码学库、电路和参数待阶段 0 定稿：

```text
verify_replica_registration(
  chain_id, producer_account, replica_generation,
  canonical_history_range, data_commitment, replica_commitment, proof)

verify_storage_period(
  certified_replica_set, committed_history_anchor,
  challenge_epoch, challenge_seed, coverage_manifest, proof)

verify_block_history_requirement(
  parent_consensus_state, block_header_binding, proof_body_or_certificate)
```

要求如下：

- 副本标识绑定链 ID、出块账号、登记代次及分段；普通出块钥匙和 BLS 钥匙轮换不应强制重封装全部历史。
- 所有历史分段必须被覆盖清单连续、无缺口地覆盖，不能让证明者只对仍然保存的分段提交证明。零长度填充和未使用空间不能算作真实历史覆盖。
- 历史封装和证明在后台增量进行；新增尾段有明确且有限的封装延迟。已封存旧段不能到期删除，不能通过不断改代次逃避旧历史责任。
- 原始可读账本须持续跟进最新最终确认；副本编码允许的尾部滞后不是删除最近历史的许可。尾段需要独立的内容挑战和覆盖规则，不能成为永远不证明的盲区。
- 周期证明有效期必须有上限；一年前通过一次证明不能永久取得出块资格。
- 证书有效期内删档仍可能存在发现延迟；若块内只引用证书，就不能声称“删掉历史后的第一块必定被拒绝”。续证周期、块内新鲜挑战与允许的风险窗口必须一起评估。
- 大证明的预提交、分批覆盖、聚合及区块内即时证明之间，需要固定上限及一致的覆盖语义；不能只验证聚合摘要而不验证底层证明。
- 不新增存储挖矿奖励，不改变投票排名；存储是获得有效出块资格所需承担的工作。

### 6.3 随机挑战不能由生产者自己挑题

挑战上下文至少绑定：链 ID、协议版本、账号/副本代次、历史锚点、挑战期以及出块所属窗口。拒绝跨账号、跨链、跨期重放。

必须审查：

1. `hash(旧区块 ID)` 可公开预测，区块内容也可能被生产者尝试多次改变来筛选结果，不能直接称为不可操控随机源。
2. 当前 Savanna QC 是参与者签名聚合，参与者集合可能不同；未经证明，不能把 QC 字节哈希当作唯一无偏随机数。
3. 自己选择 VRF 密钥、临时换钥、跳过不利时隙和选择性发布都可能制造偏置。VRF 不是自动解决这些问题的按钮。[RFC 9381](https://www.rfc-editor.org/rfc/rfc9381.html)。
4. 挑战应在副本承诺固定之后产生；规则需限制反复换承诺、换身份代次试题，并明确漏掉一次机会后是否会重新获得新题。
5. 共识截止条件用链上高度/时隙及认证锚点，不能用每台机器各自的 ping、磁盘耗时或交易到达时间。有限响应期仍不能证明没有网络代答。
6. 单节点创世没有多个独立参与者提供随机性；必须单独披露其假设，不能宣称与 21 个独立诚实参与者具有同等抗操控能力。

阶段 0 比较链内随机信标与可验证外部随机源的安全、停链及部署代价；不在本计划中擅自引入外部服务依赖，也不要求现任节点进行主观健康审批。随机源和失效行为没有定稿，严格模式就不得激活。

### 6.4 不能把抽样当作百分百全量检查

仅在样本独立、均匀且不能预知或补取的简化模型下，缺失比例为 `f`、抽样次数为 `k` 时，全通过概率约为 `(1-f)^k`。这是风险估算，不是可直接套用的最终安全证明。

抽取少量字节对“只缺少一个很小区块”的发现率可能很低；抽区块又可能低估大区块占据的数据量。需要覆盖全历史的均匀字节/分段抽样、完整性清单以及长期覆盖分析，不能只检查最近几天或几个固定高度。

## 7. 区块结构和共识接入

### 7.1 新增协议特性和有版本的扩展

拟新增原生协议特性 `PUREEOS_FULL_HISTORY_PROOF`，名称和摘要在代码实现时固定。激活前旧区块按旧规则验证，激活后按分阶段规则强制；不能根据本地配置单独启用而造成不同节点对同一个块得出不同结论。

拟新增：

- 区块头扩展：历史协议版本、认证历史锚点、存储期、必要的账号证明状态引用、证明正文摘要。
- 区块体扩展：有大小上限的内容证明/副本证明/持续证明或认证引用。
- 原生分支状态：历史累加器、已验证账号承诺的认证状态、当前证明期及激活阶段。

扩展 ID 先检查现有分配再确定；不要在计划里随意硬编码一个可能冲突的 ID。唯一性、排序、额外尾字节、最大嵌套和数组长度都要在解析阶段限制。

### 7.2 验证顺序

接收区块的目标顺序：

1. 先做网络包、扩展数量及编码长度的便宜检查，防内存/CPU 消耗攻击。
2. 验证父关系、生产者、区块签名和头部承诺，确定该分支的协议阶段。
3. 从可信父分支状态获取挑战锚点及证明上下文，验证正文摘要、覆盖范围、到期条件和密码学证明。
4. 证明合格后，才允许该块进入能够触发本节点 `consider_voting()` 的路径。
5. 保留正常 QC 验证、交易执行、finality root 核对及 commit 流程，不以存储证明代替交易合法性。

若当前架构无法在步骤 3 获得可信父状态，应排队等待，或者增加经安全审查的认证状态证明。不能简单读取未执行分支声称的根，也不能把一次针对分支 A 的“验证过”缓存复用于分支 B。

`apply_block()`、本机 `assemble_and_complete_block()`、完整重放、恢复日志重建、分叉切换也必须检查同一规则，避免只封住 P2P 入口。本机签名前做相同校验，避免自产无效块。

### 7.3 不允许的绕过方式

- `trusted-producer`、LIGHT 验证、重放优化、已验证块缓存不能跳过必要的历史证明校验；缓存需绑定完整的共识上下文。
- 链上 `eosio` 权限、开发者升级权限或换一个系统合约都不能把 native 必选证明变为可选。
- 验证失败不得通过运行时开关“临时放行”。若全网无法满足规则，就应明确是活性故障，不能悄悄退回无证明模式。
- 证明缺失、证明无效、前序状态尚未到达、本机历史磁盘故障要分别报错；不得把后两者误当成确定的恶意区块。

## 8. 创世 新节点和轮岗的边界

### 8.1 从一个节点启动

创世本身是受信的起点，历史集合为空时只能采用固定的空集合/创世认证规则；不能要求证明尚不存在的区块，也不能允许生产者任意声明“目前没有历史”。

原始历史记录从创世开始保存，分段尾部不断增长。达到规则规定的可封装条件后，进入严格证明阶段；短尾不能因为始终不足一个大分段而永久豁免，需按确定性周期封段或适用尾部证明。

单节点仅有自己参与共识，无法获得多方约束提供的同等去中心化保证。若唯一节点的数据损坏，链可能停止，不能靠协议凭空恢复历史。

### 8.2 新节点可以用快照追状态，但不能凭快照直接获得全历史出块资格

新节点可分别并行完成状态同步与历史回填。回填必须校验连续性、区块 ID、交易根及有效见证，不能仅检查“目录里有这些文件名”。

在节点官方程序层面，历史回填、索引和所需证明未就绪就不得主动签出块。链上不新增“21 个老节点批准入场”的机制；节点应在参与轮岗前自己准备完成。

首次证明可以在本人首个区块携带完整受限证明，或引用事先已上链且仍有效的证明。必须设计首块自证路径，避免“必须先让现任替我录入证书，才允许我第一次出块”的新增准入审批依赖。大型初始副本登记需要分批及认证状态设计，不能因此允许任意大首块。

正常交易或登记仍可能受到现有共识层交易审查；没有人工审批入口，不代表能够消除控制共识多数时的所有排他行为。

### 8.3 不改 Savanna 门槛，不保证任何故障都不停链

- 1 人阶段唯一节点不合格会停；2 人、3 人阶段确认仍分别需要 2 票、3 票。
- 稳定 21 人等权策略仍需 15 票；超过可容忍数量的节点失效，或交接条件不成立时，可能无法最终确认并完成换人。
- 存储证明过期若集中发生，会产生共同故障。需要重叠续证窗口、错峰及足够预算，不能把所有节点安排在同一块同时续证。
- 长暂停后的恢复必须允许合规节点重新生成/提交当前期证明，不能要求所有后续证明永久依赖一份已过期、无法更新的证书。恢复路径仍要提供真实证明，不能免验。
- 不在本轮把 finalizer 的 BLS 票格式也改为附带存储证明；保证的是出块资格及接收块有效性。若要对每一张确认票另设存储资格，需独立评估新旧策略门槛和停链风险。

## 9. 本地全历史存储和对外同步

出块模式下拟增加以下保护：

- 禁止正数裁剪和零区块日志模式。
- 允许分段存储，但每一段仍在在线可读的全历史集合里；不能用当前会被 nodeos 忽略的归档目录冒充在线历史。
- 首次启动、恢复、分段轮换时检查从第 1 块开始的覆盖；之后后台巡检内容哈希和索引，不在每个 500ms 时隙扫描整盘。
- 启动全量校验和后台校验的状态分别展示；单纯 `first_block_num == 1` 不能排除中间缺块或内容损坏。
- 数据损坏或空间不足时停止不安全的签块，保留诊断、状态和安全记录，走受验证的回填恢复流程。自动修复不等于自动删除原始故障证据。
- 状态快照是恢复加速手段，不是历史档案替代品。
- P2P 历史同步与证明生成分开线程/队列，设置带宽、并发和资源上限，避免历史下载拖垮实时出块。

没有生产者职责的普通只读/RPC 节点是否允许裁剪，应作为角色配置处理，不必强制所有钱包客户端保存历史。但它们验证激活后的区块时仍必须执行适用的共识证明规则。

“拥有副本”与“愿意向任意用户提供下载”不同。全历史同步接口属于节点运行要求；拒绝下载的链上处罚需要另设计可验证证据，不能凭其他节点声称超时就拉黑。

## 11. 性能与存储成本预算

不能承诺“不影响性能”。本机此前 22 进程测试已经出现满载及最终确认延迟，新增证明必须单独测量。

- 500ms 一个时隙，满产出约 172,800 块/天。假设每块额外放 8 KiB 证明，仅新增证明正文就约 1.32 GiB/天、481 GiB/365 天/历史副本；这是示例计算，不是参数决定或实测数据。
- 每块重复携带大副本证明不可取。拟采用后台生成、分期验证、认证证书复用和轻量块内绑定，但证书不能无限期复用，也不能因优化丢掉完整覆盖责任。
- 历史编码副本、原始可读区块、证明辅助树和恢复记录可能同时占空间；必须给出各项磁盘系数及临时封装峰值，不能只报原始 `blocks.log` 大小。
- 测量生成和验证的 P50/P95/P99、CPU、内存、磁盘随机 IOPS、网络量、漏块率和最终确认落后。区块验证预算与普通交易 CPU/NET 预算分开定义，防止把扩展当成免费算力入口。
- 候选规模从 210 增至 420/840 时，不允许每块遍历或验证所有候选的证明；用按期、分批、有界处理。是否要求未在岗候选持续续证，以及频率，应在参数冻结时明确，不隐式增加无限工作量。
- 认证根的热状态可以较小，但历史索引和副本数据仍随链增长；不能把 O(log N) 路径长度误称为总存储不增长。

若严格副本证明的最低硬件成本与预期节点门槛不相容，应回报取舍并重新确认目标，不能擅自降级成 B 层抽查后宣布完成。

## 12. 已有链如何升级

新链可以从创世累计历史承诺；已有链则必须认证升级前的全部历史。只对激活后的区块提供证明，不能满足“从创世保存”。

上线顺序：

1. 冻结规范、库版本、安全假设和验证参数；独立审查后构建可复现二进制。
2. 先部署能识别新特性、仍接受旧链规则的新程序，后台补齐历史和索引，不自动清理旧档案。
3. 对已有历史建立经过独立校验的共同承诺。不能让开发者提交一个无人验证的根，也不能让各节点因本地历史缺失而对同一激活块作不同判断。
4. 迁移设计可选择兼容格式的全历史重放预构建，或链上有界累计历史认证记录；必须证明覆盖第 1 块至迁移边界，并设计旧快照恢复路径。具体方案在阶段 0 固定。
5. 按已有公示制度处理需升级的系统合约；native 协议发布和激活另外明确授权、准备期和不可逆边界。公示 14 天不自动等于全节点已下载软件或封装完成。
6. 在独立开发网启用“观测不拒块”阶段，再测试强制阶段。生产链何时激活需另获明确确认，本次不操作已有手动链。
7. 激活后旧二进制可能不能继续验证新块；不能通过回滚二进制恢复旧规则。紧急处置不得删除安全文件或把已最终确认链重置成另一条链。

观测模式是迁移阶段，不是永久后门；严格激活后不能仅改本地配置就免除证明。

## 13. 完整测试矩阵

| 类别 | 必须覆盖的情况和通过标准 |
|---|---|
| 编码与承诺 | 空链、创世、空块、大块、交易签名/上下文数据、旧延迟收据、同 ID 不同有效见证、分段边界、非规范编码、大小溢出；不同进程得出同一规范承诺 |
| 数据范围 | 缺第 1 块、缺中间块、只有头没有交易体、仅存近期、缺尾段、伪造覆盖范围；不能被声明为完整 |

| 共识入口 | P2P 收到、本机自产、提前确认票、`apply_block`、分叉切换、重放、恢复日志、LIGHT、trusted producer；无效证明不得从任何入口获得有效性 |
| 分支确定性 | 不同本地 LIB、不同磁盘布局、线程调度、父分支未执行、根缓存过期；相同已验证父状态下结果一致，不因本机读盘失败拉黑对端 |
| 轮岗 | 1→2→3→4→21、22/23 个独立候选轮换；正常一次只换一人，所有账号均有轮到机会，新人首块自证且无人工预检 |

| 奖励 | 无效块无新增计数；有效块只记一次；孤叉回滚；首次正票激活、单节点领取、100% 块奖、减半边界保持；故障后历史收益与转账仍可按原规则执行 |
| 同步与快照 | 从任意合格节点下载创世至当前完整区块；快照只有状态不能凭空获得档案；补齐后可以出块；断点续传、恶意历史源、缺见证发现与修复 |
| 崩溃 | 封装中、索引提交中、分段写入中、投票前后 SIGKILL；磁盘满、坏段、恢复记录损坏、安全文件损坏；不静默跳过证明或丢失最后历史副本 |
| 过期与恢复 | 续证重叠、错峰、长时间全链停机、全部证书过期后恢复、无证明源可用；没有“失效后永远无法重新证明”的死锁，也不产生免验块 |

## 14. 分阶段推进与交付物

### 阶段 0 规格和可行性冻结

交付规范记录/见证编码、历史根迁移方法、证明库选型、随机源、身份/密钥绑定、尾段规则、持续期/截止期、启动/停链恢复规则、硬件预算及威胁模型。

必须先回答：能否防一份原始档案服务多个账号、怎样证明整个历史前缀而非自选子集、过期后怎样无特权恢复，以及当前出块延迟预算能否容纳验证。不能通过则停在研究阶段，不改主链规则。

### 阶段 1 全历史基础设施

实现统一档案、覆盖检查、增量索引、后台任务和 P2P 回填；测试官方程序的全历史要求。此时只是 A 层，不宣称协议已强制远端存储。

### 阶段 2 开发网协议证明通路

接入头/体扩展、native 硬校验、提前投票门禁、分支/快照/恢复；用内容挑战验证整个流程与成本。此时是 B 层开发验证，不满足严格独立副本验收。

### 阶段 3 严格副本与持续证明

接入经阶段 0 审查的证明系统及随机源，绑定全历史范围、尾段和长期续证；打通首次出块自证和恢复路径。完成恶意共享/删档/重建攻击测试及独立安全审查。

### 阶段 4 全盘回归和上线方案

执行第 13 节完整矩阵，保存成功与失败证据；核验轮岗、黑名单、奖励、资源 10%/90%、REX、一票一投和开发者公示升级未退化。形成二进制/合约哈希、参数清单、操作手册和明确的未覆盖项。

只有用户确认上线窗口后才考虑激活；不自动升级现有测试链或生产链。

## 15. 需要在正式编码前定稿的参数

这些是实现选择，不是假装用户已经确认的新增业务规则：

1. 独立副本证明的具体构造、库版本、验证参数及是否存在可信初始化。
2. 随机源及其安全/可用性假设，尤其单节点与少节点阶段。
3. 分段大小、封装延迟、证明期、续证重叠期、证明大小及 CPU/内存预算。
4. 待轮岗候选的持续证明频率；不能因为只剩 21 个在岗就忽略候选回岗准备时间。
5. 全历史字节规范，特别是旧区块签名/QC 见证的统一认证与迁移方式。
6. 是否要求物理本地磁盘。若要求“绝对证明签名机本地存储”，需明确纯软件网络协议不能提供该保证，不以模糊承诺继续开发。

默认不新增罚款、不增加储存奖励、不改变现任确认门槛、不引入人工准入、不引入未经确认的外部随机服务、不自动激活。

## 16. 本次结论

当前代码支持全历史运行，但没有把全历史存储证明作为出块有效性条件。

要把要求下沉到协议，关键不是删除裁剪参数，而是关联改造：**可认证的完整历史 → 账号绑定的副本和持续证明 → 区块头承诺与底层验证 → 提前投票门禁 → 同步/快照/恢复 → 现有轮岗和奖励回归。**

这属于 nodeos 共识协议级改造，不能只改系统合约。工程上可以强制验证证明，但不能把它夸大为远程查看每台机器硬盘的绝对保证。
