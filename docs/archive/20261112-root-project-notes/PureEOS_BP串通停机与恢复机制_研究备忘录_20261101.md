# PureEOS 在岗 BP 串通停机与恢复机制研究备忘录

记录日期：2026-11-01  
状态：研究归档，暂不实施。

用户明确希望防范在岗 BP 串通后同时关机，并已决定“这以后再研究”。本文保存讨论中的事实、边界和候选方向，方便后续继续研究。本次归档仅新增本文档，保持现有共识、轮岗、黑名单、节点配置和部署不变；不启动故障演练、压力测试或升级。

## 1. 研究目标与威胁模型

目标是在部分乃至全部当前出块 BP 联合停止工作时，让其他诚实参与者仍有机会安全推进链，并明确超出协议容错范围后的恢复方式。

需要分别考虑两种停工：

- **停止出块**：轮到的 BP 不发布区块，造成空槽；如果全部获授权的出块者停工，就没有新块可供确认。
- **停止最终确认签名**：即使其他 BP 继续发布区块，确认票不足仍会阻断新的最终确认。

攻击者不必真的关机，仅停止签名或选择性拒绝传播，也可能达到阻断效果。因此，自动重启、备用服务器和在线探测不能单独解决运营方主动串通的问题。

网络延迟、网络分区、机器故障与恶意拒签可能表现相似。超时可以作为协议推进的触发条件，但不能单凭心跳失败就证明某个 BP 恶意作恶。

## 2. 当前实现与已核对事实

研究对话期间通过默认节点 API 的 `POST /v1/chain/get_finalizer_info` 读取到：

| 项目 | 读取结果 |
|---|---|
| API | `https://aic-api.matrixai.one` |
| 活跃最终确认策略代数 | `281` |
| 确认成员 | `21` |
| 成员权重 | 每人 `1` |
| 确认门槛 | `15` |

这是研究期间的读取快照，策略代数与成员可随正常轮岗变化。此前讨论中“21 人最少需要 14 人”的说法应更正为：**在上述等权策略下，需要 15 票。**

已核对的 nodeos 源码提交为 `5d95aa18fea665f4ee60eda13b01dec82ff43535`；已部署系统合约对应源码提交为 `432360edd6763be000626898435bffcfe1aaf866`。

当前原生规则有两个关键约束：

1. 出块者由生效排班决定。注册为候补、完成同步或加入 BP gossip，并不会自动获得当前时隙的出块权。
2. 最终确认策略的正常生效依赖相关区块成为不可逆块。已经失去所需确认票时，不能假设系统合约仍能通过普通轮岗立即换掉确认成员。

当前永久黑名单依赖健康链上、满足最终确认条件的个人连续缺块窗口证据。全链或最终确认中断时暂停新增个人缺勤处罚，用来防止误罚；这个保护本身不提供恢复确认的票数。

## 3. 当前 21 人策略下的停机边界与恢复

在稳定的 21 人等权策略下，仅从票数计算：

| 同时停止确认的人数 | 剩余确认人数 | 票数结果 |
|---:|---:|---|
| 1～6 | 20～15 | 仍可能达到 15 票 |
| 7 | 14 | 不足 15 票 |
| 10 | 11 | 不足 15 票 |
| 21 | 0 | 无人确认；若同时停止出块，也没有新块 |

“票数足够”还要求网络能够通信、节点正确同步、签名安全状态允许推进，并且满足协议其他条件。头部区块暂时继续增长，也不代表最终确认正常。

普通恢复首先要恢复足够的**原生效确认身份**：例如 7 人停工、14 人仍在线时，至少需要其中 1 个原确认身份恢复参与；10 人停工时，至少需要恢复其中 4 个。其他 BP 的普通账户签名不能替代这些 BLS 确认身份。

若不足门槛的原确认身份永久失联，且没有足够的既有有效证明完成安全交接，当前普通轮岗不能保证自恢复。届时需要网络参与者协调、明确的恢复规则与升级方案，保留已经确认的历史，处理最新有效确认凭证和锁定状态，再确定新的信任与成员安排。这属于额外恢复流程，本文没有设计或授权实施。

如果停机前已经形成有效确认凭证，或者正处于策略交接，应按当时适用的活跃、待生效策略与已有证明具体判断，不能只看某一张 21 人名单作结论。

## 4. 现有措施能解决什么

| 措施 | 可以发挥的作用 | 无法单独解决的问题 |
|---|---|---|
| 同步好的候补 BP | 缩短具备安全交接条件时的补位准备时间 | 不能凭候补身份补足旧策略缺失的确认票 |
| 加快故障优先轮岗 | 在确认能力仍存在时，更早替换异常在岗者 | 不能保证跨越已丢失的确认门槛 |
| 永久黑名单 | 根据有效证据限制后续资格 | 不能依靠尚未确认的处罚立即恢复最终确认 |
| 每个 BP 配置跨机器主备 | 降低单机、进程或机房故障的影响 | 无法阻止同一运营方主动关闭主备或拒签 |
| 经济约束与退出规则 | 增加停工成本，辅助治理 | 不能在缺票时产生有效确认签名 |

主备如果使用同一确认身份，必须有排他签名、可靠切换以及正确持久化的安全状态。不能通过清空 `safety.dat`、恢复过期安全状态或让两个副本同时签名来追求恢复速度。

当前测试部署中，40 个 BP 进程与 1 个非出块历史节点位于同一物理服务器。它们不是 40 个独立故障域，也不能据此证明跨运营方抗串通能力。

## 5. 候选方向：出块与确认分离，配合原生超时接管

以下均为待研究方案，不是当前已有功能，也不是已选定的开发任务。

### 5.1 扩大独立确认成员集合

保留 21 个轮流出块席位，让更多独立 BP 持续承担最终确认职责，使阻断确认所需的串通人数超过少量在岗者。

设等权确认成员总数为 `N`，采用超过三分之二的确认门槛：

```text
Q = floor(2N / 3) + 1
仅按拒签计算，最大可容忍拒签人数 = N - Q
```

| 确认成员总数 N | 确认门槛 Q | 最大可容忍同时拒签人数 |
|---:|---:|---:|
| 21 | 15 | 6 |
| 40 | 27 | 13 |
| 64 | 43 | 21 |

因此，40 人确认集合不能覆盖“21 个在岗者全部同时拒签”的目标。在上述门槛模型下，若要容忍最多 `k` 人拒签，成员规模至少需要 `3k + 1`；`k = 21` 对应 64 人、43 票。

这里的 64 人是总确认成员数，可以包含 21 个出块成员。若这 21 人全部停工，剩余 43 人仍需诚实、在线且能相互通信。这个算例只说明票数余量，不是完整协议的安全性、活性或性能证明。

### 5.2 在没有新块时仍可推进接管

只有更多确认者仍不够：如果全部获授权的出块者都不出块，确认者必须具备一种经协议认可的方式，授权候补继续出块。

候选方向是在 nodeos 共识层研究超时与换届流程：在线确认者形成达到规定门槛的接管凭证，授权确定的候补出块；其他节点根据相同规则验证该凭证。

后续至少需要明确：

- 超时轮次、成员集合、门槛、候补顺序，以及接管凭证的签名内容。
- 如何继承最新有效确认凭证与锁定状态，保证不回退已确认历史、不确认冲突分支。
- 旧出块者恢复、凭证延迟到达、重复接管和并发接管时如何处理。
- 如何在网络分区中保持唯一、安全的授权；如何处理正常成员策略交接。
- 如何在没有新块、无法提交普通链上交易时推进协议消息。

这需要修改并验证原生共识和区块校验规则。仅缩短系统合约轮岗计时，不能获得上述能力。

### 5.3 运营与控制权独立

确认成员需要分布在足够独立的运营方、控制权限和故障域中。同一人控制多个账号，不会因为账号增加就获得相应的抗串通保障。

即使采用更大的确认集合，若攻击者控制的有效确认权重已经超过该设计的容错范围，仍可能阻断推进。任何规模都不能保证在所有有权参与者一起停工时凭空产生诚实签名。

## 6. 必须保留的安全边界

- 不根据本地看到的“在线人数”临时降低确认门槛，否则网络分区可能让两侧分别授权接管。
- 不让任意候补在超时后自行宣布上岗。资格和接管授权必须可由全网按共识规则验证。
- 不把心跳超时直接当作恶意串通证据；处罚需要单独、明确且可验证的证据规则。
- 不清除已经有效成立的违规证据或永久黑名单，也不把全链中断追溯算成诚实 BP 的个人缺勤。
- 不将已经形成的最终确认历史当作可随意回退的恢复起点。

## 7. 后续重新研究时的重点

首先确定要抵抗的串通人数与控制权模型，再选择确认集合规模，分析接管协议的安全性与活性。64 人、43 票只是覆盖“最多 21 个成员拒签”这一目标的候选算例。

后续验证应覆盖联合停工、只拒签仍出块、全部当前出块者停工、网络分区、策略交接中断、旧成员恢复、候补异常、冲突凭证和安全状态恢复。还需要测量确认延迟、通信与 BLS 验签开销、节点资源和实际 TPS。

过去接近 4 万 TPS 的测试结果不能直接用于宣称新确认规模与接管协议仍具备相同性能。是否实施、测试范围和基线推广均留待用户另行决定。
