# 原生 Savanna 硬重放恢复日志修复

2026-10-24。状态：生产修复及原生回归已通过；真实双VM恢复已通过。第一版尚未发布。

真实供应商 VM halt/start 测试暴露了两层不同情况：非正常退出的派生状态库可能带
脏标记；区块日志尾部也可能是不完整写入。普通 replay 不修补损坏尾部，须用硬重放
先恢复有效前缀。原四次失败、供应商回执和原始日志分别保留，没有改判成功。

在只读保留原数据、另建诊断副本后，旧硬重放能够恢复到第517块，但把整个
`blocks/reversible` 搬到了备份。57份已提交恢复记录也随之被移走。启动随后报告
恢复0份记录，并另建新的活动 journal。这会遗漏先于投票落盘的块和分支，影响
单节点/少节点恢复，不能只依靠另一节点追块掩盖。独立 finalizers/safety.dat
265字节在该次诊断前后摘要相同，没有删除安全状态。

## 实现

- `libraries/chain/block_log.cpp`：有 durable recovery journal 时，让它始终保留在
  原活动路径；只将其他 fork 数据移入备份。拒绝符号链接/非目录 journal，拒绝
  同时截断带 journal 的日志；这些检查在搬动日志前完成。备份目录项和修复的
  日志内容执行同步，原日志的完整字节仍留在备份。
- `plugins/chain_plugin/chain_plugin.cpp`：日志修复成功后才清理派生 state；验证
  失败时不先清空原状态。finalizers 目录不动。
- `unittests/pureeos_genesis_tests.cpp`：用真实单节点原生 Savanna、原安全文件和
  持久化记录，构造有效旧前缀加不完整尾部；验证原日志备份、journal逐字节保留、
  重建 state 后恢复最新 head 并继续最终确认；验证危险截断/链接在搬动前拒绝。

云端任务先用新增用例链接旧生产代码，要求复现 journal 丢失；再应用生产修复，
编译新程序并执行三轮恢复和原生合约矩阵。此前通过的旧二进制报告仍按旧身份
保存，不能自动视为本修复后的程序通过。第一版发布前没有 TPS 压测。

证据目录：`cloud-vm-recovery-retest-20261024-attempt-1`、
`cloud-hard-replay-repair-20261024-attempt-1`。
