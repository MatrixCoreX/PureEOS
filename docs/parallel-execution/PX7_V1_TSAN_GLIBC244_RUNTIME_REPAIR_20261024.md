# Ubuntu 26.10 / glibc 2.44 的 TSan 运行库修复验证

当前发现的是测试运行库与 glibc 的不匹配。尚不能把修复库的启动成功计作并行版本完整验收通过。生产节点、系统 glibc 和系统 libtsan 均未替换。

## 原始失败和定位

原私有 TSan 构建包含 348 个重新插桩的翻译单元，生成 ELF SHA256 `46b3abbbfb25af4498f7d82ae1852741a2a7df64ac6449937951a2ce3b41f575`。第一轮退出66，后续五轮未运行。错误为 `can't find longjmp buf` 和 TSan 内部 CHECK，并非已经报告的数据竞争。八份闭合文件已下载核验，原失败保留。

环境为 GCC 15.3 编译器、Ubuntu libtsan2 16.2.0-3ubuntu1、glibc 2.44-1ubuntu2。普通控制三项通过，TSan 控制五项均复现同一错误，包含不使用链代码、VM 或 Boost 的 sigsetjmp/siglongjmp 小程序；关闭 Boost 的系统异常捕获仍然失败。反汇编显示 glibc 使用全局 `__pointer_chk_guard`，TSan 解码保存的栈指针仍读取旧 `%fs:0x30`。

上游记录：[LLVM #216004](https://github.com/llvm/llvm-project/issues/216004)、[LLVM PR #216558](https://github.com/llvm/llvm-project/pull/216558)。该 PR 在本次取证时仍未合并，不能声称系统发行版已修好。

## 隔离修复实验

固定 LLVM 基线 `e78dda344a46c2ca2db664be8b464953c8491e4f`，单文件应用 PR 提交 `92fed264bf63a064eeb0145262dba0f41da265c4`。补丁 SHA256 为 `13926003004fd546a577aeafcd5f386119d81321e4759d515f399c00e96d3c9c`，修改后文件 SHA256 为 `8891d2995f56844f07610172e2d8d48f3f6758c03833b75b87da57d0258d41ae`。运行库自行探测跳转指针的 XOR/旋转规则，避免依赖 glibc 私有保护值的位置。

仅编译 compiler-rt 的 x86_64 动态 TSan，保留 LLVM 原许可；两项编译并发，CPU配额200%，8GiB内存，低优先级。实际编译成功，生成运行库 SHA256 `f0ccb6d4dad8bff7afd3b1d8c41752f7501fc8104cd6e467810d94fe48272fc2`。使用私有 LD_LIBRARY_PATH 向原来未改动的 GCC 插桩 ELF 提供该库；动态加载结果已核查。

已观察通过：普通跳转恢复、真实 PROT_NONE 信号恢复、实际 VM 头文件中的信号恢复、原完整 ELF 的内存故障隔离用例。互斥保护程序通过；故意数据竞争程序以66退出并报告真实数据竞争，说明检测没有被关闭。未加 suppressions、ignore 或替代 longjmp 绕过。

控制通过后才启动原定 276 项精确私有用例，JIT CLI 三轮、解释器 CLI 三轮；直接构造的执行器仍由各用例本身决定。必须核查每轮 XML 的全部用例名称，不能只核对总数。最初规定的23项控制器类排除保持不变。这个范围不等于整个 nodeos、FC、Chainbase 或生成的 JIT 机器码均已插桩。最终结果见闭合清单及独立下载核验报告，运行中状态不能计为通过。

第一启动因隔离根内缺 DNS 配置而失败，未进入构建和原生用例；保留所有证据。第二启动只增加只读 DNS 绑定。原始系统 TSan 失败与第一次基础设施失败均不会覆盖。
