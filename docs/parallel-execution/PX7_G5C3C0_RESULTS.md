## 通用资源池改造

`sync_call_resource_pool.hpp` 原本只有空池 assert，Release 未检查 pop 返回值；增长中的创建/push 失败也没有整体所有权与提交边界。现改为显式拥有资源、登记借还状态及一次发布的增长过程：

- 借出耗尽抛运行时错误，不返回未初始化指针；空、外来或重复归还返回 false，不把同一个可变 VM 发给两个调用者。
- 归还容量先预留，正常归还不申请内存、不抛异常，可用于异常清理。对象由池持有，销毁不依赖可用队列是否收齐；析构仍要求所有使用者已经停止。
- 数量乘法在 64 位中计算，超过原 32 位容量域先拒绝；线程数/深度只增长。资源工厂返回空指针、异常或重复对象都不能暴露半批资源，失败后两维配置保持旧值。
- 工厂在借还锁外运行；增长操作另行串行化。已有对象可在增长途中借还。准备好全部对象后，转移稳定 map 节点并发布新资源，资源地址不会因容器扩容改变。

为了完整的所有权/失败保证，原 lock-free 栈改成短临界区登记。借出 O(1)，归还包含 O(log 容量) 的归属查询；不持锁运行 WASM，也不持借还锁创建资源。这不是“没有额外开销”的性能声明；本阶段不由小型正确性测试推算 TPS。

## 调用方复查及剩余项

解释器原入口先取得一个 allocator，再立即安装 scope-exit，已经保留正确单资源清理顺序。OC 的两处入口（`wasm_interface_private.hpp` 和 `webassembly/runtimes/eos-vm-oc.cpp`）原先却先取得 executor、再取得 memory，最后才安装同一个 scope-exit；第二次申请失败会遗失第一次借用。已改为逐次申请后立即安装清理，第二次失败及执行阶段失败的同型 guard 用例通过，实际调用源码另做 OC 宏开启的对象编译检查。

OC 分层 `memory_pools.cpp` 原有新池扩容索引问题（循环从 0 用 `pools[i]`，不是刚添加的池）。已把同一实际算法提取为 `depth_resource_pools<T>`，OC 包装直接使用它：每个新池先按当前线程数完整初始化，浅层独立、第五层及更深共享最后一个池；新槽初始化完成后再原子发布数量，旧池地址不变。归还按真实所有者查找，不依赖当前布局或传入深度重新猜所属池。原上层协议深度检查不改变。

新布局增长失败不会发布部分新池；对多个已有池逐一增加线程时，前面的池可能保留额外容量，但逻辑线程数维持旧值，重试可补齐后面的池，不回收在用对象。这是有意的单调多分配，不宣称跨多个池的物理容量完全回滚。

增加 7 项 / 850 条，合并共 15 项 / 1,072 条的普通、ASan、TSan 均各三轮通过。包括两种配置顺序、1–9 层 / 4 线程容量、新布局失败回滚、部分线程增长后旧逻辑维度及重试、所有者归还、非法/溢出输入、4 线程 20,000 次借还期间发布新池、慢工厂期间借还和两资源异常 guard。算法测试的资源是普通对象，不冒充 OC WASM 执行。

进一步发现 `eosvmoc::memory` 构造中取得整段 mmap 后，后续切片/内置接口表初始化抛异常不会进入析构；已加构造阶段整段映射 guard，成功时才转交析构。真实 `memory.cpp` 的失败注入先通过三轮 3 项 / 28 条，追加实际 `munmap` 返回值检查后，最终三轮各 3 项 / 32 条通过，注册的三个池/分配器入口也通过。覆盖初次 mmap 失败、两个切片阶段失败、内置接口表初始化失败及成功后析构恰好一次，核对整段地址/长度、系统调用成功及文件描述符数量。

失败注入目标使用空内置接口目录及链接期系统调用包装，只证明真实分配器源码的生命周期，不链接/执行完整 OC 合约运行时。测试替身由专用编译宏限制，普通 unit_test 不定义替身符号。Linux x86-64 下额外对象目标开启 OC 宏，实际编译 `eos-vm-oc.cpp`、`memory_pools.cpp`、`memory.cpp`、`wasm_interface.cpp` 全部通过；对象未链接入普通节点，不改变 ENABLE_OC=OFF。
