# PX7：向通用合约并行执行扩展（滚动实施）

开始日期：2026-10-11。按用户要求边研究、边开发、边校正本计划。分支沿用 `feature/parallel-tx-execution`；本轮起点 `0068f79`，PX0–PX6 报告保留为历史证据，不覆盖失败性能样本。

## 目标与不变条件

目标是让普通资产合约及一般合约的独立交易能够真实并行执行 WASM，而不局限于手写小型测试模块。所有交易不可能无条件同时提交：余额、权限、索引、调用树等有依赖时仍需按原顺序处理。正式账本、授权、资源结算、receipt、通知输出与最终确认继续遵守原规则，不采用多线程直接写 Chainbase。

不改系统合约经济/治理、不修改 `main`/基线标签、不覆盖原程序/手动链/个人配置、不推送；实验默认关闭。未支持的语义必须整笔安全回退，不得靠忽略通知、RAM、权限或资源费用来扩大覆盖率。

## 代码复查得到的实际阻碍

以下记录本计划启动时（`0068f79`）的情况，已解决项以各阶段进度和验收记录为准，不代表后续源码仍保留这些旧限制。

1. `primary_state_overlay::depend_on` 与 `ordered_attempt_batch::can_use` 只记整表依赖；同表不同主键会误冲突，canonical adopter 还会逐行复查整表。
2. `controller::prepare_isolated_attempts` 当前枚举 receiver 名下所有表再冻结，超过 64 表/4096 行/4MiB 回退。真实 token 的多账户 scope 不适合这种全量捕获。
3. `isolated_host` 仅 15 个接口，普通 CDT 产物的内存、断言、账户检查、通知、创建行等导入不能链接；不能仅把 eosio.token 哈希加入名单就宣称已支持转账。
4. 当前日志只描述既存行、同 payer、同长度更新；没有创建/删除、临时 ID、RAM payer 改变和二级索引的事务日志。
5. 当前 adopter 只接管顶层一次 WASM，未隔离通知/inline/sync-call 调用树，也未支持一笔交易多个 action 的统一私有状态。
6. 热点退化与关闭模式性能门槛尚未全部达标；扩大能力需要同时保留性能对照，不能只看测试通过数量。

## G1 依赖契约

保留表元数据依赖（存在性、对象编号、payer、count），新增 `(code, scope, table, query-kind, primary-key)` 查询集合及本地数量预算。当前允许的写仍只改变已有行的值，不改变键集合/顺序/元数据，因此前序值更新仅使选择了该主键的查询失效；缺失点不会被无关行更新错误污染。写入自身也必须登记该主键依赖。

提交前重新执行同一查询：比对存在性、选中的主键/对象 ID/payer/长度及完整原值。范围查询不能仅记录最后余额；插入/删除导致选择结果或表元数据改变时必须回退。日后 G4 引入结构变化，协调器的依赖类型必须一起扩展，不能沿用“值更新不会产生幻读”的当前限定。

任何串行回退仍保守丢弃本批后续旧试算；G1 不顺带实现无版本证明的跨冲突继续采用。

## 首轮研究补充：真实 token 不是补一个 transfer 接口

只读检查现有 CDT 产物 `reference-contracts/build/pureeos-resource-split/eosio.token/eosio.token.wasm`：23 个导入、46 个本地函数；线性内存初始 1 页，**未声明最大页数**。除主键/授权接口，还有 `memcpy`、断言、`abort`、`is_account`、`require_recipient`、`prints_l`、store/remove，以及模块中存在但转账未必调用的参数/提议生产者/时间接口。

因此 G3 拆为以下独立验收项，不能仅打开哈希名单：

1. 内存增长：G3a 之前要求显式最大页数，是为了避免局部内存上限把原本成功的 `memory.grow` 改为返回 `-1`，使合约走另一条“成功”分支。支持未声明上限的 CDT 模块，必须在可能触及局部而非协议上限时使整次尝试回退，或完整模拟协议上限；不可直接删除检查。
2. 未执行的危险导入：可研究“可链接但调用立即整笔回退”的显式桩，但它不是实现该 host，更不能把它登记为已支持。任何默认空实现都是禁止的。
3. 通知：`require_recipient` 产生后续执行，不能吞掉。先审查原 `apply_context` 调度次序、接收者存在性、失败撤销和资源结算，再决定由完整私有调用树执行，还是由 owner 按原序调度子动作。任何只看余额的验收不足以证明通知正确。
4. 首个真实转账验收只覆盖既存双方余额行；新建余额行、最后余额行删除、payer/RAM 变化必须等 G4，不可假称所有 transfer 已并行。

G2 初拟“按需整表捕获”，但源码推演发现它仍会因单张大表超过 4096 行而退出。因此调整为**按具体查询选中记录的稀疏捕获**，同时解决大量无关 scope 与目标表很大这两种情况；仍保留 64 张实际访问表、4096 条实际复制记录/查询、4MiB 副本总量等本地预算。

### G2 数据请求协议（实施规格）

1. worker 读未捕获的表元数据或具体查询时，退出当前尝试，返回只含表键/查询键的拥有值；不能返回 Chainbase 指针，也不能把未捕获当作不存在。
2. owner 等整个工作批次返回，再从原数据库复制所请求的表元数据和查询选中行。保留负查询结果及完整选中行；不同查询选中同一行只保存一份。对“上一条/下一条”不能在稀疏副本中自行推断相邻行。
3. 每次补充后创建新的不可混用批次身份，重新执行整个批次。旧结果/旧票据全部丢弃；在所有探测结束前，没有正式账本写入或输出。
4. 最多 8 个探测轮次，验证端整个私有准备阶段有本地总时限，生产端还受原有更短的出块墙钟预算。超限只影响采用率，必须原序串行，不能拒绝原本合法的块/交易。
5. 原 `attempts` 诊断应计入数据发现阶段的实际尝试，不能只报最后一轮而隐去重跑成本；正式 CPU 仍按完整成功执行加原结算流程计费，丢弃的局部探测属于节点本地开销。
6. 额外测试：4100 行表只复制 2 行；超过 64 个无关 scope 不阻止目标行采用；有代码支持但不断产生新查询的合约能有界退回；中断、错误块/undo、旧程序重放继续覆盖。

### G3 后续接口改造的源码约束

- `webassembly/common.hpp:basic_type_converter` 在进入 host 前已校验指针；新 worker 不能只模仿函数体。例如 `memcpy/memset` 的零长度调用仍检查目标至少 1 字节，`eosio_assert(true, msg)` 的字符串参数也不能绕过原指针检查。
- `webassembly/memory.cpp` 禁止 `memcpy` 重叠；`memcmp` 返回值规范化为 `-1/0/1`。新实现若直接返回平台 libc 的任意差值，会改变合约可观察结果。
- `host_context.cpp:is_account` 读的是 `account_object/by_name`，不是“有余额表”或“有代码”。需要新增有界、受依赖追踪的账户存在性副本；不能在 worker 查询 controller。
- `apply_context.cpp:exec/require_recipient` 先完成当前接收者，再按去重后的通知顺序执行通知，随后执行 inline。可研究先让 root WASM 并行、无代码通知由 owner 按原序生成 receipt，但有代码/原生处理器通知的状态写入不能绕开依赖失效；在调用树适配前必须明确回退。
- 实际 `eosio.token.cpp:sub_balance` 使用 `modify(from, owner, ...)`。如果余额行最初由别人付 RAM，即使双方已有余额行，首次付款也可能改变 payer，必须等 G4 或整笔回退。`add_balance` 对既有收款行使用 `same_payer`；余额变为零不会在 transfer 中自动删除，删除由 `close` 执行。
- G3 要修改的入口包含 `parallel_wasm_worker.hpp/.cpp`、状态读取接口/副本/依赖、`parallel_canonical_adoption.cpp`；逐 host 测试与 `parallel_audited_intrinsics.hpp` 对应的拒绝/受支持/仅回退桩分类须同步。旧 15 host 边界不会因为写下本计划而自动扩大。
- G5 不能直接把新 worker 接到原 sync-call allocator pool：`sync_call_resource_pool.hpp:acquire` 依赖预先按线程数/深度扩容，Release 下并未处理 `stack.pop` 失败的返回值；本轮 GCC 也发出 `res may be used uninitialized` 警告。当前私有执行器不调用该池。本轮不改它，但调用树扩展必须明确独占 allocator 和耗尽处理，不能把池容量假设带进新并发路径。

### G3a 本轮实施切分

先完成可单独核验的运行时兼容层，再接入账户依赖与通知。改动集中在 `parallel_wasm_worker.cpp`：所有 `memory.grow`（含 start）先检查本地上限；超限整次丢弃，不能让本地 `-1` 改变合约分支。模块未声明内存上限不再直接拒绝，初始页数、代码和执行预算仍有界。负数/极大增长保守回退，不改 EOS VM 子模块。

新增 `memcpy/memmove/memcmp/memset`、三个断言入口和 `abort`；失败由原串行路径产生正式异常。另有 10 个明确“可链接、调用必回退”的入口，只为允许 CDT 模块中未调用的库导入；不把账户读取、通知、控制台、store/remove 或特权操作登记为已实现。其余 229 个生产接口继续拒绝链接。原生产 host 的 262 项审计分类不自动批准。

新增 `unittests/test-contracts/parallel_cdt/` 的源码、ABI 和固定 WASM，使用真正的 CDT dispatcher、`multi_index`、动态分配与已有行修改，验证端/生产端分别检查真实采用、热点、失败断言、超限后回退及原串行 receipt/RAM/状态。它不是 token，G3a 完成也不能勾选“真实资产转账完成”。`is_account` 的有界副本、通知日志和接收者代码检查仍为接下来的 G3b。

### G3b 实施规格（已按本节边界验收）

1. 账户存在性由 owner 在 `account_object/by_name` 读取，按需复制存在/不存在证明；worker 的未知账户只能提出带类型的数据请求。扩展 `transaction_state_view`、frozen/overlay、工作池结果和 controller 探测集合，分别限制账户数及请求数。不能把未捕获账户当不存在，不能借用 token 余额表作证明。
2. `is_account` 的实际读取进入结果依赖，正式采用前重新检查。不要把每笔通知都会变化的 `recv_sequence/auth_sequence` 混进账户存在性版本，造成无关交易误冲突；账户对象身份或存在性与接收者执行能力需分别审查。
3. root 的 `require_recipient` 仅记录有界、去重、保留首次出现顺序的通知列表，自身已在通知集合。先完成 root WASM，再由 owner 通过原 `require_recipient` 和 `exec_one` 生成各通知的 action trace/receipt/序列及计费；无代码通知也不能省略。

### G5 源码复查与实施切分

`transaction_context::exec` 先调度全部顶层 action，再依次执行，每个 action 的通知随后生成新的 ordinal。因此不能靠“下一个 action trace”直接匹配下一个顶层私有结果；通知可能插在执行次序中，但顶层 ordinal 已经分配。当前 `apply_context::exec_one` 只交换一次私有指针，也必须改为明确的交易级游标，避免通知误消费下一项。

G5a 先提取 `isolated_wasm_module` 的单步执行，新增有线程归属的交易级执行器。每笔最多 16 个受限顶层 action，在同一工作线程按顺序共享一个 `primary_state_overlay`；每步重新建立动作级游标，重置内存/start/通知去重和返回值。保留每步的写入区间、通知位置、执行指纹及私有执行耗时，最终只 seal 一次。任何一步取数失败、越界、trap、超时或调用未支持接口，整次调用不返回任何可采用结果；不会将已成功前缀暴露给正式执行。总读写预算不按 action 重新获得，整笔另受绝对时限约束，模块缓存仍每执行器最多一个。

G5b 再把交易级结果接入原工作池、顺序协调器和正式采用。需要在首次写入前核对整笔原始依赖及所有 action/代码/通知能力；后续 action 读到的前序私有新行不能拿临时 ID 和正式分配 ID 直接比较。由原 host 按分段日志重放，在原交易 undo 中统一成功或失败，禁止“写完前半后重新执行整笔”造成重复扣款、重复通知或重复 CPU 计费。原生/特权操作、带代码通知及未覆盖子调用仍作为整笔串行屏障。正式接入之前，G5a 的私有测试不计作多 action 已能上链采用。

G5c 再实现带代码通知/inline 的完整执行顺序、授权与深层失败；同步返回调用需要另外解决调用栈、独占 allocator、耗尽和返回传播。不是简单删除 `receiver == account` 或放行 `send_inline` 导入。每一切分都需原串行 oracle、跨 action 读写依赖/生命周期/授权隔离、重复与失败、1/2/4 worker、sanitize 和恢复证据。

G5c 后续源码约束（本节只是研究记录，尚未实现）：

- `apply_context::exec` 对同一根动作先执行根 receiver，再遍历可追加的 `_notified`，最后执行 context-free inline 和普通 inline；不能用递归立即执行通知来替代。`require_recipient` 在整个根动作通知组去重，通知 B 再通知 A 或 B 不能重新执行，通知生成的新接收者按队列顺序处理。
- 同一 `apply_context` 在通知接收者间复用原 host 迭代器缓存。G5a 的“每个顶层动作重置游标”不能直接变成“每个通知重置游标”，否则返回的迭代器数值可能不同；需要通知组级缓存和逐接收者写权限检查。新的顶层动作及新的 inline 才建立各自上下文。

重放发送时应调用原 `webassembly::interface::send_inline`，保留严格长度、原 FC 解包和 `execute_inline` 的当场授权及调度；不要复制一套看似相同的权限逻辑。`schedule_action` 可能重分配 action trace 向量，因此跨发送不能继续使用旧 trace/act 引用；原 apply_context 会刷新自己的 action 指针，新 adopter 也不能缓存后继续解引用。所有调度、写入、CPU 检查异常走原 undo，不允许在已有正式写入后整笔重跑。

`apply_context::execute_inline` 在发送发生的位置立即检查目标账户、授权账户/permission、黑白名单及 `authorization_manager::check_authorization`，随后分配 trace ordinal 并排队；并非子动作开始时才授权。`exec()` 先跑完本组所有通知，再执行 context-free inline 队列，最后执行普通 inline 队列；通知产生的 inline 也在这同一组队列中。每个 inline 执行创建新的 apply_context/游标，但仍处于原交易共享状态和 undo 中。不能把 inline 混入通知的接收者去重集合，也不能按 ordinal 递增顺序执行整个调用树。

实现普通 inline 时，事件日志应保留完整拥有所有权的 action（目标、名称、授权和参数）、发送位置及分配的 ordinal；原 adopter 必须在同一事件位置调用原 `execute_inline`，原授权失败直接撤销整笔，禁止先执行子动作再补权限。私有树预检则绑定发送事件与子组输入、creator/ancestor/深度及全交易预算，子组合约代码也由 owner 按需捕获并检查名单。原 `get_sender()` 返回 creator 的 receiver，通知和 inline 都不能一律返回顶层 account；如开放此 host，必须把真实创建者关系纳入指纹和差分测试。初步只开放普通 inline，context-free 与同步调用分别验收，未支持的整笔回退。

继续复核 `webassembly/transaction.cpp` 后补充：`send_inline` 的原始字节长度要求是严格 **小于** `max_inline_action_size`，并先执行原始 action 解包再调用 `execute_inline`。日志必须保留发送的原始字节串并绑定解包后的子输入，不能仅重打包一个等价 action（可能丢失尾部字节，改变长度检查或解包错误）；正式重放保留相同 host 包装检查和异常发生位置。`apply_context::schedule_action(action&&)` 将 inline 的 `closest_unnotified_ancestor` 设为**发送者所在组的首接收者 ordinal**，不是 0，也不是新 inline 自己；只有该 inline 后续通知才以新的组首 ordinal 为 ancestor。树节点因此需要独立保存 creator、ancestor、组标识和深度，不能继续用当前通知模式的 `root_index + 1` 推导全部 inline 关系。

`sync_call_resource_pool.hpp::acquire` 当前只在 assert 中检查空池，Release 下未检查 `stack.pop` 的返回值便返回未初始化指针；`resize` 还需审查乘法溢出、部分创建失败的所有权以及 push 失败。该池供原 WASM allocator/OC executor 使用，当前私有通知 worker 不借用此池；在进一步接入嵌套同步执行前单独修复并做耗尽、恢复、并发独占和失败释放测试，不能因正常深度测试通过就忽略 Release 防御。此次构建仍是 ENABLE_OC=OFF，不能宣称 OC 路径已实际验收。
