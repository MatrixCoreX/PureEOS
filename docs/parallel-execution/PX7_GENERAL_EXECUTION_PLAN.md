# PX7：向通用合约并行执行扩展（滚动实施）

开始日期：2026-10-11。按用户要求边研究、边开发、边校正本计划。分支沿用 `feature/parallel-tx-execution`；本轮起点 `0068f79`，PX0–PX6 报告保留为历史证据，不覆盖失败性能样本。

## 目标与不变条件

目标是让普通资产合约及一般合约的独立交易能够真实并行执行 WASM，而不局限于手写小型测试模块。所有交易不可能无条件同时提交：余额、权限、索引、调用树等有依赖时仍需按原顺序处理。正式账本、授权、资源结算、receipt、通知输出与最终确认继续遵守原规则，不采用多线程直接写 Chainbase。

不改系统合约经济/治理、不修改 `main`/基线标签、不覆盖原程序/手动链/个人配置、不推送；实验默认关闭。未支持的语义必须整笔安全回退，不得靠忽略通知、RAM、权限或资源费用来扩大覆盖率。

## 代码复查得到的实际阻碍

1. `primary_state_overlay::depend_on` 与 `ordered_attempt_batch::can_use` 只记整表依赖；同表不同主键会误冲突，canonical adopter 还会逐行复查整表。
2. `controller::prepare_isolated_attempts` 当前枚举 receiver 名下所有表再冻结，超过 64 表/4096 行/4MiB 回退。真实 token 的多账户 scope 不适合这种全量捕获。
3. `isolated_host` 仅 15 个接口，普通 CDT 产物的内存、断言、账户检查、通知、创建行等导入不能链接；不能仅把 eosio.token 哈希加入名单就宣称已支持转账。
4. 当前日志只描述既存行、同 payer、同长度更新；没有创建/删除、临时 ID、RAM payer 改变和二级索引的事务日志。
5. 当前 adopter 只接管顶层一次 WASM，未隔离通知/inline/sync-call 调用树，也未支持一笔交易多个 action 的统一私有状态。
6. 热点退化与关闭模式性能门槛尚未全部达标；扩大能力需要同时保留性能对照，不能只看测试通过数量。

## G1 依赖契约

保留表元数据依赖（存在性、对象编号、payer、count），新增 `(code, scope, table, query-kind, primary-key)` 查询集合及本地数量预算。当前允许的写仍只改变已有行的值，不改变键集合/顺序/元数据，因此前序值更新仅使选择了该主键的查询失效；缺失点不会被无关行更新错误污染。写入自身也必须登记该主键依赖。

提交前重新执行同一查询：比对存在性、选中的主键/对象 ID/payer/长度及完整原值。范围查询不能仅记录最后余额；插入/删除导致选择结果或表元数据改变时必须回退。日后 G4 引入结构变化，协调器的依赖类型必须一起扩展，不能沿用“值更新不会产生幻读”的当前限定。

任何串行回退仍保守丢弃本批后续旧试算；G1 不顺带实现无版本证明的跨冲突继续采用。

## 首轮研究补充：真实 token 不是补一个 transfer 接口

只读检查现有 CDT 产物 `reference-contracts/build/pureeos-resource-split/eosio.token/eosio.token.wasm`：23 个导入、46 个本地函数；线性内存初始 1 页，**未声明最大页数**。除主键/授权接口，还有 `memcpy`、断言、`abort`、`is_account`、`require_recipient`、`prints_l`、store/remove，以及模块中存在但转账未必调用的参数/提议生产者/时间接口。

因此 G3 拆为以下独立验收项，不能仅打开哈希名单：

1. 内存增长：当前要求显式最大页数是为了避免局部内存上限把原本成功的 `memory.grow` 改为返回 `-1`，使合约走另一条“成功”分支。支持未声明上限的 CDT 模块，必须在可能触及局部而非协议上限时使整次尝试回退，或完整模拟协议上限；不可直接删除检查。
2. 未执行的危险导入：可研究“可链接但调用立即整笔回退”的显式桩，但它不是实现该 host，更不能把它登记为已支持。任何默认空实现都是禁止的。
3. 通知：`require_recipient` 产生后续执行，不能吞掉。先审查原 `apply_context` 调度次序、接收者存在性、失败撤销和资源结算，再决定由完整私有调用树执行，还是由 owner 按原序调度子动作。任何只看余额的验收不足以证明通知正确。
4. 首个真实转账验收只覆盖既存双方余额行；新建余额行、最后余额行删除、payer/RAM 变化必须等 G4，不可假称所有 transfer 已并行。

G2 初拟“按需整表捕获”，但源码推演发现它仍会因单张大表超过 4096 行而退出。因此调整为**按具体查询选中记录的稀疏捕获**，同时解决大量无关 scope 与目标表很大这两种情况；仍保留 64 张实际访问表、4096 条实际复制记录/查询、4MiB 副本总量等本地预算。

### G2 数据请求协议（实施规格）

1. worker 读未捕获的表元数据或具体查询时，退出当前尝试，返回只含表键/查询键的拥有值；不能返回 Chainbase 指针，也不能把未捕获当作不存在。
2. owner 等整个工作批次返回，再从原数据库复制所请求的表元数据和查询选中行。保留负查询结果及完整选中行；不同查询选中同一行只保存一份。对“上一条/下一条”不能在稀疏副本中自行推断相邻行。
3. 每次补充后创建新的不可混用批次身份，重新执行整个批次。旧结果/旧票据全部丢弃；在所有探测结束前，没有正式账本写入或输出。
4. 最多 8 个探测轮次，验证端整个私有准备阶段有本地总时限，生产端还受原有更短的出块墙钟预算。超限只影响采用率，必须原序串行，不能拒绝原本合法的块/交易。
5. 原 `attempts` 诊断应计入数据发现阶段的实际尝试，不能只报最后一轮而隐去重跑成本；正式 CPU 仍按完整成功执行加原结算流程计费，丢弃的局部探测属于节点本地开销。
6. 额外测试：4100 行表只复制 2 行；超过 64 个无关 scope 不阻止目标行采用；有代码支持但不断产生新查询的合约能有界退回；中断、错误块/undo、旧程序重放继续覆盖。

### G3 后续接口改造的源码约束

- `webassembly/common.hpp:basic_type_converter` 在进入 host 前已校验指针；新 worker 不能只模仿函数体。例如 `memcpy/memset` 的零长度调用仍检查目标至少 1 字节，`eosio_assert(true, msg)` 的字符串参数也不能绕过原指针检查。
- `webassembly/memory.cpp` 禁止 `memcpy` 重叠；`memcmp` 返回值规范化为 `-1/0/1`。新实现若直接返回平台 libc 的任意差值，会改变合约可观察结果。
- `host_context.cpp:is_account` 读的是 `account_object/by_name`，不是“有余额表”或“有代码”。需要新增有界、受依赖追踪的账户存在性副本；不能在 worker 查询 controller。
- `apply_context.cpp:exec/require_recipient` 先完成当前接收者，再按去重后的通知顺序执行通知，随后执行 inline。可研究先让 root WASM 并行、无代码通知由 owner 按原序生成 receipt，但有代码/原生处理器通知的状态写入不能绕开依赖失效；在调用树适配前必须明确回退。
- 实际 `eosio.token.cpp:sub_balance` 使用 `modify(from, owner, ...)`。如果余额行最初由别人付 RAM，即使双方已有余额行，首次付款也可能改变 payer，必须等 G4 或整笔回退。`add_balance` 对既有收款行使用 `same_payer`；余额变为零不会在 transfer 中自动删除，删除由 `close` 执行。
- G3 要修改的入口包含 `parallel_wasm_worker.hpp/.cpp`、状态读取接口/副本/依赖、`parallel_canonical_adoption.cpp`；逐 host 测试与 `parallel_audited_intrinsics.hpp` 对应的拒绝/受支持/仅回退桩分类须同步。旧 15 host 边界不会因为写下本计划而自动扩大。
- G5 不能直接把新 worker 接到原 sync-call allocator pool：`sync_call_resource_pool.hpp:acquire` 依赖预先按线程数/深度扩容，Release 下并未处理 `stack.pop` 失败的返回值；本轮 GCC 也发出 `res may be used uninitialized` 警告。当前私有执行器不调用该池。本轮不改它，但调用树扩展必须明确独占 allocator 和耗尽处理，不能把池容量假设带进新并发路径。
