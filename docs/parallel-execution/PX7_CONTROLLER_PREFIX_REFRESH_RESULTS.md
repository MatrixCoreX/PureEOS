## 实现

- `controller.cpp::prepare_isolated_attempts` 增加内部借用模式：仅重新准备当前冲突交易，复用原批次身份、线程池及剩余准备预算。重新捕获真实根、代码、上下文、查询，允许重新发现 sync/mixed 模式及调用对象。每一发现轮都生成新的当前前缀 ticket，不把旧结果改标签。
- `refresh_conflicting_attempt` 先只读区分依赖冲突与不可用。只有完整结果发生依赖冲突时尝试刷新；先释放旧 ticket、结果和该位置的目录。失败则保持空结果，沿原串行回退关闭尾部，不能重新使用旧 journal。
- 新结果按原顺序交给原 canonical adopter，仍走授权、资源、undo、收据和信号路径。新实际写集进入后续依赖检查，其他旧结果保留原基底和完整 dirty 集。原生/特权、无法准备、采用失败、交易异常等不放开。
- 同时接入生产和区块验证。私有重试仍共用最初生产至多 50ms／验证准备 500ms 的绝对截止、64 轮发现额度及 4 MiB environment wire 额度；没有给每次冲突新开预算。已完成结果的正常采用仍使用原真实区块／交易限制，而不是追溯套用已经结束的私有准备时限。
- 生产回调新增存续的 order 指针。即使 expected slot 已经消费，回调或重入观察者再调用公开 `push_transaction`，仍关闭旧批次；公开 scheduled push 同样形成屏障。额外交易不冒充队列内一次回退计数。
- 新增本地计数 `prefix_refresh_requests`、`prefix_refresh_successes`。前者包括被剩余预算拒绝的刷新请求，后者仅表示取得新私有结果，不代表授权或正式采用；真正 worker 执行次数继续由 `attempts` 统计。冲突只记录一次。

不改变线程上限 16、共识／CPU/NET 计费／经济与治理规则；没有并发写 Chainbase，没有启用旧链兼容。

当前接线保留“只读预检查 → run_next 正式检查”两道边界，因此未冲突的后续候选可能重复扫描依赖。这是本阶段需要测量的 owner 成本，不能只根据多采用几笔结果就宣称 TPS 提升。后续若合并检查，需要保证检查后没有状态变更、结果替换、重入或取消遗漏，不能直接删掉正式检查。

初版编译期间发现的宽 catch 已按上述方式修正：不再把正式 callback 的中断异常当作提交前的普通停止。初版证据保持原样；新增中断测试已包含在上述专项及完整核心三轮中，不能用较早六项专项代替它。

## 测试范围

`parallel_validation_tests.cpp` 引入 `parallel_prefix_refresh_cases.hpp`。前六项已在初版运行，修正版追加第七项；均为真实控制器／WASM，用新创世 `initial_savanna.version = 2`：

1. 0/1/2/4/8/12/16 worker：A 改变 X，B 因新 X 将写入对象从 Z 改为 Y，C 使用新的 Y，独立 D 保留。比较本版本串行／并行验证的账本与原收据/trace，并核对只请求刷新 B/C。
2. 新分支在已写入后陷阱：B 全部撤销，D 按串行屏障继续，不采用旧 B。
3. 消费 expected slot 后再公开提交额外交易：即使后续交易独立，也必须关闭旧批次。
4. 私有刷新成功但签名错误：原授权仍拒绝，且停止尾部采用。
5. 在首笔生产回调中故意等待 70ms：真实区块时限未到，但冲突重试不能重置原 50ms 私有截止。
6. 初始发现恰好用完 64 轮后再发生冲突：验证端不能另获一批轮次，账本仍匹配串行。
7. 正式生产回调消费 slot 前／后主动中断并抛异常：必须向调用者传播，不能吞掉异常；新批次使用新 epoch 并正常恢复。

旧用例中“首次冲突后全尾部串行”的精确路由计数需要结合新行为逐项审查；不得批量删除断言、放宽账本／授权／收据检查，或把一般 host、JIT、容量、新节点与 TPS 验收算作本批完成。
