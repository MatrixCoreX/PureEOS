PureEOS 并行容量与 CPU 预算改进方案
日期：2026-10-19
状态：研究与离线模型第一步；不是新计费协议已上线，也不是正式容量已提高。

一、先纠正判断

累计区块总工作量并不过时。并行节点仍必须限制计算、网络和内存。
真正要改进的是：总容量如何匹配最低节点规格；热点串行工作如何受限；
用户资源账单如何与本机调度策略分开；减少并行准备和回退的重复计算。
本机 worker 数、CPU 核数、实测墙钟不应成为节点各自解释的区块有效性规则。

当前代码：
* config.hpp 默认 max_block_cpu_usage=200000 us，min_transaction_cpu_usage=100 us。
  正常每秒两个块，仅这项规则对最轻交易的理论上界约 4000 TPS；不是性能保证。
* transaction_context.cpp 的 apply_isolated_cpu_charge 把成功私有执行时间加入账单；
  resource_limits.cpp 的 add_transaction_usage 继续累计并限制区块 CPU。
* controller.cpp::assemble_block 把同一 max_block_cpu_usage 用于弹性账户资源参数。
  所以直接修改此值还会影响账户资源容量，不能把它当成纯本地装块开关。

这只是每模式一轮，未满足三轮稳定增益标准，也没有跑满 12 个逻辑 CPU。

以上数据不支持“再提高 CPU 额度即可解决”，也不支持“机器性能已经耗尽”。

三、优先顺序

A. 先解决现有执行器浪费，再提高正式容量。
   依据本批数据，优先原计划 R0/R1/R2：完整结果保留、减少缺状态重启、
   有界混合批宽和热点退避。12 SMT 不等于 12 个物理核；保留 4～16 worker
   的扩展接口，但批宽需依据实际工作成本，不以线程越多越好为目标。
   50ms 生产准备保护、500ms 验证准备保护、真实块截止和验证均不直接关闭。
   不在已冻结测试途中换二进制；新优化另建目录、同额度、同语料重测。
   本轮进一步定位到 controller.cpp::for_each_parallel_production_transaction：
   目前只有 homogeneous && workload 时才 observe 准备结果，异类混合批次不学习
   deadline 成本。不能把混合批的成本强行记到队首简单交易的形状键上；应补有界
   混合批成本分类、统计和保守取批，并测试动态配比/分支改变/恢复探测。
   此代码事实是优先调查点，不等于已证明本轮全部 deadline 都由它造成。

B. 近期安全扩容：链上统一容量档位，而不是跟随单机线程数。
   以最低支持硬件的完整验证、传播、最终确认和故障恢复能力选择档位。
   串行/并行使用同一档；增额度收益与执行器收益分开。
   高额度测试不是发布建议。不能在缺少热点保护时把总预算按核心数无限乘大。
   仍保护账户配额、最低/逐笔最大 CPU、NET、RAM、内联深度与租赁经济规则。

C. 中期：区分总工作量与最长依赖链，保留串行/未知操作预算。
   总预算限制整个块消耗，关键路径预算限制必须依次执行的计算，
   未覆盖的原生/特权/全局/范围副作用保守计为前后全部依赖的屏障。
   读读不相互依赖；RAW、WAR、WAW 都要覆盖，跨 X→Y→Z 的桥接依赖不能漏。
   简单按每账户单独限额仍可能漏掉跨账户长链，不能代替完整依赖核验。
   任何单个热点链和全串行块都不能借用“有很多线程”获得无界预算。

四、已实现的第一步及严格边界

tests/PerformanceHarness/parallel_budget_model.py：纯离线整数模型。
以抽象工作单位和抽象读写键计算总量、RAW/WAR/WAW 关键路径、未知屏障量；
64 位检查加法，限制每块/每笔键数、交易数，非法输入失败关闭。
无核心数/worker 参数，不访问节点、不写账、不替换现有 CPU/NET 检查。
test_parallel_budget_model.py：8 组，包括 1000 组固定种子随机语料与独立 O(n²)
依赖图算法对照。模型通过不证明真实读写覆盖、费用正确或 TPS 提升。
例：8 笔各 100 单位且独立，合计 800、最长路径 100；同一行 3 笔各 100，
合计 300、最长路径 300。数字是抽象例子，不是新的微秒额度。

五、正式底层接入前必须完成

1. 确定性工作计量，先观察不判块。
   不能把生产者填写的 receipt CPU 直接当作真实计算量证明，也不能把主观
   elapsed 除以线程数。研究 WASM 基本块计量 + 按字节/页/次数计的 host 成本；
   JIT/解释器、冷热缓存、软浮点、加密、memory.grow、通知、inline、sync_call
   必须给出一致规则。成本表和版本是全链统一参数，不由硬件跑分临时决定。
   成功语义路径只收一次；发现/冲突重试的白算作为本地保护统计，不能重复扣用户。
   WASM 指令计数不涵盖所有原生/数据库/授权成本，未覆盖项必须保守处理。

2. 在真实 canonical 路径完整捕获依赖。
   在 apply_context/host_context、transaction_state_view、原生系统处理路径
   核对主键、二级索引、范围/负查询、表结构、代码/权限、资源和协议依赖。
   串行及并行验证都能独立导出同样结果，不信任用户声明或仅成功采用的私有读集。
   账户资源累加/提交开销不能静默忽略；未证明可交换前不得当作独立操作。

3. 新链统一准入参数和检查。
   chain_config.hpp/.cpp、chain_config_helper.hpp、config.hpp：全链总量/路径/
   串行预算及验证关系，明确单位与版本。仅在新链创世采用，不做旧链迁移承诺。
   genesis_state.cpp/.hpp、global_property_object、序列化、snapshot/replay 与
   get_consensus_parameters：新节点/自身恢复一致，缺失/溢出/非法组合拒绝。
   controller.cpp、resource_limits.cpp、transaction_context.cpp：保留真实权限、
   资源账单和撤销；预算失败不得留下私有结果、计数、费用或正式写入。
   当前用户 CPU 资源账单与新装块工作预算分开审计，逐项列出账户配额影响；
   没有独立通过前，不删除既有 CPU 上限，更不绕过 validate_cpu_usage_to_bill。
   总量与关键路径预算须在最低配置上联合校准，还需预留正式串行提交、
   传播和最终确认开销。两个抽象预算各自通过，不保证某台机器能及时完成；
   上述 800/200 仅为算法示例，不能直接改成正式微秒参数。
   webassembly/privileged.cpp、系统合约 setparams/ABI：仅正确授权可改参数。
   参数授权与开发者合约升级/14 天公示/节点否决流程分别审计，不恢复节点治理。

4. 验收不止吞吐。
   独立、全热点、50/50、跨行桥接、读后写、删行重建、范围新增、权限/代码变更、
   原生/不支持操作、恶意低报工作量、内存和 NET 压力、失败撤销、abort、分叉、
   重启和重放；4/8/12/16 worker 及串行验证须得相同有效性和账本。
   在最低支持规格上确保最坏块可持续验证/确认。显式报告计量自身的开销。

六、参考，不照搬交易/收费格式

Solana 官方区分调度成本模型与执行计量，并保留区块及写账户额度：
https://solana.com/docs/core/fees/compute-budget
Aptos 官方描述计算、IO 和存储的资源计费，以及考虑冲突的交易排序：
https://aptos.dev/network/blockchain/gas-txn-fee
本文双预算与接入顺序是 PureEOS 的设计提案，不宣称它们已采用同一实现。

七、交付状态

完成：混合实链单轮对照；每逻辑 CPU/TID 占用证据；离线双预算算法及随机对照。
未完成：确定性实际工作计量、canonical 完整依赖、共识接入、正式容量选择、
三轮重复性能验收及真实多机最低配置验证。
结论：已开始合理改进，不把离线模型当成已经提高主网 TPS。
