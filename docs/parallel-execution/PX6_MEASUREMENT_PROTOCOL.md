# PX6 测量口径与受控启用门槛

状态：工具已实现、首轮工具烟测通过，正式重复测量与持续运行仍在进行。本文不宣称性能验收完成。

## 对照与负载

固定使用保留的旧串行二进制、新版关闭并行、新版 1/2/4 worker；均为 Release、eos-vm 解释器、完整验证、相同默认链上资源限额。所有模式开启相同的阶段计时，测试不禁用持久化、不跳过授权/undo、不扩大 CPU 或 NET。数据目录均新建，日志来自同一份签名区块，不另生成更有利于某模式的输入。

`parallel_benchmark_fixtures/export_fixed_replay_workloads` 通过显式环境变量导出四类语料，每类 32 个业务块、512 笔写状态交易，再补空块使业务全部不可逆：

- `independent`：16 个独立 scope/表，每笔固定 80,000 次解释器循环，更新已有行。
- `hot`：全部访问同一 scope/表；测量冲突后的串行尾部与无效试算成本。
- `mixed`：每业务块穿插两次原生 `setcode`，其中一半业务使用未准入的替换代码，验证串行屏障成本。
- `serial`：所有业务代码均不在本地哈希准入列表，测试原串行退化。

第一次导出 `px6-corpora-v1` 实际通过 4,341 个断言。此语料不是生产链的 EOS 转账、PowerUp 或 REX 性能模型；系统合约业务正确性由原回归另行覆盖。

## 统计与边界

工具在 `tests/PerformanceHarness/parallel_replay_benchmark.py`，复用独立进程测试的节点隔离与完整性验证。至少三次独立冷进程运行，并轮换每次模式顺序，保留所有样本、中位数、最小/最大值，不挑最好一次。计时前不强制清理系统页缓存，因此是冷进程而非冷存储测试。

原节点重放日志中的秒数为整数，小数 `ms/block` 使用 `head-start`（实际重放数量减一）作分母。工具按该源码公式还原微秒级耗时，并验证取整秒数一致性。另记录进程启动至 API 可用的墙钟时间，不能把启动成本偷偷扣成负数。

记录完整状态摘要、实际采用/回退数、阶段直方图、进程 CPU 累计时间、内核 VmHWM 峰值 RSS、主机 CPU/内存/负载。阶段时间包含嵌套和并行重叠，不能相加视作整块时间。RSS 不是磁盘数据库文件大小，也不代表 SSD 持久化性能。编译或其他压力存在时的首轮 `parallel-replay-benchmark-xjceu29a` 只用于检查工具链，不作为正式提升结论。

真实出块测试使用原 `finality_tps.py` 口径：唯一已发送业务 ID、成功 receipt、实际不可逆分支、固定观察窗，以及 P50/P95/P99 延迟。初始脚本为 8 秒；当前修正版为 14 秒，包含最多六秒的出块轮次对齐等待。每模式只发送 16 笔，是受控兼容负载，16/14 TPS 由输入决定，不是容量上限。默认出块提前量按整轮 12 个槽位累积，因此仅对齐半秒边界不能确保足够的并行试算窗口；对齐整轮不改变节点或链上限额。即使重放更快，也不能把该结果转换为生产者 TPS 提升百分比。

持续运行工具 `tests/parallel_producer_soak_test.py` 会在同一组长驻进程反复入队、恢复出块、达到暂停点、对照旧版验证者，记录每轮资源和状态。主动暂停间隔不算漏块，每个真实活动窗口逐槽检查；最终比较整个 SHiP trace/state 文件。测试时长以实际报告为准，不称几分钟本地运行已证明数月生产稳定。

## 事先约定的判断

1. 正确性硬门槛：零未解释状态/收据/资源/历史差异；失败、取消、恢复及线程检查无未处理错误。
2. 性能观察线：关闭并行及热点负载相对旧版中位吞吐退化以原计划建议的 5% 为线，低冲突需有可重复收益。超线如实记为性能门槛未通过，不修改输入、共识限制或失败预期来抹平。
3. 如果只有受限低冲突负载受益，而热点明显退化，交付可关闭的实验实现与适用边界，**不默认启用、不推荐全网部署**。更广泛准入及自适应策略另行审查，不从这些夹具外推任意 EOS 合约提速。
4. 原分支、旧程序和系统合约保留不动。所有实际运行结果、限制与关闭/恢复操作将在 PX6 总结中给出。
