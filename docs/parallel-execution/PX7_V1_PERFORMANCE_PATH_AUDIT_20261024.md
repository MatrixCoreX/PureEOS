## 代码确认的边界

1. **区块CPU仍按逐笔账单累计。** 采用私有结果时，`apply_isolated_cpu_charge`
   把成功私有执行的耗时计入原交易计时器，再经原资源管理器结算；没有按线程数
   除账单。失败的内部状态发现尝试消耗机器CPU，但不会累加成用户那笔成功执行
   的链上CPU账单。物理工作量与收据CPU不能直接画等号。
2. **默认参数只能推出理想持续上界。** 500ms/块、200000us/块、最低100us/笔，
   在普通成功交易都只付最低CPU、理想无漏块且没有其他CPU消耗时，最多2000笔/块，
   对应4000笔/秒的仅CPU预算长期上界。NET、隐式交易、状态处理、出块截止等仍会
   限制实际容量。这个式子不是实测TPS，不是当前机器的预测；积压释放造成的短窗
   最终确认速率也不能直接拿它作同口径比较。参数改变后须重新计算。
3. **当前N1提示不是任意新账号的通用预取。** key包含真实code、receiver、action、
   授权账号、数据长度和树/CF上下文。相同账号只改nonce可以复用路径；不同授权
   账号有不同key，首次出现的账号不能借用其他账号的key。不能把低业务冲突等同
   于没有冷启动和状态发现。
4. **提示容量有明确上限。** 当前默认256个key、每key最多32条路径；第33条不同
   路径使该key进入饱和状态，按设计停止使用部分提示，回到安全发现路径。它保证
   有界性，不能据此声称64个动态业务路径都会持续得到预取收益。具体语料是否
   触发饱和仍须实际观察，不单凭scope数量判定。
5. **N2已选择性重试，但无法消除首次缺状态的成本。** 每轮只把 `retry[i]` 的槽位
   再交给worker，已完成结果保留；第一次执行遇到缺失状态时，该笔仍需要补状态
   后重做。若重计算位于首次DB读取之前，这一成本尤其需要诊断。
6. **owner和会合屏障仍存在。** owner读取新鲜快照、worker执行并会合，随后owner
   按原交易顺序检查依赖、授权和提交。增加线程不能跳过这些步骤，平均批次很小
   也不能让配置的所有worker持续工作。

以上是当前代码路径的确认和条件性推断，没有把任一项直接判为当前TPS的唯一根因。
暂不调整路径容量、准备时限、区块参数或计费，以免在没有本候选性能证据时换掉
正在进行完整功能测试的版本。
