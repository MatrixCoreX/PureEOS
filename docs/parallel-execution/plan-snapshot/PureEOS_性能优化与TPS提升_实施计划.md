## 1. 目标和结论

目前有性能优化空间。优先方向是：建立准确的压测基线，减少重复序列化和无效状态写入，评估现有 WASM 优化执行器，控制交易/确认票队列，最后根据实测决定是否改造安全写盘机制。

这里的“提高 TPS”指：**在相同硬件、相同安全要求和相同业务负载下，每秒有更多成功交易获得最终确认，同时确认延迟、漏块率和故障恢复能力不退化。**

不是提高 RPC 接收速度就算完成，也不预先承诺提升几倍。当前已有测试是功能和故障恢复验收，还没有能够量化各瓶颈占比的原版/当前版对照压测。

建议推进顺序：

```text
P0 正确计量与基线
    ↓
P1 重复工作优化 + 配置与执行器对照试验
    ↓
P2 交易和确认票队列优化 + 系统合约热点优化
    ↓
P3 仅在写盘确为瓶颈时，改造持久化布局
    ↓
P4 全盘回归、重复压测和上线建议
```

## 2. 本轮不改变的规则

- 保留 500ms 时隙、现有生产窗口、最多 21 人在岗和正常一次顺序替换一人。
- 保留候选容量四年分段线性增长、一票一投、禁止代理投票。
- 保留满 21 人才按连续三个完整本人零产出窗口永久禁入、不满 21 人不永久拉黑的规则。
- 保留 100% 实际出块奖励、首次正票激活、四年减半，不改历史收益与资产保护。
- 保留直接质押加 REX 约 10%、其余 PowerUp 的资源权重规则及租赁业务。
- 保留开发者升级公示及否决制度，不恢复节点多签治理或人工准入。
- 保留 Savanna 验签、QC 门槛、分叉检查和崩溃恢复安全约束。
- 不强制全历史、不新增历史挑战，不自动更改裁剪配置。

不得用下列方式作为默认优化：关闭 `fsync`、清空 `safety.dat`、跳过 BLS/交易验签、使用 LIGHT/trusted-producer 绕过验证、降低确认门槛、单纯放大交易超时或取消磁盘保护。

真正的并行写交易执行已另立[多核并行交易执行实施计划](PureEOS_多核并行交易执行_实施计划.md)，不混入本计划既有单线程优化的完成状态。缩短出块间隔和修改链上 CPU/NET 限额仍属于单独的规则调整项目，不作为两个性能计划的默认实施项。

### 3.1 现有测试的边界

最近 22 进程测试使用完整 Release 构建，但 `ENABLE_OC=OFF`，不能再把“改成 Release”本身当作尚未完成的新优化。证据见 `PureEOS/build/local-tests/positive-vote-iinjKN/release-node-manifest.json`。

同批测试的数据目录重定向至 `/dev/shm`；它能验证运行流程，不代表真实 SSD 上同步落盘的性能。此前最高采样 100°C、head 与 LIB 最大采样差 757 块，证明本机满载存在问题，不证明问题全部来自某一项代码。亲和性实验未改善确认速度，不能把重复绑核作为已知修复。

当前机器为 i5-1130G7、4 核 8 线程；本次只读检查磁盘约 95% 已用、剩余约 8 GiB。后续大规模构建或压测前必须核实精确字节余量和保护阈值，不通过降低保护线来启动，也不擅自删除现有证据。

## 4. P0 先建立可信的性能基线

### 4.1 TPS 分开记录

至少同时输出四个量：

1. 发送 TPS：压测端实际发出的唯一交易数，不是配置的目标数。
2. 接收 TPS：节点接收/预执行成功的数量，仅用于诊断。
3. 入块 TPS：真实规范链区块中成功交易的数量。
4. 最终确认 TPS：固定真实时间窗口内，首次进入最终确认范围的成功、唯一业务交易数量。

主指标使用第 4 项，按交易 ID 和成功收据核对，排除隐式 `onblock`、重复发送、失败交易、仅 RPC 返回成功的交易、孤叉和压测准备交易。

交易内包含多个 action 时分别报告 TPS 和 actions/s，不能将十个 action 算成十笔交易。峰值一秒、持续吞吐和全程平均值分别展示。

### 4.2 统计必须覆盖漏块和最终确认积压

- 使用观察端单调时钟记录发送、首次入块观察、最终确认观察，输出 P50/P95/P99；保留轮询或订阅采样误差。不能把生产者声明的区块时间直接当成确认到达时间。
- 根据已最终确认的区块 ID、实际收据验证结果；一个高度发生分叉时不能沿用旧 ID 的结果。
- 固定测量窗口，保留窗口内的空块、漏块、掉线、排队和确认停顿。只按预先声明的准备/预热区间剔除数据。
- 测试结束后的排空阶段单独报告。不能把排空后才确认的交易补进原窗口分子，却不增加分母。
- 同时记录发送批次的最终完成率、失败/过期原因、排空耗时、待确认数量和队列增长趋势。
- 跨机器时记录时钟同步状态；端到端时延优先由同一观察端测量，避免直接相减不同主机时钟。

### 4.3 复用工具，但先修正口径

复用 `tests/trx_generator/` 的真实签名转账和定速发送能力，以及 `tests/PerformanceHarness/` 的运行与数据分析框架。新增 PureEOS 场景适配器，不让旧式启动脚本绕过本链的原生创世、正票激活、资源初始化和正常轮岗。

需要补齐：

- 按真实时间统计最终确认 TPS 的独立分析器和机器可读结果。
- 生成器自身落后、签名 CPU 饱和、网络背压的监控；生成器未达到目标时，该轮不能用来判定链的上限。
- 按比例和明确完成条件判定达标，不沿用“小于 100 TPS 误差”作为通用成功标准。
- 独立检查器通过原始发送记录、区块和收据重算结果；原有按两块窗口统计可以保留作兼容图表，但不再作为主验收指标。
- 测试账户正常获得 CPU/NET/RAM，有足够余额，遵守本链投票和 REX 约束。账户资源不足与机器执行能力不足分别统计，不把前者误报为 TPS 瓶颈。
- 大规模发送不要打印私钥或将测试密钥写入报告；只使用隔离测试链的可丢弃身份。

### 4.4 给瓶颈加观测点

复用 `plugins/prometheus_plugin/`，新增或扩充低开销计时指标：

| 路径 | 需要测什么 |
|---|---|
| 交易入口 | JSON/ABI 处理、解包、签名恢复、排队、重试、拒绝原因 |
| 状态执行 | 每笔业务/`onblock` 耗时、WASM 与 host 开销、数据库读取/写入、undo 开销 |
| 出块 | 有效执行时间、空闲时间、deadline 提前结束、组装、签名、广播 |
| 确认 | 票入队至处理耗时、队列长度、重复票、BLS 验证、QC 聚合、最终确认观察时延 |
| 持久化 | 恢复文件大小/数量、文件和目录同步耗时、等待锁时间、安全记录保存、恢复记录清理 |
| 主机 | 每线程 CPU、上下文切换、温度/降频、内存、页错误、磁盘延迟、网络及磁盘余量 |

指标不能按交易 ID、区块 ID 或无限增长账号集合创建标签，避免监控本身耗尽内存。精细 trace 仅短时抽样，正常压测不逐笔同步打印日志；另测开启监控的自身开销。

若 `perf` 等分析工具受限，采用已有计时和可用诊断替代，不自行修改系统权限、安全策略或内核参数。

## 5. P1 优先实施的小范围优化

### 5.1 轮岗上下文只构造一次

现状：`read_context()` 两次调用 `get_rotation_context_v1()`，底层两次复制列表并完整 `pack`。

拟改法：

1. 优先保留现有 WASM import 和序列化 ABI，底层按已执行父块 ID/必要上下文版本缓存不可变的打包结果；查大小和取内容复用它。
2. 若缓存的线程和生命周期成本高于收益，则对比无分配的长度计算与直接打包方案，依据微基准选择；不预先承诺缓存必然更快。
3. 缓存不得只按高度或当前时间索引。分叉、重放、快照恢复、换钥、新旧策略交接、abort/retry 都要验证；不能把可变的本地 QC/LIB 混进确定性上下文。
4. 缓存有明确大小和生命周期，禁止无限保存每个高度的上下文，也不能缓存错误授权状态。

主要文件：`PureEOS/libraries/chain/controller.cpp`、`libraries/chain/include/eosio/chain/controller.hpp`、`libraries/chain/webassembly/privileged.cpp`。合约 `rotation_state.cpp` 作为调用方测试，优先不改 ABI。

收益预期：减少每块固定开销，对单个普通转账的直接收益可能不大。需测 1、21 人及合法多密钥大上下文，不能恢复曾经会卡住合法策略的 64 KiB 限制。

### 5.2 轮岗状态处理减少重复工作

拟对 `rotation_state.cpp` 中同一调用内重复的成员列表构建、名称转换、候选行读取、策略 digest 计算做局部复用。

`common_members()` 使用的小集合最多 21 人；先测再决定是否引入额外集合/排序，不能因为理论复杂度就加入更贵的分配。

对单例写回增加精确变更判断或统一的保存出口，避免真正相同的状态再次写入；但必须保留：

- `last_slot`、窗口产出、待结算证据、队列游标、排名冻结状态、暂停代次及观察进度的全部必要变化。
- 每块排名/队列/窗口预算，不能通过提高预算隐藏更大的单块延迟。
- 所有早退分支的已发生修改，不能把“此块没换人”当成“状态没变化”。

实际多数块会改变时间或观察字段，因此“不写单例”的命中率可能很低。若为比较状态增加的序列化成本超过省下的写入，就不采用这项子优化。

### 5.3 全局单例与奖励策略的变更写回

`system_contract` 析构目前写回 global、global2、global3、global4。计划核查真正未变化的单例，考虑按单例保存初值或维护完整的 dirty 标记。

要求：

- 初始化时不存在的表必须按原语义创建；不能因为初始值与默认值相等就漏掉建表或改变 RAM payer。
- 遍历所有修改入口，包括动作中直接 `_global4.set()`、构造/析构、inline 调用、通知、失败回滚和奖励激活边界；不得漏写。
- 既有 `reward_policy` 已仅在变化时写回，保留其版本检查、首次正票激活和减半时钟，不删掉安全校验来省几条指令。
- 如果存在重入或多动作内共享状态，比较必须针对正确的数据库版本；不能用旧内存快照覆盖嵌套动作的结果。
- 只在收益超过比较成本时实施，优先范围小的单例，不一次重构整个系统合约。

这属于系统合约升级，虽拟保持业务语义和表 ABI，也要走既有公示升级流程；不是只换 nodeos 就生效。

### 5.4 构建和执行器对照

- 保留当前完整 Release 作为基线，核验 nodeos、BLS 库、合约 WASM 的编译方式和源码/依赖哈希，避免把 Debug/混合优化构建与 Release 混比。
- 单独构建 OC 可用版本，在独立测试链比较 `eos-vm-jit` 与支持的 OC tier-up 路径；覆盖 `auto` 与有必要时的 `all`，不使用源码明确标为开发用途的 `eos-vm-oc-forced` 作为生产方案。
- `ENABLE_OC=OFF` 的二进制不能只改配置就获得 OC。
- 分别测冷编译、热缓存、缓存淘汰、合约升级、编译失败回退和恢复；核实实际走的是哪条执行路径，不能只看配置字符串。
- 测试新增治理、轮岗 host intrinsic、OC 中断后事务重启与撤销、同步调用资源池、内存边界。此前构建警告和缺少 OC 实测的部分要明确核查。
- 默认不使用只适合本机 CPU 的不可移植发布选项；LTO/PGO 若尝试，单独成组，保留代表性训练负载与回归，不能代替业务优化。

收益未知；OC 对 WASM 计算密集业务可能有帮助，但不会自动解决数据库、写盘、BLS 或已经触及计费下限的问题。

## 6. P2 交易 确认和资源隔离

### 6.1 调整线程和节点职责

在相同硬件上用小矩阵试验 `chain-threads`、`vote-threads`、`net-threads` 与 HTTP 线程组合，记录争抢和排队。线程越多不必然越快；本机 22 进程的每进程配置不是独立服务器的推荐配置。

查询/API 节点与生产节点分工：高频表查询、ABI 编解码、历史读取尽量由独立 API 节点承担。此类节点没有备用出块奖励，也不新增治理权；属于服务职责分离。

只读线程只在源码允许的非 producer 角色启用，不放宽限制强行在生产者上并行执行只读事务。生产者必要诊断接口仍保留。

不默认改变账户主观计费、签名计费比例、队列上限或交易时限。每次配置变更都单独记录，区分“处理效率提高”和“限制放宽”。

### 6.2 交易预处理 缓存和背压

已有签名恢复线程池，应先测其利用率、等待时间与后续状态执行瓶颈，避免重复实现已有并行路径。

可选改造：减少同一交易重复解包/复制，复用已恢复密钥，合并同一在途交易的预处理任务，完善有界队列和反馈。

缓存必须绑定链 ID、完整签名/打包交易及验证上下文，不能只按不包含签名的交易 ID 就复用验签结果；授权结果还依赖链状态，不得跨权限变更盲目缓存。错误请求不能污染成功缓存，过期、fork、重试必须正确处理。

无效/超额流量要尽早受控，但保持正常来源的公平性。扩大队列只会延后过载，有可能增加内存和确认延迟，不算吞吐优化。

关联文件：`transaction_metadata.cpp/.hpp`、`transaction.cpp/.hpp`、`controller.cpp`、`producer_plugin.cpp`、`unapplied_transaction_queue.hpp`、网络和 HTTP 入口；具体路径见第 10 节。

### 6.3 确认票队列与 BLS

当前 `qc.cpp` 已在有效票聚合前检查重复票，并在同一票对应 active/pending 策略时复用本次验签结果。因此先统计：重复票是否主要消耗在线程池排队、未知区块等待、策略查找，还是实际 BLS 运算。

只有观测到相应占比后，才尝试：

- 对等待区块到达的票按 block ID 建立更直接的索引，减少新块到达时反复重扫不相关等待项；保留现有过期、LIB 清理、连接限额及乱序处理。
- 对在途任务做有界合并，并保持 block ID、key、strong/weak、签名、策略上下文等足够身份信息。未验证的伪造票不能占坑使合法票永久被丢弃。
- 分析 `notify_new_block()` 重复投递待处理任务的情况，必要时合并唤醒；必须测试 lost wakeup、关闭/启动和并发入队。
- 将关键票和区块传播与大批量历史同步、普通交易洪泛合理隔离；不能饿死换岗新人所需的同步，也不能擅自改变共识超时规则。

本轮不默认增加 BLS 批量验签，不改变曲线、签名安全检查或 QC 阈值。若密码学运算确为瓶颈，需要专项审查与恶意输入测试后另立子项。

### 6.4 普通交易和资源交易分开优化

普通转账应以 `eosio.token`、状态数据库和交易执行为主要观察对象；轮岗优化省的是每块固定成本，不保证转账 TPS 同比例提高。

REX/PowerUp/质押操作额外更新资源市场、票权和候选索引。只考虑合并同一动作内可证明冗余的读取/计算，不推迟必须即时生效的票权更新，不破坏租金托管账户或 10%/90% 约束。

业务“无变化”也不能直接跳过所有处理：零资源增量时可能仍有时间相关市场状态和合法性检查，需要逐条证明等价。

## 7. P3 安全持久化布局优化

### 7.1 为什么放在后面

目前恢复记录逐块创建文件并同步，安全文件也原子替换并同步，可能增加尾延迟。但每秒约两块，不代表一定需要大量 fsync 才能处理更多交易；块变大时的复制/校验/写入成本也要测。未定位前，不直接做高风险存储重构。

### 7.2 第一层 保持格式的小优化

- 恢复记录缓冲区一次预留容量，评估减少重复内存分配和数据复制；保留现有编码、校验值与落盘顺序。
- 分别计量文件同步、目录同步、加锁和恢复记录删除，不把它们合成一个无法定位的总时间。
- 已保存/已清理记录当前已有去重，不能把“再加一次 contains 检查”当作新收益。
- 分段退休与每 256 块清理的写盘顺序保持；测试清理突发是否需要有界处理，任何拆分不得先推进清理水位再确保持久性。

### 7.3 第二层 追加式恢复日志与有界合并提交

若真实 SSD 数据证明文件元数据或同步确为瓶颈，才设计版本化追加式恢复日志（WAL），减少逐块创建/rename，支持带校验的恢复记录、提交边界、轮换和索引。

允许评估自然并发写入的 group commit，但必须满足：

```text
区块及其必要祖先可恢复且已经持久化
        ↓
对应 finalizer 安全状态已经持久化
        ↓
才允许发送依赖这些记录的签名/确认票
```

- 每个等待者拿到的是已持久化的完成信号，不是“已进入后台队列”。异步并不意味着可以先发票再补写盘。
- 不为了凑批等待下一块或下一张依赖当前票的 QC，防止单节点创世及少节点死锁。
- 定义最大排队时延、大小、背压和失败路径。批处理可能降低吞吐成本但增加单块等待，必须同时看 TPS 和 P99。
- 不能仅按区块高度合并不同分支；必须覆盖被安全记录引用的完整依赖关系。
- 最终确认前不可丢弃仍可能需要的分支。旧恢复文件向 WAL 迁移采用可恢复流程，验证新记录持久化后才允许退役旧副本。
- 能明确判断为未提交的尾部记录才可按规则恢复；若涉及已发送签名所依赖的记录而发生缺失或损坏，必须拒绝不安全启动。
- finalizer 安全记录若增量化或合并，需要独立格式和顺序证明，保留 inactive key 历史安全信息；不能简单保留最后一个键或最后一条票。

优先只改恢复数据布局；安全文件格式改造是否值得做，要依据数据单独决定。WAL 不是已获准立即实现的必做步骤。

## 8. 链上限额与真正并行执行的后续边界

### 8.1 更快的代码不一定能突破计费上限

源码默认值为：500ms 时隙、每块 CPU 上限 200,000μs、每笔最小 CPU 100μs、每块 NET 上限 1 MiB。应在压测前读取测试链实际参数，不能把源码默认当成已部署参数。

仅按这些默认 CPU 数字，忽略其他消耗且每笔都只计最低 CPU 时，粗略计费上限是：

```text
200,000 / 100 / 0.5 = 4,000 笔/秒
```

这不是实测 TPS，也不是保证；系统处理、真实 CPU、网络、账户资源、最终确认等都可能更早成为瓶颈。源码旁边“10000 TPS equiv”等注释不能取代实际计算和链上参数。

如果优化后受最小计费或块上限限制，应报告“单笔成本下降、余量增加，但同限额 TPS 已封顶”。调低计费下限、提高块上限或改时隙会影响反滥用、资源经济、弱节点及网络传播，需单独方案和授权，不混入本轮同条件对照。

### 8.2 写交易并行不是增加线程数

当前交易可并行预处理，但状态修改依然有既定顺序和 undo/权限/通知/inline/sync-call 语义。

真正并行执行需要冲突检测、读写集、确定性提交、失败重执行、RAM/CPU 计费与交易排序方案。这不是本轮的小优化。2026-10-10 已根据代码另立[多核并行交易执行实施计划](PureEOS_多核并行交易执行_实施计划.md)：优先研究不改变区块格式与规则的隔离试算、按序提交，先验证区块，再推进生产者打包；若必须改变共识或计费规则，须另立协议升级事项，不能隐含在性能改造中。

## 9. 对照测试和验收方式

### 9.1 三组比较不要混淆

| 组别 | 用途 | 约束 |
|---|---|---|
| B0 原始仓库基线 | 解释已有改造的总体成本 | 原始基线已有 Savanna；使用双方支持的公共场景，不强行要求原版支持本链单节点创世或轮岗规则 |
| B1 当前完整工作区 | 本轮所有优化的主要参照 | 固定现有业务规则、构建、合约和测试配置 |
| B2 单项优化后 | 判断每个优化是否有效 | 一次只变一个因素，再测试组合；不能同时改硬件、限额、执行器和代码后把收益都算给代码 |

优先 B1/B2。构建 B0 时使用独立目录保留用户工作区，不执行 reset/checkout 覆盖现有修改。共同业务的旧激活条件、资源分配和生产者设置要显式完成并记录；不同经济模型或不同业务状态的结果不可直接声称严格 A/B。

### 9.2 负载矩阵

- 空块：测每块固定开销和稳定最终确认。
- 转账：真实签名的正常转账，分别使用少量热点账户与较多账户；不把空动作当作业务吞吐。
- 合约计算/表读写：选定固定输入和状态规模，测试不同计算及数据库比例。
- 投票：一票一投切换、票权变化、候选索引更新。
- 资源：REX 买卖/排队成交、CPU/NET 租赁到期/续租、PowerUp 及直接质押。
- 混合：预先固定业务比例，再加入正常查询及可控过载流量。
- 轮岗：1、4、21 席；22/23 个独立签名进程跨满员轮换；候选数据规模 210/420/840 另测，不冒称运行了同数量服务器。
- 故障：掉线、重启、真实 SSD 的 SIGKILL 恢复，确认停顿及恢复期间的吞吐/延迟另报。

稳态压测应开放环定速发送并记录背压，不能仅靠“收到上一笔响应才发下一笔”隐藏过载。负载从低档逐步增长，接近上限后缩小步长；数值依据基线制定，不先写一个宣传 TPS 目标。

### 9.3 时长和重复

建议起始方案：每档预热约 2 分钟、固定测量约 10 分钟，关键档至少重复 3 次，并穿插基线/优化版以降低温度和运行顺序偏差。长稳态和完整轮岗另测，不能把短微基准代替持续运行。

采用真实 SSD 的数据目录测持久化；tmpfs 只能作为明确标注的 I/O 排除对照。生成器、监控与节点争用同一机器时要单独报告；本机多进程不是跨机器网络验收。

温度、频率、内存或磁盘不满足预先约定条件时停止或标记该轮无效，保留完整记录；不自动关闭温控、改变功耗或降低安全保护线。

### 9.4 通过标准

1. 正确性、安全性和业务回归必须全部通过；任意不安全投票、状态不一致或历史收益损坏均否决该优化。
2. 同负载下最终确认 TPS 提升，或同 TPS 下 CPU/I/O/P99 明确改善；必须超过重复实验波动，报告每次结果及分布，而不是只选最好一次。
3. 不允许靠不断增长的队列维持表面吞吐，最终确认积压要稳定可控；发送失败和过期不能从报告中消失。
4. 小幅代码优化若受计费下限影响，应只报告微基准和资源余量收益，不冒称链 TPS 提升。
5. 不预设已经能提高 10% 或翻倍。显著性、尾延迟容忍范围和稳定窗口在 P0 后冻结，不能看完结果再调整标准让它通过。

对同一固定区块流，优化前后 nodeos 必须能独立重放并验证相同结果。系统合约代码变更后的独立实时跑链可能有不同时间戳、计费、代码哈希和区块 ID，不强行要求两条链 ID 相同；应比较声明的业务不变量，并各自完成无私钥独立重放验证。

SIGKILL 不能替代真实断电及设备缓存行为验证；涉及持久化格式变化时，软件故障注入与物理持久性验收分别报告。不能把 tmpfs 上的恢复通过当作 NVMe 掉电测试通过。

## 12. 阶段交付与决策

### P0 基线和瓶颈报告

交付可复现脚本、最终确认 TPS 统计器、现有指标与新增计时、环境和产物指纹、每个负载的瓶颈排序。没有可比数据时，报告限制，不进入“已提升多少”的结论。

### P1 低风险候选和配置试验

先做上下文重复构造优化；并行安排独立的 OC/线程配置对照试验，不混合收益。全局写回优化先完成全入口审查后再实施。每项给出收益、正确性和是否保留的决定。

这里的“并行安排”指独立工作项，可按机器资源顺序执行，不要求同时在当前笔记本运行多组重负载，也不默认启用多个开发代理。

### P2 按热点改造

只有瓶颈报告支持时才处理交易缓存、确认票等待队列、系统合约热点或网络隔离。已存在的优化不重复计功；没有显著收益的改动保留实验记录，不强行合入。

### P3 持久化专项

仅在 P0–P2 后仍由持久化限制且预期收益值得风险时启动。先冻结恢复格式、持久化顺序、迁移和降级边界，再做实现及故障注入。不得把关闭同步当作最终解决方案。

### P4 组合验收和交付

重复全套功能回归，运行关键负载持续压测、真实多进程轮岗和适当环境下的跨机器测试。输出：

- 当前版与优化版的逐项比较，不只给一个峰值 TPS。
- 各版本代码、未跟踪构建输入、合约、二进制、依赖与配置指纹。
- 原始发送/确认记录、资源曲线、失败和超时记录、独立核验结果。
- 哪些优化实际采用、哪些无收益或暂缓、哪些测试尚未覆盖。
- 原生程序更新与系统合约公示升级的分开操作说明；不自动部署到已有手动链。

## 13. 目前可以承诺与不能承诺的内容

可以承诺的是明确的优化路线和验收方法：先量准，再优先减少已观察到的重复工作，在安全约束下评估执行器、队列和磁盘布局。

目前不能承诺具体 TPS、提升百分比、21 进程在本机满载一定稳定，或者单纯增加线程/换执行器就能消除所有瓶颈。

建议最先开发的组合为：**最终确认 TPS 压测基线 + 轮岗上下文复用 + 关键路径计时。** 它能最快把“哪些地方看起来能优化”变成“哪些优化确实有效”的证据。全历史强制保存及存储证明继续不做。

## 17. 单线程路径优化第一批（2026-10-10）

按最新要求，暂不实施并行交易执行，先依据代码消除现有串行路径中的重复工作。容量结论仍须真实测量；本批不运行压测、不根据本机耗时推算服务器 TPS，也不以代码层面的拷贝减少量承诺 TPS 百分比。本批仅优化恢复记录的内存处理，**不属于更改 P3 磁盘布局、异步提交或减少同步次数**。

### 17.1 已修改的源码

`PureEOS/libraries/chain/reversible_recovery.cpp`：

- 写入前一次预留“文件头 + 已序列化区块 + 校验码”的完整容量，避免追加校验码时重新分配、复制整个记录。固定文件头在栈上序列化，不再单独分配链 ID 的打包向量；文件名的区块 ID 字符串只生成一次。
- 恢复读取先取得长度，在分配前检查原 v1 格式的大小范围，再一次读取完整字节，替代逐字节流迭代和向量反复扩容；短读、读取错误及追加尾部仍拒绝接受。
- 每个已读取区块的 ID 和高度保存为排序键，排序比较不再反复计算区块头哈希。排序仍严格按“高度、完整区块 ID”，代价是恢复期间增加少量每区块临时元数据。
- 写入侧也检查原读取端已有的 `UINT32_MAX` 完整记录上限，避免写出本版本无法恢复的超大记录。

保持不变：v1 文件格式、完整 SHA-256 校验、链 ID/文件名/尾部检查、互斥锁、去重和清理逻辑，以及 `write → flush → 文件同步 → close → rename → 目录同步 → saved` 顺序。没有修改交易执行顺序、资源计费、轮岗、奖励、共识规则或系统合约。写入优化作用于保存恢复记录时的内存处理；读取/排序优化主要作用于重启恢复，不能将其直接当成稳态交易执行 TPS 提升。
