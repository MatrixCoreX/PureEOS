## 1. 用普通话说明要做什么

现在可以有多个线程处理验签、网络和部分只读请求，但**普通交易修改链上状态的主要执行路径仍然按顺序运行**。增加验签线程，不等于多个核心同时执行多笔转账。

本计划的目标是：让多笔交易先在各自隔离的临时状态中同时计算，再按照区块原有顺序检查、写入正式状态。如果前一笔交易改变了后一笔交易依赖的内容，后一笔必须在正确的新状态上重新执行。

例如，区块顺序是 A、B、C：

- A 和 B 操作互不影响的数据，经过完整检查后，可以直接采用两笔并行计算的结果。
- C 要花 A 刚转入的钱，C 在旧状态上算出的结果不能直接采用，必须等 A 提交后重新计算。
- 即使两个转账账户完全不同，它们仍可能共同修改合约接收序号、授权序号、RAM 计费或表元数据；这些也要处理。
- 任何节点，无论开几个工作线程，都必须接受、拒绝同样的区块，并得到相同的共识状态。

最终希望提升的是**成功交易获得最终确认的吞吐量**，不是请求排队速度，也不是后台线程数量。

实施顺序：先改造状态访问和隔离基础，再试验“验证收到的区块时并行”，最后才试验“生产者并行打包交易”。第一阶段验证更快，不等于生产者 TPS 已提高。

## 4. 总体方案：隔离试算，按顺序提交

### 4.1 第一版采用分批冻结，而不是直接实现完整 MVCC

第一版建议使用**有界批次 + 稳定基础状态 + 每笔交易私有增量层 + 顺序提交**。

增量层（overlay）只保存这笔交易读取的依赖、创建/修改/删除的数据和待提交事件，不复制整份链数据库。工作线程不能直接修改正式 Chainbase。

```text
主线程：块首处理 / onblock / 必要串行交易
                 ↓
        冻结一批交易的基础状态 S
                 ↓
工作线程： T0 的私有状态   T1 的私有状态   T2 的私有状态
                 ↓ 全部退出本批执行区
主线程：按 T0 → T1 → T2 校验依赖并提交
        有冲突的交易在正确前缀状态串行重执行
                 ↓
        下一批 / 串行屏障 / 块尾处理
                 ↓
        原有收据校验、区块校验与提交流程
```

“冻结”是执行器生命周期保证，不是简单调用一次 `set_read_only_mode` 就完成。它必须阻止所有会改变基础数据库或相关可见状态的写路径，覆盖块中止、切叉、代码替换、快照和关闭流程。

本批工作线程全部结束并释放引用后，才允许主线程修改正式数据库。第一版不允许“一边保留指向旧 Chainbase 对象的引用，一边向同一数据库提交”。

该方案仍有批次等待和串行提交开销，但比一开始加入跨批多版本、版本垃圾回收、同时读写共享索引更容易建立正确性边界。只有测得这些开销成为主要瓶颈后，才另行评估流水化 MVCC。

### 4.2 不采用的捷径

- 不把现有 `controller::push_transaction` 直接投递给多个线程，共享数据库和 pending block。
- 不为每笔交易复制完整数据库；大链状态下内存、复制时间均不可控。
- 不靠“不同账号”“不同 scope”“用户申报互不冲突”直接放行。
- 不用全局大锁包住整笔交易后宣称已经并行执行；这样仍然只有一笔在实际运行。
- 不让工作线程自行抢全局序号、持久化对象 ID、区块剩余额度或回调顺序。
- 不将普通写交易伪装成 `read_only` / transient 交易来避开计费和状态检查。

### 4.3 第一版的最小成功定义

至少有一组正常写状态的交易，WASM 执行时间真实重叠，且多个交易的试算结果不经完整串行重跑便可按序提交；其收据和最终状态与参考串行执行一致。

如果所有交易最后都串行重跑，只能算“影子验证器/调试基础”完成，不能算并行交易能力或性能收益验收完成。

## 5. 状态访问与冲突检测设计

### 5.1 先建立统一访问边界

拟新增 `transaction_state_view` 接口，区分串行正式状态视图与隔离试算视图。第一步让现有串行路径通过它工作并保持行为不变，再接入并行。

至少覆盖：

1. 账户、代码/ABI 版本、权限和权限链接。
2. 主键表、表元数据和全部二级索引类型。
3. 授权使用状态、RAM payer、CPU/NET 用量与额度。
4. 交易去重、已知交易、过期/延迟交易相关状态。
5. 全局配置、协议特性、块时间及其他执行上下文查询。
6. action receipt 序号及所有原生调用可读写状态。

必须检索、分类所有 `db()`、`mutable_db()`、`get_index()`、`get_mutable_index()` 及管理器中的数据库引用。仅重载 `create/modify/remove` 不够，因为原始迭代器和对象引用可以绕过记录。

工作上下文不应随意取得可写 canonical controller/database。未完成适配的状态入口，必须在实际访问发生前中止本次试算，转入原串行执行，不能先修改正式状态再补救。

### 5.2 每次尝试要保存什么

| 数据 | 作用与要求 |
|---|---|
| 批次身份 | 父块完整 ID、待执行块身份、执行 epoch、交易顺序号、attempt ID |
| 固定执行上下文 | 块时间、协议特性、配置、运行模式等；只固定本批确实不可变的内容 |
| 点读取集 | 逻辑键、读取版本/存在性；不能只记录读到的值 |
| 范围读取集 | 索引类型、上下界、边界开闭、顺序和观测版本，或保守的整表/索引 epoch |
| 私有写入层 | 有序创建、更新、删除及必要前置条件；支持读取自己的写入 |
| 资源与收据事件 | RAM 变化、计费账户、序号需求、action 执行顺序，不提前改正式计数 |
| 私有输出 | trace、返回值、控制台、异常分类；不提前发布成正式结果 |
| 本地预算 | 增量字节数、读写项数、执行时限、取消状态、重试次数 |

版本号属于执行器内部数据，不增加区块字段。发生回滚/切叉后，即使同一逻辑键的值恢复相同，也不能让旧 attempt 凭过期版本通过；使用 epoch 和版本共同防止删除再创建、回滚等 ABA 问题。

### 5.3 必须记录“没有”和“范围”

| 情况 | 不能遗漏的依赖 |
|---|---|
| 查询账户、表或主键不存在 | 不存在本身是读取结果；前序交易创建它就应触发重验 |
| `lower_bound` / `upper_bound` / `next` / `previous` | 前序插入、删除可能改变返回项或空结果，需要检测范围变化 |
| 二级索引重复键 | 必须保持原有按二级键及主键的排序与定位语义 |
| 删除后再创建同一个键 | 不能只比较“当前值相同”，还要验证生命周期与前置条件 |
| 更新 RAM payer / 创建第一行 / 删除最后一行 | 涉及旧 payer、新 payer、表创建销毁、表计数等状态 |
| 权限树、链接权限改变 | 相同签名不能保证前后授权结论相同 |
| 同一合约更新代码后立即调用 | 后一笔必须使用前序提交后的代码、ABI/代码序号与权限 |

第一版允许使用较粗的整表/索引版本，宁可多重跑，不能漏冲突。后续优化为区间检测时，要单独证明不会漏掉范围中的新增记录（幻读）。

对私有层中的读取，应区分“读取本交易先前写入”和“依赖基础状态”；不能因为后来覆盖了一个键，就删除本交易早先对该键基础版本的依赖。

### 5.4 逻辑键、迭代器与对象编号

合约数据建议以 `(code, scope, table, primary_key)` 等逻辑键标识；原生对象按对象类型及自然键标识。不要让 worker 持有跨批次使用的 Chainbase 对象指针或 mmap 分配器对象。

现有 host 迭代器缓存包含原始对象/表指针，需改为本 attempt 所有的句柄。`end`、无效迭代器、删除后的引用以及同步调用广播失效行为必须有一致性测试。

正式对象 ID 由主线程按照原串行创建顺序分配，并修正私有对象间引用。必须覆盖“同一交易创建后删除再创建”、多类索引对象、异常撤销和 `_next_id` 恢复；不能只导出最后的行内容而丢掉会影响编号的操作顺序。

在编号重映射完成前，涉及尚未支持的创建/删除路径整笔串行回退。不能把随机或工作线程完成顺序分配的 ID 写入正式数据库。

## 6. 共享热点怎样拆，哪些不能硬拆

### 6.1 action receipt 序号

`apply_context::exec_one` 当前直接生成并追加 action receipt，其中包含：`global_sequence`、`recv_sequence`、`auth_sequence`、`code_sequence`、`abi_sequence` 和 action 摘要。

如果将整个账户元数据对象简单作为写冲突单元，同一代币合约的多笔转账会争抢接收序号，甚至所有 action 都争抢全局序号。

拟改造方式：

1. 按原执行顺序记录“需要生成哪一个 action receipt”的事件，包括通知和 inline 子 action。
2. 对确实只用于收据生成、执行期间不可观察的计数，延后到主线程顺序提交时分配。
3. 分配后再形成最终 action receipt 摘要和区块聚合结果，不能沿用带占位序号的摘要。
4. `code_sequence`、`abi_sequence` 与代码修改有真实依赖，不能作为可随意递增的独立计数处理。
5. 逐项检查所有原生/host 读取入口；若某字段可以影响执行，则记录依赖或将相关交易串行化。

“延后”必须以可观察行为等价为前提，不能仅因为一个字段很热就从冲突集中排除。

### 6.2 表计数、RAM 与授权状态

- 表 `count`、表对象生命周期和 RAM 费用经常相关，不能无条件当作可交换的 `+1/-1`。
- 同一 payer 同时增删行，要在正确前缀状态检查 RAM 溢出、下溢、配额和授权。
- `authorization_manager::update_permission_usage` 的状态还存在读取接口，不得未经审计直接移到最后。
- `resource_usage_object` 混合多类用量；字段级拆分需要证明其他读取不会依赖整个对象。
- 全局 pending CPU/NET 应顺序计入，并逐笔检查区块剩余额度，而不是批次全部执行后才发现超额。

第一版允许保守冲突和回退。是否做字段级拆分，依据“正确性已证明 + 确实形成热点”决定，不预先承诺普通转账一定无冲突。

## 7. 执行、提交、失败与生命周期

### 7.1 顺序提交算法

以下为设计伪代码，不是当前可调用接口：

```text
完成块首串行步骤
for 每个有界批次或串行屏障:
    屏障交易 -> 沿用原串行路径
    普通批次 -> 固定基础状态和 epoch，隔离并行试算
    等待本批全部 worker 退出并释放数据库/代码引用
    按区块内原顺序逐笔处理:
        若 epoch 失效 -> 丢弃整个旧批次
        若能力不支持或读取版本变化 -> 在当前正式前缀状态串行重跑
        否则 -> 在正式 transaction undo 内重放经校验的写入/事件
        按正确顺序完成授权使用状态、资源约束、序号、收据和回调
        失败按原交易类型处理，任何已写状态必须可撤销
完成块尾步骤，执行原有收据/区块校验及提交
```

第一版冲突后优先直接串行重跑，避免无限乐观重试；后期才研究依赖感知的小批重调度。写入重放不是仅将最后一份内存结构覆盖回库，而是保持必要操作顺序、约束、对象编号和 undo 行为。

### 7.2 异常分类

必须分清三类结果：

- **状态过期或能力不支持**：不是非法交易，转入正确前缀的串行执行。
- **本机取消、超时、内存不足、线程故障**：不能仅凭试算失败宣布收到的区块违反共识；按原验证路径与本地故障策略处理。
- **正确前缀上确认的协议异常**：沿用原逻辑决定拒绝交易/区块及 rollback。

一笔在旧余额上执行失败的交易，可能在前序转入后成功；不能将旧状态上的异常直接当成最终结论。反过来，旧状态试算成功，也不意味着当前前缀仍可通过。

发现串并行结果不一致、未跟踪状态访问或不可能的内部状态时，测试必须失败并保留证据；生产试点应停用该并行路径并告警，不能静默忽略差异继续宣称验收通过。

### 7.3 undo 与区块级原子性

- 保留每笔提交的 transaction undo 和整个区块的 block undo。
- `transaction_context::reset` 涉及资源、trace、receipt、计时器和升级临时授权等，重试必须全部清理。
- 私有层也要具备与当前路径一致的事务/嵌套调用状态语义；不能假定返回错误就一定与异常有相同撤销行为。
- `skip_db_sessions` 的快速回放模式需单独处理。初期禁用其并行入口或强制建立必要撤销边界，不能在没有撤销能力时尝试部分提交再回退。

### 7.4 切叉、关闭、读写窗口与缓存

建立统一生命周期：`创建 epoch → 派发 → 取消或收集 → 全部 worker 静止 → 提交/撤销 → 释放`。

块中止、分叉切换、重放重置、快照、数据库关闭及代码缓存淘汰，都要先使相关 epoch 失效并等待引用安全释放。旧 future 完成后只能丢弃，不可向新 pending block 回填。

不得在线程仍运行时销毁 controller、解除映射数据库或强行回收 WASM 模块。取消采用受支持的检查点/计时器机制；长交易和不可及时取消路径必须有测试及上限。

Savanna 当前接收路径包含执行前的区块头/QC 处理与投票考虑步骤，并不是所有签名都统一等待全部交易执行结束。并行项目必须逐点保留这些既有安全边界和恢复记录先后关系；不能凭直觉将其全部挪到执行后，也不能让 worker 提前触发投票或改写 finalizer 状态。

普通交易 worker 与已有只读执行窗口先互斥运行，不在第一版引入三套状态视图同时活动。保留网络/确认处理需要的 CPU 和调度机会，不能以无限等待一个批次拖住出块截止。

## 8. 哪些交易先支持，哪些先串行

### 8.1 起步范围

先用已审计的测试合约代码哈希，验证“已存在行上的独立读写”和无外部副作用的计算。代码哈希范围仅是实验启用条件，不是生产链新增合约准入权力。

逐步扩展至主键增删、二级索引、普通代币转账、通知和 inline。每扩一类，必须补相应访问记录、回退路径和串行差分测试。

不能仅静态看外层 action：通知/inline 可能调用任意已部署合约。运行途中发现未支持调用时，整笔私有尝试作废，在其正确顺序位置串行执行；原交易不能被拆成部分并行提交、部分串行提交。

### 8.2 第一版屏障清单

| 类别 | 处理原则 |
|---|---|
| `onblock`、过期清理、块尾资源处理、生产者/finalizer 策略更新 | 固定块首/块尾串行屏障 |
| 原生 `newaccount`、`setcode`、`setabi`、权限及权限链接修改 | 整笔串行；避免代码、对象和授权跨批变化 |
| 原生升级治理、一次性升级能力、相关系统合约升级动作 | 整笔串行，保持公示、否决、授权校验及能力消耗原子性 |
| 系统参数、协议特性、资源额度、特权状态修改 | 串行屏障；更新后重新形成下一批上下文 |
| 系统合约投票、轮岗、REX、PowerUp、奖励及 RAM 交易 | 初期保守串行，后续按真实读写依赖逐项开放，不改变经济逻辑 |
| scheduled/deferred 交易及 `onerror` 等特殊收据路径 | 先沿用原 `push_scheduled_transaction` 处理；普通输入禁延迟不代表历史回放路径可删 |
| sync-call | 首版回退；其返回值、写入、异常、只读传播和迭代器失效语义完成审计后再开放 |
| 未支持 intrinsic、原始数据库访问或执行器模式 | 整笔串行回退，不能拒绝本来合法的交易 |

现有 sync-call 的 RAM 处理含待调查注释。本专项先复现当前串行行为，不借并行改造悄悄改变计费；若确认旧逻辑有独立缺陷，应另列问题及修复验证。

## 9. CPU/NET/RAM 计费与出块截止

### 9.1 先做区块验证的原因

`controller::apply_block` 当前将收到的 receipt CPU 作为显式计费值传入。验证阶段交易顺序和收据已确定，适合验证状态隔离与提交是否等价。

并行验证仍需检查交易/区块 CPU、NET、RAM、权限、收据状态及最终区块结果。不能因 CPU 已由生产者填写就跳过限额或其他验证。

### 9.2 生产者阶段必须单独完成的设计

当前非显式 CPU 计费使用经过现有计时调整的时间差，不是确定性的指令 gas。并行增加排队、争用、冲突重试和提交等待后，不能原样把一切等待时间算入用户 CPU，也不能任意扣掉原本应计费的执行成本。

生产者试点前必须写出并测试：

1. 入队等待、有效执行、冲突后重跑、顺序提交四部分怎样计时。
2. 如何保留最低计费、账户额度、块额度及原有主观/客观限制。
3. 哪些内部试算成本只计入节点运营指标，而不重复向交易记账；最终计费规则须兼容现有验证。
4. 同一笔交易重试后只能形成一次正式用量和收据；不得重复扣 RAM/CPU/NET。
5. 到达出块截止时停止接收新批次，取消或丢弃未采用的私有结果，保留组块/签名/持久化时间。
6. 收据未接受前不向 RPC 返回正式成功；未收录交易按既有队列语义处理，不丢失、不双提交。

若这套设计不能保持当前协议兼容，停留在并行验证阶段，另提计费升级方案。**不默认改为“多个核心 CPU 用量取最大值”或“CPU 限额乘核心数”。**

即使执行更快，也可能受区块 CPU 总额度、NET 或最低交易计费限制；本专项不自动放大链上限额。

验证端的同一固定区块应得到完全一致的共识结果；生产者在不同运行时长下形成的计费值可能不同，不能要求两次独立打包的块字节天然相同。生产者阶段的关键验收是旧串行程序可以完整验证其区块，且没有规则越界。

## 10. WASM、线程池和外部输出

### 10.1 WASM 执行器

起步使用已验证构建路线中的非 OC 执行模式，单独初始化每个 worker 的 TLS、transaction timer、WASM allocator 和调用资源池。不得依靠只读线程曾经使用过这些对象就判定全部安全。

检查编译模块可共享部分与实例内存、栈、运行上下文的分离；审计缓存插入、最后使用高度、LIB 淘汰、代码替换和异常退出的引用寿命。

OC 的异步编译完成逻辑涉及执行中代码及主线程计时器。支持并行 OC 前，必须将中断关联到正确 worker/attempt 并验证取消竞态；未完成时关闭该并行组合或回退串行，保留原串行 OC 能力。

性能 profiling、调试回调和 JIT/OC 混合模式分别验收，不能用一种模式的通过结果覆盖所有执行器。

### 10.2 线程与内存预算

新执行池与签名恢复、P2P、BLS/确认、RPC 及现有只读池共同规划。配置上限是节点本地运行参数，不写入共识，不根据完成顺序改变区块顺序。

同时限制交易数、输入字节、增量总字节、单笔读写项数、trace 字节、活动 WASM 实例和全局待执行批次数。触及本地优化预算应缩批或回退，而不是将协议允许的大交易判为非法。

首先测试 1、2、4 个 worker；4 是实验点，不表示本机适合长期开 4 个，更不是默认开启所有逻辑核心。小区块/高冲突区块应能直接走串行，避免付出无效并行开销。

### 10.3 输出和插件兼容

试算结果不能直接触发正式 `applied_transaction`、RPC 成功、state-history/trace 消费或会影响外部系统的插件事件。控制台及调试输出需区分试算日志与正式执行日志，不能重复冒充交易执行成功。

主线程按原顺序、原 rollback/可逆块语义发布正式输出。现有信号有的发生在最终块提交前，应保持其既有语义，不是把所有信号统一移到最终确认后。

因此需要审计信号订阅者和 Deep Mind 日志，不只检查数据库相等；时间耗时等本机诊断字段可以不同，但业务返回值、事件顺序和共识字段必须一致。

## 12. 分阶段推进与停机线

阶段编号使用 PX，避免与总计划 P0–P4 混淆。每阶段分别提交变更清单、测试证据和未解决项；不能以“后面再补测试”为理由跨过关键关卡。

### PX0：访问清单与可行性收敛

- 列出所有数据库/管理器/intrinsic 入口，包括原始索引访问及隐式写入。
- 对每个入口标记：固定只读、需跟踪的读取、私有写入、提交事件、串行屏障或暂不支持。
- 审计序号是否可观察、ID 是否可映射、权限/RAM 是否能隔离、WASM 缓存是否能安全固定。
- 保存当前串行源码与二进制基线，建立固定区块语料和比较字段清单。

完成标准：入口分类无“默认当作安全”的遗漏；有可执行的最小隔离路径设计。如果必须大改协议或没有可用隔离边界，交付阻碍报告，不能直接共享数据库开多线程。

### PX1：串行状态视图与独立参考执行

- 新接口先只连串行实现，worker 数仍为零。
- 建立两个独立 controller/数据库：旧串行参考与新接口版本执行同一语料。
- 比较收据、持久化对象、资源状态、快照/完整性摘要及输出语义。

完成标准：默认串行运行无功能回归；未走新接口的路径均已识别并被安全隔离；保留旧二进制作外部参考，防止双方共用新错误。

### PX2：隔离层与并行最小闭环

- 支持已审计测试合约；实现稳定基础状态、私有读写、容量限制、epoch 和取消。
- 先跑单 worker 隔离再提交，证明 overlay 自身正确；再跑 2/4 worker。
- 完成最小序号事件处理、必要资源结算和按序提交；无法支持的操作按正确位置串行回退。
- 加入 native 模块的 race/lifetime 检查和异常注入。

完成标准：达到 4.3 的真实并行写入定义；已支持操作无正式状态逃逸；所有未支持操作完整回退；失败、取消不泄漏状态/线程/实例。

### PX3：离线区块并行验证与差分

- 接入 `apply_block` 实验入口；完整保留交易顺序、显式 CPU、收据状态、区块 ID 等验证。
- 串行和并行使用独立数据库；按完全相同区块流运行，不复制一边的执行结果替另一边执行。
- 覆盖普通交易、混合屏障、非法区块、回放和分叉；检查每一块而非只比较最终余额。

完成标准：第 13 节关键矩阵通过，至少三次独立重复；1/2/4 worker 同结果；改变调度随机种子仍同结果。此阶段不宣称生产者提速。

### PX4：真实进程验证节点试点

- 独立本地链/观察验证节点接收串行生产者的区块，启用完整验证，不信任生产者跳过检查。
- 与纯串行节点比较链 ID、块 ID、LIB 对应区块、状态与资源统计，测试重启/重放/切叉/快照。
- 验证只读窗口、代码缓存淘汰、限内存与本地超时回退；默认仍关闭并行。

完成标准：真实 nodeos 的兼容和故障测试通过；出现差异可关闭功能并恢复串行重放；没有破坏 finalizer/recovery 顺序。单机多个进程只证明其实际覆盖项，不当作真实多机容量结论。

### PX5：生产者并行打包实验

- 单独评审并实现第 9 节计费方案。
- 按受控入队顺序冻结批次，不能按 worker 完成先后直接决定提交顺序；交易顺序仍不新增共识要求。
- 实现出块截止、背压、队列重投、部分批次未采用和冲突退化。
- 由此前串行 nodeos 验证并行生产者产生的区块，并反向验证混合节点链。

完成标准：资源、计费、回调无重复，未采用结果不泄漏，旧程序正常验块；漏块/最终确认不恶化。计费或生命周期未解决时不得开启本阶段。

### PX6：性能、长期稳定性与受控启用

- 以相同硬件/限额/执行器/合约和交易序列，对比当前串行版本、带新接口但关闭并行版本、开启并行版本。
- 执行低冲突、高冲突、系统混合和故障场景；记录纯串行退化成本。
- 输出适合/不适合的负载、线程建议、峰值内存、限制和关闭操作。
- 只有正确性及安全门槛全部通过，且目标负载确有收益，才讨论扩大适用合约和默认启用。

后续完整 MVCC、流水化重试、并行 OC、复杂 sync-call 支持均为独立扩展，不以“第一版已完成”为由省略验收。

## 13. 测试计划：不仅测余额

### 13.1 串行参考与比较内容

同一固定区块流至少比较：

- 交易接受/拒绝、receipt status、CPU/NET 及 action/通知/inline 的顺序。
- action receipt 的全局/接收/授权/代码/ABI 序号、返回值参与的摘要和区块聚合结果。
- 交易根、对应区块类型的 action/finality 相关摘要、重新计算的 block ID。
- 所有共识相关数据库对象、对象 ID/引用、资源用量、权限状态、交易去重状态及 undo 后状态。
- 快照恢复、相同分叉选择结果和同一高度已最终确认区块的一致性。
- 正式 RPC/插件输出次数与顺序；本机耗时字段单独比较，不要求不同机器时间一致。

优先复用现有快照/完整性工具，再补未覆盖状态。新增本地比较摘要不表示新增链上状态根字段；不按原始 mmap 地址/空闲内存字节判断共识相等。

### 13.2 必测矩阵

| 编号 | 场景 | 必须证明 |
|---|---|---|
| T01 | 1/2/4 worker，打乱线程完成顺序 | 相同固定区块的结果、序号、资源一致 |
| T02 | 独立余额转账、独立行计算 | 存在真实执行重叠，部分试算结果可直接采用 |
| T03 | A 转 B、B 再转 C；同余额重复扣款 | 后序读取前序结果；不能双花或错误拒绝 |
| T04 | 全部交易写一个热点行 | 安全退化、重试有界，无活锁和内存堆积 |
| T05 | 读不存在的账户/表/行，前序创建 | 正确识别否定读取失效 |
| T06 | 范围查询、空范围、首尾迭代，前序插入/删除 | 不漏幻读、边界变化或索引排序变化 |
| T07 | 所有二级索引类型、重复键、删除后重建 | 与原串行索引及迭代器行为一致 |
| T08 | 创建/删除/再创建、跨表 ID 引用、撤销后重试 | ID 顺序、表计数、引用及 `_next_id` 正确 |
| T09 | payer 变更、相同 payer、RAM 临界值和溢出 | 不漏扣、不重复、不越额，失败恢复 |
| T10 | 相同权限使用、前序修改权限/链接/代码/ABI | 正确授权、执行正确代码，序号正确 |
| T11 | 多层通知/inline，跨合约写入及异常 | 整笔原子性；动态不支持入口完整回退 |
| T12 | sync-call 成功/错误返回/异常/只读传播/迭代器失效 | 首版回退正确；扩展后与当前串行语义相同 |
| T13 | CPU 最小值、账户/块 CPU/NET 临界值 | 按序结算，不能将多个核心用量视为免费 |
| T14 | 试算失败但前序补余额后成功；反向情况 | 试算异常不是最终合法性结论 |
| T15 | 重复交易、过期/TAPOS、特殊/延迟交易收据 | 保留去重及原验证/错误语义 |
| T16 | setcode/升级治理穿插普通交易 | 屏障有效；14 天、公示否决、一次性能力不被绕过/重复消耗 |
| T17 | onblock、1→21 增长、21/22+ 轮岗及故障窗口 | 最多 21 人、单席位替换、满员黑名单与低于 21 例外不变 |
| T18 | 排名增长边界、一票一投、REX、资源、奖励 | 线性扩容、10%/90%、出块奖励及四年减半等现有规则不变 |
| T19 | 批次中 abort、切叉、旧 worker 延迟返回 | 旧 epoch 永远不能写入新分支或污染新 trace |
| T20 | 代码缓存淘汰、LIB 前进、关闭/重启/快照 | 无悬空引用、无退出挂死；状态可重建 |
| T21 | 超时、OOM、增量/日志上限、worker 取消 | 本地资源故障不被误判为共识无效；回退/停机可控 |
| T22 | 收据/区块摘要/签名等被篡改的区块 | 串行拒绝的区块不能因并行被接受 |
| T23 | RPC、trace、state-history、Deep Mind、控制台 | 无丢失、重复正式输出或顺序颠倒 |
| T24 | 正常退出、强制终止、恢复记录故障点 | 保留现有恢复/签名安全边界，不把未安全保存的状态当可恢复 |
| T25 | 新并行生产者 + 旧串行验证者，反向及混合网络 | 无协议格式变化，能完整互验及切换回串行 |
| T26 | 开关指标、关闭并行、支持/不支持混合交易 | 观察不改变状态；默认行为与串行基线兼容 |

随机差分测试固定并记录种子，生成读/写/删除/范围查询/权限变化组合；发现失败要保留可最小复现区块和前置快照。每个关键场景至少独立重复三次，不能把重复运行累计成不同用例数。

ASan/UBSan、可适用 native 模块的 TSan/竞态检查分别记录覆盖范围。JIT 或第三方库不支持某检查时要明示，不能将跳过描述为通过。

进程强杀不等于物理断电；controller 模拟集群不等于真实 P2P 多节点；短时冒烟不等于长期容量验收。

## 14. 性能评估与验收口径

### 14.1 先依据代码判断收益条件

潜在受益：执行计算较重、依赖较少、批次足够大的普通合约交易。

收益可能很小甚至变差：小区块、同一热点余额/表、系统合约串行操作占比高、频繁代码/权限修改、RAM payer 高度集中、磁盘/网络/确认已是瓶颈。

粗略时间组成是“块首尾串行工作 + 每批最慢试算 + 依赖验证/有序提交 + 冲突重跑 + 组块/持久化/确认”。这只说明影响因素，不是 TPS 数值预测；CPU 核心翻倍不代表吞吐翻倍。

### 14.2 必采指标

- 已最终确认成功 TPS、失败/过期/重复率、P50/P95/P99 提交至最终确认延迟。
- 已验证块/秒、每块验证耗时与峰值；明确与生产者 TPS 分开。
- 并行可用交易比例、直接采用比例、冲突比例、串行回退原因、重试耗时。
- 每批排队/试算/等待/验证/提交/重跑耗时及批次大小。
- onblock/组块/写盘/确认耗时，漏块率、LIB 积压和确认票队列延迟。
- 峰值 RSS、overlay/trace/代码缓存字节、活动实例、CPU 使用和内存分配成本。
- 新接口关闭并行时相对原串行基线的退化量，高冲突时的最坏退化量。

指标标签要有界，不以交易 ID、账号或每个逻辑键生成无限标签。测试输出记录具体样本即可。

### 14.3 验收与报告

正确性要求是零未解释差异；不得用平均性能收益抵消共识/恢复错误。性能报告至少有纯串行、支持并行的低冲突、高冲突和系统混合四类负载。

建议在正式测量前冻结门槛，例如串行关闭模式和高冲突自动退化模式的吞吐下降不超过 5%，确认尾延迟/漏块不超既定预算；**5% 是拟议工程门槛，不是当前测得结果**。短样本噪声较大时延长测量、重复并报告波动，不能挑最好的一次。

只在实测后报告提升比例；验证加速、生产者打包加速、最终确认 TPS 三项分别列出。没有收益时允许保留实验功能默认关闭，或撤回引入额外复杂度的部分。

## 15. 本地配置、部署与回退

### 15.1 拟议运行模式

以下为拟新增本地配置概念，当前不可直接作为 nodeos 参数使用：

| 模式 | 行为 |
|---|---|
| `off` | 默认；原串行执行路径 |
| `shadow` | 独立状态实例上比较串行/并行，正式结果仍来自串行；初期仅离线测试工具支持 |
| `validate` | 对收到的区块使用已验收并行路径，不启用生产者并行打包 |
| `produce` | 生产者实验模式；只有 PX5 验收后可启用 |

建议参数职责包括 worker 数、批次交易/字节上限、overlay 总预算、试算时限、输出预算和允许的实验能力集。具体 CLI 命名与默认数值在实现时确定，不在计划阶段假装已有开关。

切换模式应在安全块边界、所有 worker 结束后进行；首版可要求停机重启，不必为了热切换扩大复杂度。旧版本不认识新配置项，回退到旧程序时使用原有配置副本。

### 15.2 本地实验安全边界

全部实验使用独立目录和端口，不覆盖：

- `manual-block-rewards-20261008/`
- `manual-test-chain/`
- `manual-reward-chain-20261008/`

先小规模隔离测试，再按资源预算增加 nodeos 进程。正式容量测试沿用总计划的磁盘/内存/环境记录要求；笔记本能验证逻辑，不据其成绩推算未来云服务器 TPS。

不为本项目自动删除历史数据、缩分 Windows 分区、修改内核热保护或改变共识安全配置。用户此前单次编译允许仅记录温度，不自动扩展为所有长期压测的温度策略。

### 15.3 回退原则

overlay、读写版本、调度队列均为本地易失状态。关闭并行后沿用原块/快照/状态恢复路径，不需要重新创世或迁移资产。

必须实际验证：并行生成的合法区块可由旧串行程序重放，当前数据库/快照可按既有兼容规则恢复。如果实现意外要求持久化 schema 变化，先停止兼容上线承诺，补迁移与回退方案。

保留基线二进制、配置和测试快照；发现一致性故障时隔离该节点、保存证据、从可信状态串行恢复。不能仅关闭开关后继续使用可能已被错误提交污染的状态。

## 16. 当前结论与待完成清单

代码层面结论：**可以立项研究隔离式多核执行，但当前数据库、host 接口和提交链路不能直接安全地多线程写入。主要工作在原生 `nodeos`，不是只修改系统合约。**

首选路线是分批稳定状态上的试算、完整读写依赖检查及原顺序提交。并行区块验证先行；生产者计费、截止和输出语义单独过关。系统合约和现有治理/资源/奖励规则保持不变。
