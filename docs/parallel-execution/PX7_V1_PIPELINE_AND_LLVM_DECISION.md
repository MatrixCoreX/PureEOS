# 首版边界：跨批流水线与 LLVM 迁移评估

日期：2026-10-22。结论是**本首版暂不引入**，不是声称两个架构已经开发完成。
当前首版仍需最终同版本的功能、恢复、多节点与性能门槛，不由本决策豁免。

## A1：先保持有界 joined 批次

代码依据：

- `controller.cpp::prepare_isolated_attempts` 在每一轮状态捕获后调用
  `isolated_worker_pool::run`，全部任务完成后才在 owner 上补取缺失状态。
- `parallel_worker_pool.hpp` 的 `run` 返回整批结果；输入、取消和工作线程寿命
  目前以这个同步边界为准，不允许未完成任务带出控制器引用。
- `parallel_state_overlay.hpp::frozen_primary_capture_session` 仅在同一未变更
  正式前缀中复用捕获值。owner 提交、回滚、分叉后必须新建捕获 session。
- `parallel_ordered_batch.hpp` 的 ticket/preparation 绑定快照及提交前缀；当前
  冲突刷新不是把旧结果改个标签，而是从新的实际前缀重新准备和执行。

这里有两个不同的后续方向，不能混称“再开线程”：

1. 批内流式完成：后面的 worker 继续执行时，owner 提交已经完成的连续前缀。
   理论上不要求 worker 写正式数据库，但必须重新设计输入寿命、旧快照依赖、
   访问缺失补取、回调重入、错误撤销和取消后的全量 join。当前代码不能仅把
   `run()` 改成不等待，就得到安全流水线。
2. 跨批流水线：新批捕获、旧批提交、工作线程执行重叠。若捕获继续读取实时
   Chainbase，就不能与正式写入无保护重叠。需要显式的状态版本/读屏障或
   多版本状态，并分别约束跨版本依赖、代码切换和峰值保留内存。

后续原型的最低验证矩阵：连续前缀先完成/后完成、首笔失败、中段授权/RAM
失败、缺失状态转到新前缀、inline/通知/同步嵌套、重复结果、切块/中止、分叉、
停机时仍有任务及极慢尾任务。必须保留原签名、资源、撤销和最终确认语义。
不得通过 detach、共享 VM 或并发写正式数据库，掩盖这些寿命问题。

本首版先评估 N1 的发现轮次减少及 N4 的小批唤醒；没有证据证明流水线是达成
当前首版门槛的必要条件。A1 在本轮以“评估完成、实现暂缓”跟踪。

## A2：不把宿主升级等同于合约编译器升级

本地 CDT 源码的构建入口仍区分专用 `cdt-llvm` 和宿主编译器：
`modules/ToolsExternalProject.txt` 传入 LLVM 源码和构建目录；
`modules/InstallCDT.cmake` 包含 `clang-9` 安装项；
`tools/include/eosio/abigen.hpp`、`codegen.hpp` 参与 ABI 和合约代码生成。
因此，节点在较新 Ubuntu/GCC 上构建，并不表示 CDT 已迁移到现代 LLVM。

首版选择：固定已经实际验证的专用编译器，单独标明修改后的 SDK/运行库来源。
头文件和默认 WASM 轻量分配器已重编与测试；这不是 LLVM 全源码迁移成功。
不能把 SDK 加固包继续标成未经修改的官方预览安装包。

未来迁移必须独立验证：

- Clang AST/属性处理与 ABI 输出，特别是模板、继承、bool、容器及同步调用。
- 专用代码生成/SoftFloat pass、linker、内建函数、libc/libc++ 和默认运行库。
- 生成 WASM 的导入、指令及内存能力，是否被当前正式 VM 和私有解释器/JIT
  支持。不能仅凭新版工具链能编译自身就推定合约可部署。
- 系统/token/第三方合约的 ABI、执行结果、错误、资源、通知/inline 和重放。
- 使用相同引擎、计费、负载和硬件的实际代价。编译器版本提高不保证 TPS 提高。

本轮新增的真实编译/链接/ABI 全集测试及 18 个原生 SDK 单元程序可以作为
后续迁移基线，但不能代替 WASM 实链或完整节点验收。A2 在本轮以
“迁移边界评估完成、迁移实现暂缓”跟踪。

## 与首版发布的关系

这两个决定只是不把长期研究无限挂在首版开发上，不降低已有发布标准。
CPU 资源规则仍保持当前首版边界；多核执行不等于可以忽略区块 CPU 配额，
也不能据此承诺 TPS 随核心数线性增长。若真实性能门槛仍不通过，应继续定位
瓶颈并报告未完成，不改判旧测试，也不把研究决策当成性能证据。
