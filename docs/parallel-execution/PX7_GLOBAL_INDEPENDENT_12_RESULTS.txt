严格独立负载
* 简单合约：真实CDT lightbench::step(actor,key,nonce)，一个action，一次已有行+1。
  每笔独占调用者及主键；整批不重复签名账户或业务行，无计算循环、sleep或假负载。
* 转账：真实当前eosio.token::transfer，每笔0.0001 SYS；每笔独占付款/收款账户，
  所有付款集合与收款集合互不相交，整份语料不复用账户，不是循环1,024对。
* 各类正式语料8,192笔；转账16,384个独立业务账户。简单调用者也使用独立账户。
  发压前检查完整目标集合，发送器验证实际签名包ID和action数，事后逐账户/行查账。
* 独立指业务写入与调用账户；公共代码/token stat/表元数据读取和链的按序资源结算仍存在。
  不承诺所有协议内部对象绝无共享，也不通过关闭授权、资源账单来制造独立。

预先固定测试设计
1. 先每类64笔，合约执行0/0、12/12两组冒烟；通过才启动正式负载。
2. 正式每类8个样本：先三轮0/0与12/12（顺序交替），每轮重新起链。
   这六个样本先单独测producer，自身真实Savanna最终确认，验证器测量期间不运行。
   生产暂停后才启动独立P2P validator，完整同步并核验状态和业务账本。
   该指标叫“单producer整批确认TPS”，不是两节点同时运行的全链TPS。
3. 每类最后另跑两个producer/validator同时工作的0/0、12/12对照，记录完整确认链路。
   两种口径分开，不拿延后验证节点的时间差解释实时积压。
4. 0/0指两端WASM实验并行关闭；12/12指两端各12 worker。验签等chain-threads
   固定12；不是把所有原有后台线程也强制单线程，更不是12物理核。
5. JIT、batch24、CPU6,000,000us/NET8MiB新创世诊断额度、状态DB256MiB。
   转账batch24避免触发64表快照预算；不放宽生产50ms、验证500ms准备保护或真实计费。
6. 8,192笔/秒发送1秒，排空30秒；全语料不复用账户。该短时负载不是稳态或绝对最高TPS证据。
   同时记录固定窗和整批首发至最后确认。固定窗0不会再令整个汇总除零，但仍原样呈现0。
7. 记录实际并行入口比例、采纳/尝试/回退、出块与验证日志、进程/每核CPU、噪声门槛。
   不强制绕过准入策略；若多数仍串行，必须报告，不能把12 worker配置当100%并行证明。
8. 独立验证包含真实余额、总供应、全部预分配行、stake/RAM、10/90资源状态和完整hash一致性。
   程序/输入前后SHA校验；任何业务失败保留并停止，不挑成功重跑、不降低原噪声门槛。

已直接观察到的瓶颈：
1. 入口碎批。首个12 worker样本8192次分发对应4808次排空，平均1.70笔；
   只3180次分发送入并行准备，另5012次直接串行。后续两轮并行准备分发
   5021、5329次；12 worker配置不等于8192笔100%进入并行。
2. 动态状态发现会重复执行。前三个并行样本attempts/succeeded为
   6359/3179、10042/5021、10660/5330，约2:1。计数含中止区块/重新处理，
   不是唯一交易覆盖率。prefix_refresh并不等于动态状态发现，不混称资产冲突。
3. 代码当前为owner取不可变快照、worker整批执行/会合，再owner逐笔核验落账；
   仍有串行段和批屏障。没有分阶段精确剖析，不能给每一段虚构耗时百分比。
4. 首轮有一次准备/worker deadline，次轮没有；不能把所有直接串行分发归因于超时。
   三轮capacity_reductions、capacity_bypasses均为0，未显示CPU计费容量是主要限速点。
5. 每批仅发1秒，整批确认还含出块与最终确认时延。CPU采样仅1秒粒度，
   首轮有效业务窗内只有一个完整间隔，不能据此推断亚秒峰值利用率或硬件极限。

源码对应：producer_plugin.cpp receive_ready_incoming/drain_ready_incoming（立即post排空，
无凑批等待）；incoming_transaction_batch.hpp preparation_count（单笔旁路）；
controller.cpp prepare_isolated_attempts（空访问集合启动、补状态重试、同步run），
for_each_parallel_production_transaction（按序callback/adoption）。
优先研究方向：有界且遵守出块截止时间的微批、可失效的访问路径提示/新鲜状态捕获、
减少每轮分配复制及批屏障、压低owner核验提交成本。不是单纯增加worker或取消安全限额。

正式结果（UTC 18:10测试结束，以下为最终测试结果）
1. 正确性：正式16/16组通过，核验131,072次业务执行；另有4组冒烟共256次。
   每类正式语料各8,192笔，同一份语料在8条重新创建的测试链分别执行，
   131,072是执行次数，不是同一条链上的131,072个独立账户对。
   全语料调用者/主键或付款/收款集合互不复用检查通过，真实签名、全账本、
   双端完整状态hash、资源政策与供应量检查通过。正式16组噪声证据均eligible。

2. 三轮主指标：单producer整批首发到最后最终确认TPS（验证器之后独立复核）。

   独立转账  3424.796 / 2926.711 / 3825.396   3400.623 / 3219.602 / 2939.867

   简单调用：串行3430.093 → 并行4059.896，原始+18.36%；

   这些是真实并发链路的整批确认结果，不与主指标混称，也不是持续负载峰值。

4. 为什么仍没有明显提高：
   a. 只有配置为12 worker，不是全体交易都经过并行。三轮简单调用并行入口
      提供3180/5021/5329次分发；转账为1862/1095/1544次。转账第三轮另有
      旧队列重新处理走并行，不能仅用实时入口分发或累计adopted冒充唯一覆盖率。
      大量直接串行不计入serial_fallbacks，因此该计数为0不等于没有串行工作。
   b. 简单调用约两次worker尝试对应一次成功，转账约七次；这是发现状态/通知等
      所需的额外尝试，并非七次完整合约执行。三轮转账统计为
      attempts/succeeded：13029/1861、7668/1094、17640/2520。
      prefix_refresh_requests为0，没有证据说明主要损耗来自资产冲突重做。
   c. 源码仍是owner捕获状态→整批worker执行/会合→owner按序核验/资源结算/落账。
      获取新状态会再次尝试，轻合约的有用计算不足以摊薄这些固定成本。
      现有日志不能给每一阶段准确分摊百分比，不虚构某一锁的占比。
   d. 准备阶段还有安全窗口：max_transaction_cpu_usage=150000us时，生产准备
      在剩余区块CPU额度充足时会预留150000+5000us给原串行处理；
      进入该窗口不再启动并行准备。
      它不同于区块CPU计费额度，不应为测试数字盲目删除。
   e. 所有并行组capacity_reductions/capacity_bypasses均为0，业务收据最大CPU
      占比仅10.37%。收据不包括隐式/待处理开销，但本轮没有支持“计费容量是
      主要限速点”的证据；也不能据此认为所有安全截止时间都没有影响。
   f. 一秒发压与最终确认时间使总指标易受区块时机影响，不是稳态。每样本仅
      1–2个完整的一秒CPU采样间隔；最高采样忙碌37.44%，没有持续跑满12逻辑核。
      不能由此排除亚秒突发，更不能把等待最终确认的低CPU当成硬件峰值测量。

5. 验证端的诊断（不是全链TPS）：
