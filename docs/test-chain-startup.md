# PureEOS 测试链新链部署与 TPS 测试标准流程

制定日期：2026-11-02  
适用范围：现有测试服务器上的 AIC 测试链重建、单 BP TPS 测量、历史服务恢复、BP 逐步加入及另行授权的故障验证。  
执行记录：[40 BP 部署与单 BP TPS](performance-results/machines/amd-epyc-4345p-8-core-processor--baremetal--8physical-16threads--65536MiB/20261102-bp-bond-newchain-r1/REPORT.md)、[投票、普通业务及浏览器准备](performance-results/machines/amd-epyc-4345p-8-core-processor--baremetal--8physical-16threads--65536MiB/20261102-bp-bond-preparation-r1/REPORT.md)、[五节点停机、永久黑名单及罚没验收](performance-results/machines/amd-epyc-4345p-8-core-processor--baremetal--8physical-16threads--65536MiB/20261102-bp-bond-offline-five-r1/REPORT.md)均分阶段留档。本文定义启动规则；每轮须分别记录通过、失败、未执行和正在进行的项目。

## 文档维护约定

本文件是后续测试链启动的统一规则入口。用户确定新的命名、账户、押金、权限、参数、启动顺序或留档规则时，必须先更新本文件及本轮执行计划，再按新规则执行；不能只留在聊天或临时脚本里。项目 `AGENTS.md` 保留入口和最新覆盖规则。

修改时记录日期、适用范围和被替代的规则。仅讨论、尚未选定的研究方案标明“未采用”，不得作为启动默认值。历史结果及已发布文件保持原样；更改默认值不等于授权重置现有链、增加服务器或追加压力测试。本轮经用户明确授权的新链部署和一轮单 BP TPS 测试继续按下述流程执行。

## 1. 固定执行顺序

**开发押金模式 → 远程构建和功能验证 → 归档旧链 → 部署新链 → 单 BP TPS 测试并保存记录 → 启动独立历史节点并恢复历史查询 → 其他 BP 逐个加入 → 验收与持续观察。**

单 BP TPS 测试完成前，不启动其他 BP、历史节点或索引后台。BP 逐步加入前，先使新链压测交易能够从历史 API 查询并在浏览器显示。

不得将多 BP 共享主机的结果写成多台独立机器的性能或去中心化资格证明。

## 2. 已确定的押金规则

| 项目 | 固定规则 |
|---|---|
| 普通 BP 准入 | BP 本人授权缴纳 `10000.0000 AIC` 后才能注册并参与出块候选 |
| 押金用途 | 履约担保；与 CPU/NET 质押、投票资产、奖励资金分开 |
| 押金托管账户 | 独立协议账户 `eosio.bond`，在治理封存前建立 |
| 罚没账户 | 独立协议账户 `eosio.bslash`，在治理封存前建立 |
| 退款 | 完成原生出块和最终确认职责交接、处理旧待结算窗口后冷却七天；退出检查点最终确认后领取 |
| 冷却时间 | `604800` 秒；不为测试或演示缩短生产规则 |
| 罚没触发 | 正式进入现有永久黑名单，罚没该 BP 专用押金 |
| 罚没资金去向 | 锁入罚没专用池；本版不提供转出、分配或销毁接口 |
| 普通撤票、轮岗、维护 | 本身不构成罚没理由；原生职责交接前仍需在线履职 |
| 既有违规证据 | 不因注销、退出、重新缴纳、重新注册或换密钥而清除 |

`eosio.token` 仅继续承担当前 AIC 代币合约职责，不作为押金或罚没资金的托管账户。

采用新链初始化方式，不以放宽“治理封存后禁止新建 eosio.* 账户”的保护来兼容旧链。两个托管账户必须在封存前由系统初始化建立，不预先手工占用账户名。

托管权限和资金流必须按以下方式验证：

- 初始化时，两个账户的 owner/active 均无普通私钥，阈值为 1，仅由 `eosio@eosio.code` 授权执行系统资金流程。
- 治理封存后，受保护账户 owner 权限的阈值为 1，但 keys/accounts/waits 均为空，不能满足授权；active 无普通密钥，仅保留协议允许的 `eosio@eosio.code` 和该账户自身的代码权限。封存后不开放普通权限修改路径。
- BP 永久拉黑时，先原子扣除其可退押金并记为待结算罚没；实际罚没决定块最终确认后，任何人均可触发一次结算，资金只能进入 `eosio.bslash`。待结算期间也不得退款。
- `eosio.bslash` 不部署可提款代码，本版系统合约不提供该池的转出、分配或销毁动作。开发者没有直接提款私钥。
- 保护账户的合约升级仍遵循既有开发者升级提案、七天审查及 BP 否决机制，并非必须获得 BP 肯定投票。开发者不能绕过该流程直接更新系统合约。“本版锁池”不代表今后经治理升级的代码永远不可改变；`eosio.prods`、`eosio.wrap`、`eosio.msig`、`eosio.null` 的永久限制继续保留。

本次不新增“拒绝最终确认签名”的黑名单条件，也不实施此前讨论的扩大确认委员会或超时接管方案。

| 项目 | 固定配置 |

| 工作方式 | 构建、合约修改和测试在远程测试服务器完成；本地负责编排与接收、校验允许保存的源码及证据 |
| 节点执行 | 所有运行中的 nodeos 均使用已验证的并行模式，保留最低硬件检查 |
| 区块 CPU | `max_block_cpu_usage=3200000`，CPU16 |
| 区块 NET | `max_block_net_usage=4194304`，4 MiB |

| 每连接交易在途保护 | 100 MiB |

以最新已验证的完整链参数预设为基础；旧 NET16、CPU32 等历史测试参数不作为本流程默认值。

## 4. 阶段一：开发与验证

1. 从最新通过资格验证的源码建立独立候选分支与远程工作目录，不修改其他 agent 的工作区或原有发布物。
2. 实现固定押金、注册及轮岗准入、退出交接、七天退款冷却和永久黑名单罚没。
3. 在原生控制器和真实 WASM 上验证资金流、授权、交易原子回滚与原生策略交接，不能仅用模拟账本证明通过。
4. 覆盖未缴押金注册失败、余额不足、重复缴纳、伪造充值、未交接退款失败、冷却期边界、合法退款、永久拉黑罚没、退款绕过、重复罚没及托管账户越权提款等情况。
5. 验证原有投票、资源、奖励、治理、轮岗、全链中断保护和历史权利仍正确。正常缺勤证据与预期攻击拒绝分开统计。
6. 记录源码提交、WASM、ABI、原生测试程序、运行二进制及配置的哈希；保留所有失败、修复与重试证据。
7. 文档中区分构建通过、功能通过、尚未执行的部署或压力测试；资格未通过的版本不得用于本次新链部署。

功能测试中可以使用原生测试控制器推进七天时间，但不得把生产合约冷却期改短，也不得以此宣称真实线上运行七天已经验证。

## 5. 阶段二：归档旧链并部署新链

1. 部署前读取现有拓扑、运行进程、服务、链 ID、合约、排班和最终确认状态，记录切换前基线。
2. 停止旧链自动注册、旧压测发送器及可能错误恢复旧实例的作业；按正确顺序停止旧 BP、历史源和历史后台。
3. 对旧链数据、区块、历史数据/索引及必要配置进行可恢复归档，保存旧链 ID、永久黑名单和完整证据。不得用新链记录覆盖旧结果。
4. 建立新的 genesis、数据目录、运行目录和链 ID；本次不新增服务器。普通 BP 与测试账户使用 12 字符原生名称，协议固定系统账户保留所需名称。
5. 部署已验证的新链系统合约和 AIC 代币配置：初始发行 `100000000.0000 AIC`，最大供应 `2100000000.0000 AIC`，不提前增发剩余额度。
6. 在治理封存前建立押金、罚没托管账户，初始化 RAM、资源市场及必要系统权限，核对押金模式已生效。
7. 只启动首个真实 BP `gptgenesisbp` 的节点进程。其本人缴纳 10,000 AIC、注册出块/确认/发现密钥、以本人账户给本人投票并获得入选条件，通过正常原生交接接替协议创世签名者。创世引导不作为普通 BP 的永久押金豁免。
8. 预先准备压测账户、真实 RAM 购买、自付质押、自付 PowerUp、转账资金和签名；为后续 BP 留足真实可支配的注册及押金预算，不能在封存后才发现资金不足。
9. 启用既有治理与必要协议特性，核对七天审查、并行模式、CPU16/NET4、16 GiB 状态容量、RAM1024及禁用 deferred stages。
10. 核对只有一个 BP nodeos 进程在运行，其他 BP、历史节点和索引后台尚未启动，链头与最终确认正常前进。

新链重新开始链内状态；旧链黑名单和违规证据必须留在旧链归档，不得伪造为新链产生的证据。逐步恢复的名单以切换前健康运行的 BP 为准，旧链已永久拉黑者不自动重新注册。

## 6. 阶段三：单 BP TPS 测试并保存记录

固定复用已有单节点纯转账方法，进行一轮测量：

| 项目 | 默认值 |
|---|---|
| 交易 | 纯 AIC 代币转账 |
| 发送连接 | 8 |
| 提交目标 | 80,000 TPS；仅表示客户端目标，不能写成链已达到的 TPS |
| 账户工作集 | 复用已验证的 81,920 转账账户对方法，在新链重新准备与签名 |
| 预热 | 1 秒 |
| 固定窗口 | 12 秒 |
| 排空观察 | 90 秒 |
| 生产者 SHIP | 关闭 |
| 其他 BP / 历史节点 / 索引后台 | 测量期间停止 |

不得重用绑定旧链 ID 的签名交易。准备工作必须先完成；计时期间不编译、不部署合约、不创建账户、不买 RAM、不做资源初始化、不启动额外节点或历史后台。

分别记录：

- 实际 CPU、核心/线程、可见内存、OS、源码、二进制、系统合约与所有测量参数。
- 客户端发送量、拒绝/丢弃量、实际入块量、最终确认量和未确认量。
- 固定窗口入块 TPS、固定窗口最终确认 TPS、全交易集入块与最终确认 TPS；不得混为一个数字。
- 区块高度、规范区块 ID、交易 ID、余额和完整性检查、CPU/内存/磁盘及发送时间边界。
- 原始日志、失败或中断原因、独立审计与哈希核验结果。

若因发送器、准备或采集错误导致本轮无效，保存原失败并注明无效原因；只有修复明确缺陷后才进行必要的针对性重试，不为追求更高数字自动追加多轮测试。

测量结束后形成可审计报告及摘要哈希；使用可追踪的链上记录保存结果摘要哈希，并保存对应交易及最终确认凭证。浏览器中后续能够查询本轮真实交易。历史“接近四万”的结果作为参考，不替代本轮实际测量。

## 7. 阶段四：独立历史节点与历史 API

1. 单 BP 测量完成并保存原始边界后，再启动一个独立的非出块历史 nodeos。
2. 历史节点同样运行并行模式，使用新链 ID，从新链创世同步，启用 SHIP；生产者继续保持 SHIP 关闭。
   在启动索引前，先通过历史节点自身 RPC 核对链 ID、同步进度及同高度不可逆块 ID 与新链一致；不能只检查 SHIP 端口存在。
3. 为 PureHistory 建立与新链 ID 隔离的历史存储、索引及消费游标，保留旧链历史归档。
4. 恢复历史后台，核对新押金合约的 ABI/profile，避免因新合约哈希未识别而静默漏记数据。
5. 验证历史节点与首个 BP 的规范不可逆块一致，确认索引从创世连续覆盖压测区间，能够查询压测交易及相关账户历史。
6. 保持既有访问地址：
   - 浏览器：`https://aic.matrixai.one`
   - 节点 API：`https://aic-api.matrixai.one`
   - 历史 API：`https://purehistory-api.matrixai.one`
7. 浏览器服务器继续提供静态前端，浏览器直接读取 API；核对新链 ID、最新区块、近期交易、供应量、节点及轮岗信息，不显示旧链缓存。

“历史节点”与“历史索引/API”必须分别验证。端口可访问或 API 返回成功，不等于压测交易已经完整入库。

默认每批仅加入 1 个 BP，相邻节点的启动时间至少间隔 60 秒。同步、注册最终确认及签名发现的等待时间计入该间隔；只有上一节点全部必要检查通过，且启动间隔已经满足，才启动下一节点。前一个节点未通过时暂停后续批次，不通过缩短原生交接或绕过押金条件来追赶计划。

每个 BP 的固定步骤：

1. 核对 12 字符身份、独立账户/出块/BLS/peer 密钥及服务、端口，私钥和钱包只保存在远程受限目录。
2. 在计时测量结束后准备真实资金、RAM、本人资源质押与 PowerUp；本人授权缴纳 10,000 AIC 押金，检查托管余额与个人押金账本一致。
3. 注册 BP、BLS 确认密钥及 peer key，按原规则投票；押金不替代投票或密钥条件。
4. 使用独立数据目录启动并行 nodeos，生产者 SHIP 关闭，核对实际 BP gossip 连接、同步和规范不可逆块。
   节点先于注册启动时，先用普通引导连接同步。等待链上 peer key 缓存更新并生成本人的签名广播；若原普通连接仍未进入签名发现状态，可重新连接同一个引导地址一次，再验证真实签名连接及学到的其他 BP 广播。记录该次恢复，不用手工填入全量 BP 地址，也不把仅有普通静态连接算作发现通过。
5. 确认缴纳、注册和密钥操作的交易已经最终确认，记录时间、交易 ID 与区块证据，才推进下一批。
