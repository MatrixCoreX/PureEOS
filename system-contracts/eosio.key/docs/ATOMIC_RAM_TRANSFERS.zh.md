## 本金、费用与 RAM 的关系

收款人收到完整本金。付款方另外承担 AIC 应用手续费；发送 USD/CNY 也要有 AIC。
收款公钥可以没有 AIC、没有命名账号，也不必自己开表。以后主动转出才需要 AIC 手续费余额。

以 0.0001 AIC 为一个整数单位，计算：

```
work = ceil(unit_fee × work_units × PowerUp_multiplier / 10000)
RAM = 实际调用 eosio::buyram 的 AIC 总额（含原生买入费）
base = max(0.0100 AIC, work + RAM)
relay = 无中继时 0；否则 ceil(base × 已签中继费率 / 10000)
total = base + relay
系统保留费用 = base − RAM
```

中继费率为 10%–30%，按 0.0001 AIC 向上取整，正费率至少一个单位。
PowerUp 倍率依据链上 CPU/NET 市场占用，不是机器负载；倍率只乘工作费，不乘 RAM。
普通命名充值工作量为 8；key→key 为 `8+ceil(memo_bytes/64)`；key→命名为
`10+ceil(memo_bytes/64)`。`unit_fee`、倍率上限等以该次初始化的公开策略为准。

`RAM` 根据当前已审核 RAM 曲线反算，并包含向上取整的 0.5% 买入费和一个净 AIC
单位的舍入余量。真正支出的就是该总额；原生 `logbuyram` 必须确认 payer/receiver
均为 KEY、金额一致、得到的 RAM 不少于预算。余量转化为实际多买到的 RAM，不是重复收费。

预算是保守分配上限，不是逐行精确测量：新公钥加首余额 1536 字节；已有公钥新增币种
余额或命名收款人首次开代币余额 512 字节；已有记录 0。非原生代币首次准入另含
2048 字节元数据/托管余额预算，仅首次承担；AIC 初始化已具备元数据，不加这一项。

交易同时核对实际原生 RAM 配额、每币种预算、全局数量上界和托管准备金等式。
已有记录不再次购 RAM；两个并发请求创建同一收款人，后执行的交易看到已有记录，不能重复收购置费用。

## 1. 命名账号 → 公钥

钱包构造**一个交易、一次命名账号签名、三个根动作**：

1. `eosio.key::deposit` 声明发送人、币种、收款公钥、完整本金、费用上限和请求标识。
2. `eosio.token::transfer` 从同一发送人支付本交易 AIC 费用资金 F，附言固定为 `atomic key fee`。
3. 对应代币 `transfer` 从同一发送人转完整本金到 KEY，附言固定为 `atomic key principal`。

三个动作都明确由发送人 `@active` 授权。合约验证完整报文和实际入账，自动购缺失记录
所需 RAM、创建记录、全额记账，并在同一交易退回 `F−total`。没有持久手续费预存余额，
也不需要另发一笔充值交易。签名权限不广泛委托给合约。

F 必须够本次费用且不超过已签 `max_fee`。SDK `nativeDepositActions` 可指定
`feeFunding`，默认使用 `max_fee`；因此命名发送人须暂时持有 F，而实际只扣 total。
发送 AIC 须暂时有“本金+F”；发送 USD/CNY 须同时有对应本金和 F AIC。
发送账号自己承担这笔原生交易的 CPU/NET。无商业中继服务费。

直接向 KEY 发旧 `fee`、PK1/PK2 附言的独立转账会整体失败，不能悄悄退回旧预存模式。
旧原生 cleos 的命名→公钥封装尚未适配三个动作；应使用本分支新版 SDK 构造后由合法钱包签名。

## 2. 公钥 → 公钥

1. 钱包查询审核过的实际链/合约、币种、资源报价、记录情况和所选 BP 中继费率。
2. 用户本地签名完整原生交易和 owner 证明，绑定收款公钥、本金、币种、期限、撤销代次、
   请求标识、选定 BP、费率及总费用上限。不同设备不需要共用序号分配器。
3. 中继校验并用自己的命名账号/专用子权限提交，承担原生 CPU/NET。
4. KEY 独立验证用户证明及 BP 资格，从发送公钥的 AIC 账本扣实际 total，扣完整本金；
   缺记录时用费用中的 RAM 金额自动调用原生购买，再创建记录和全额贷记收款人。
5. 原生实际 RAM 支出只从准备金移出一次；费用留存及 BP 收益分账，发出费用回执。

发送 AIC 时扣“本金+total AIC”；发送 USD/CNY 时扣该币本金及额外 total AIC。
收款人不必准备 AIC。中继没有用户私钥，单靠中继权限不能改收款方、提高上限或替用户授权。

## 3. 公钥 → 命名账号

用户证明和中继提交方式同上。命名收款账号必须已存在。若该账号没有该代币的余额行，
KEY 用本次费用购买 512 字节预算，并以 KEY 为 RAM 付款人调用审核过的 token `open`，
随后转出完整本金。AIC/USD/CNY 均自动处理，收款账号不必预开表或预先有 AIC。

已有余额行时不购买 RAM。发送方仍付工作费与选定中继费；收款方不签字、不承担这笔
原生交易 CPU/NET。可用命名账号资源的持有人也可走 `selfout`：自己的命名账号明确
授权并承担 CPU/NET，用户公钥证明仍必须通过，商业中继费为零，工作/RAM 费用仍保留。

## 原子失败、领取与维护

费用超上限、资金不足、白名单/系统摘要改变、签名错误、重复/过期交易、非法内部调用、
容量不足、原生购 RAM/open/transfer 失败都会回滚本金、费用、曲线、配额和账本记录。
实际测试还故意在排队购买 RAM 后触发容量失败，验证整笔退款回滚。

中继及网络收入 `claim` 继续全额、零应用手续费。领取人承担原生 CPU/NET，缺失的
领取 AIC 行由领取人自己付 RAM；不能把免费 claim 的开表规则与普通自动转账混淆。

KEY 仍非特权、owner 封印、active 仅代码权限，无 dev/BP 直接改账、冻结或改公钥入口。
后续合约维护仍走公开的精确代码提案、公示和 BP 否决；这是一套治理保障，不宣称任意
获准的新代码在数学上永远不能改变行为。USD/CNY 的普通发行账号管理不等于控制 KEY。

历史命名充值接口、浏览器费率模块、原生 cleos 和已发 Android APK不能因为签名线格式
部分兼容就宣称全部适配；新链的调用、Chain ID、代码摘要、历史索引和界面仍须更新并验证。
